# 主动业务助理

玄圃维护承诺、业务进展和跟进状态。LLM 从当前员工的主对话、本人业务会话及工作区识别承诺、等待结果、可能停滞和缺少安排；系统复核证据、权限和版本后通知。没有建立待办也能识别，模型不能凭空认定业务完成或未完成。

## 状态与数据流

1. `ProactiveWorker` 分别运行规则扫描和语义评估循环，慢模型不阻塞时间检查。
2. `ProactiveService` 在工作区员工锁内认领评估，保存租约和下次执行时间，随后释放事务调用模型。
3. 模型使用既有 `fast` 档位、租户预算、并发准入和员工用量审计。输出只包含结构化候选，引用必须来自当前上下文。输入是数据，不能成为后台执行授权。
4. 提交时重新检查员工、消息/工作区版本及业务会话活动快照。已完成、回收或非待办记录不能被模型重新变为催办对象。
5. `proactive_check`、`proactive_followup`、`proactive_scan_state` 与工作区写入共用事务。通知直接写现有 `notification`，来源为规则、语义或原生提醒，复用 `notification_delivery`。
6. 用户确认安排后转为 `waiting`，保存明确 UTC 时间；到点核实，完成/忽略后停止。记录新进展时取消旧提醒并重新安排复查，不能保留旧时间。

## 进展与去重

待办 `last_progress_at` 与 `updated_at` 分离，改标题不代表业务有进展。目标或有效进展改变才推进 `generation`；规则按阶段唯一，同一消息的独立承诺使用片段序号。语义与规则命中同一待办时合并关注事项。

语义上下文最多100条、32KiB，主对话、业务会话和工作区摘要各有独立字节预算。主消息和业务长文本以稳定字符偏移分段，完整读完才推进记录游标；未读片段不会被标成已检查。工作区每轮分页25条，长字段摘要明确标记截断；已有待办跟进复查恢复当前版本。旧承诺同时恢复原始证据与最近已读进展，并读取关联业务会话的新消息；所有来源会话参与提交前版本复核。没有新增建议也推进已读关注事项的复查时间，避免历史挤占。

## 用户操作与通知

对话建议卡、通知“处理”入口和功能页共用 `/v1/proactive`。所有决定带请求幂等键、跟进版本和可选待办版本。设置原生提醒通过 `ReminderService.prepare` 和工作区事务 outbox 原子提交；完成、延期或进展同时取消旧提醒。提醒管理页的改期与取消也在同一员工事务中同步跟进状态、时间、版本和旧通知资格。模型复查保留用户安排的原生提醒关联。

员工无需配置模型或密钥，默认启用站内跟进。外部渠道须本人选择；飞书是可替换出口。免打扰保留站内通知，延迟浮层与外部发送；原生提醒若关联主动跟进，也使用该设置。通知游标在员工行锁内分配并持有至提交，避免晚提交记录被跳过。用户处理后，旧通知仍留作历史，但事务内撤销其排队投递；浮层到点和外部发送前再次核实来源，避免过时提示。后台复查时间与用户确认的到期时间分别保存。

## 实际限制

模型判断可能不完整，系统以证据和询问表达不确定性；无法获知的外部业务结果不会自动确认为完成。默认每用户30分钟最多一次语义评估，规则每60秒扫描；有界分页和服务负载会影响可见时间，不承诺即时或硬实时。原生规则提醒在模型错误或预算耗尽时仍独立运行，语义失败记录错误并退避重试。
