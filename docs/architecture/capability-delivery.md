# 能力目录与安装契约

R4-A已实现能力登记、配置预检和待发布安装（[记录](../guides/releases/2026-10-25-r4a-acceptance.md)）。R4-B已在源码实现到人分配、统一能力决策、调用绑定与文件型能力完成契约；R4-C已在源码实现隔离评测与证据绑定的按员工发布、停止、撤销（见下文），安装只能经发布置为ready。尚未生产部署。

## 数据归属与兼容

业务归档正本仍由PackageRegistry和ObjectStore管理。独立delivery.json指向精确包名、版本、归档SHA256与入口，不能放进自己引用的ZIP形成自引用摘要。能力标识与同租户package+entry永久一一对应，每份修订、预检和安装配置不可改写。不同版本可追加同能力修订；相同描述复用已有修订。

新增capabilities领域复用现有协调事务，不另建发布数据库或执行内核。0020增加capability_root/revision/preview/config/installation五表，租户复合外键限定引用。当前安装可通过CAS替换配置指针，旧配置继续保留。登记、状态、outbox事件及操作回执在一次协调提交中落库；内存后端同样异常回滚。所有请求依据服务端当前身份，机器管理密钥不能冒充员工。

登记与staged安装不会改变旧包active_version、旧会话或R2执行规则。私人工作方法记录也不授予执行权。

## 到人分配与能力决策（R4-B）

`capabilities/assignments.py`、`resolver.py`，迁移0028的`capability_assignment`表。分配目标为直接到人（`{kind:user,id,user_epoch}`，固定员工生命周期代次）或可选按岗位/部门（`{kind:position|unit,id,target_version}`，经员工当前真实任职解析，目标结构版本须仍为分配时确认的版本）；`allowed_revisions`为1–20项明确修订，没有通配符；可选`valid_until`。撤销按版本CAS，代次加一，不可复活或改写，不物理删除。分配只授权使用能力，不授予读文件、使用连接或组织审批。

能力决策`decide`只由认证员工和权威记录构造：员工在职且代次相符；有一个生效发布把这名员工（含代次）列在固定名单里（多个生效发布同时命中409，不猜）；发布固定的安装仍为`ready`且配置未被替换；发布所用修订在某项有效分配的范围内（多项分配命中取最早一项）；没有依据一律404。分配与发布缺一不可：分配说明谁可以用，发布说明哪个经评测的版本对谁生效。`resolvable`给出员工此刻可新受理的全部能力，即`GET /v1/me/capabilities`与对话目录的数据来源。

## 统一入口与调用绑定（R4-B）

包内任一入口登记为能力即视为纳管，纳管包的每条入口都经`CapabilityAdmission`：

- **新受理**：显式`POST /v1/sessions`、对话分流（目录按员工过滤并换成决策版本）、管家匠人目录与派工、`work-tasks`交办、定时/事件发生实例（在实际发生时受理，定义固定的版本须仍是员工此刻的决策版本，否则阻塞`capability_unavailable`）。须员工身份、租户开启`capability_delivery`、有效决策；显式版本不等于决策版本404；机器身份404；纳管包里未登记的入口拒绝运行。
- **调用绑定**：新会话与新任务各写一次`capability_binding`（迁移0028），固定员工代次、能力修订、包摘要、入口、安装与配置、分配及代次；同键重写须完全相同。会话与绑定分属不同存储，没有同一事务：进程在两者之间退出时，纳管工作因缺绑定在续跑时被拒，不猜依据。
- **续跑复核**：续聊、批准后继续、任务承载会话的每一轮都对照绑定复核——员工代次、原分配（同id同代次、未撤销未过期）、原安装（`ready`/`draining`可收尾，`disabled`拒绝）；不用此刻恰好存在的另一项授权替换失效的原依据。每一轮开始与批准恢复时复核；一轮内**每次模型调用前**也复核（`runtime/capability_guard.py`：模型会话打开与每次发请求前，按服务端执行空间 `session:`/`task:` 找绑定，不在每个流式块上复核）——撤销落在轮开始之后，这一轮的下一次模型请求即被拒。未纳管的包直接放行，但每次模型请求多一次能力快照读取，能力存储不可读时这一轮失败（不放行）。经权限策略的每次工具调用执行前同样复核（`CapabilityPermissionPolicy`：先核资格再交给原策略；批准恢复时内核对它调用的 `preapprove`/`issue_grant`/`revoke_grant` 原样转给原策略），资格失效时已有批准也不能放行这次调用。
- **旧激活接口**：纳管包的`POST /v1/packages/{name}/activate`与`publish?activate=true`返回409（后者在写归档前拒绝），不发布可照常上传。
- **开关**：`capability_delivery`关闭时纳管能力不能新建，不退回旧的全租户入口；已绑定的工作按上述当前资格收尾。
- 能力读取经协调存储的只读快照`capability_snapshot`（可重复读、不取租户与员工锁），可在已持锁的任务事务里调用而不互等。

## 隔离评测与按员工发布（R4-C）

`capabilities/evaluations.py`、`releases.py`，迁移0029的`capability_evaluation`、`capability_release`表；均不物理删除。

- **评测**：`POST /v1/capability-evaluations`固定能力修订、安装配置摘要与套件摘要（严格JSON`xuanpu-eval-suite/v1`，最多50个用例，只允许包含/不包含/token上限这类预定义检查）；套件摘要须等于交付描述的`evaluation_suite_sha256`，否则409。后台串行运行，按实际轮次结局与回复独立判定，不听模型自报；总token超预算`blocked`。评测会话经`sessions.create(evaluation_id=…)`建立、写评测绑定，只在评测进行中且评测记录列名时可续，评测结束后不能复用。声明企业连接或写入/外部工具的能力本版本直接`blocked`（`external_implementation_not_verified`），不用替身补pass。进程中断时仍在进行的评测在启动时标`interrupted`，不自动重放。
- **发布**：只读预览核对证据（评测通过、7天内、评测针对的正是这个安装的某个配置快照，修订与配置摘要一致；不要求是安装此刻的配置）、固定员工名单（1–100人含代次）与重叠的生效发布，返回确认摘要；确认发布在事务内重算，摘要不符或`supersedes`与重叠集合不一致409。被取代的发布改为`retired`，首次发布把安装置为`ready`；`POST /v1/installations/{id}/state`仍拒绝直接置ready。
- **首次纳管排空预览**（`capabilities/drain.py`，`GET /v1/admin/capability-drain?package=`）：登记前只读数出这个包仍在进行、没有能力依据的会话与任务承载会话（纳管后它们续跑会被拒），扫描上界 2000、超出标 `truncated`；定时安排不统计。只是预览，登记本身不因此阻塞。
- **停止与撤销**：`retire`只拒新受理，已绑定工作按原授权收尾；`revoke`代次加一，续跑复核拒绝其已绑定工作。两者都不改旧任务的包、配置或输入。
- **配置快照与升级**：每次安装都追加一个不可变配置快照；发布固定它评测时的那个快照，能力决策按发布的快照运行，不看安装此刻的配置。升级（重新预检、安装新修订）不撤销已生效的发布：安装保持`ready`/`draining`，旧发布照常可新受理，直到新修订评测并发布、取代旧发布为止。
- **回退**：用旧修订的配置快照与它7天内通过的评测再发布一次（取代当前发布），同样走预览与确认，不需要重装；评测已过期则需重新安装该配置并重新评测。已受理的工作始终按各自绑定的版本与配置继续（`T/r4_contract/test_office_rollback.py`）。
- 目前没有：评测制品对象存储与原始报告下载、平台/沙盒策略指纹进入证据、原生发布界面与故障注入用例（见R4-C计划进度）。

## 文件型能力完成契约（R4-B）

完成契约只由决策固定的能力修订决定（`WorkTaskService.capability_profile`），客户端与模型都不能指定：输出契约为`office_files`/`table_summary`的能力按办公任务受理（`execution_kind=office`、`completion_policy=office_files`），只接受交付描述声明的CSV输入，沿用`outputs/manifest.json`与四类成果校验，缺一失败，不凭只读回执判成功；其余能力照旧`capability_receipt`。手动交办与发生实例共用同一判定。

## 严格描述与权限

格式为xuanpu-delivery/v1；未知字段拒绝。输入与输出只接受office_files、capability_receipt或read_only_answer固定契约，成果类型须匹配输出契约。A只核对声明，文件成果适配及运行完成核验留给B2。

permissions固定脚本命令/出网、审批等级、模型档位、预算，以及外部工具名称、参数schema SHA256和effect。这些值须匹配已校验的包清单；未填写的包预算按平台默认值解析后比较。MCP必须在包中明确白名单，不能开放全部工具。连接要求使用可替换的wecom只读连接契约。

公开参数只能填写requirements声明的键、类型与枚举。secret_refs是逻辑槽至本租户保管库名称的绑定，connection_refs是连接槽至本租户已安装连接的绑定；均不接受秘密明文。公开响应只显示凭据配置状态，内部密文变化指纹、实际秘密引用和连接元数据不回显。交付描述不得携带企业身份、材料或机器路径；文本本身由管理员核对，服务端不声称能识别自由文本里的所有敏感内容。

## 两阶段预检与提交

1. 管理员显式请求预检；读取精确修订、现有安装版本和当前身份，不创建业务任务。
2. 事务外核对归档真实字节及摘要，打开声明需要的沙盒，启动连接器并列出工具。只握手/列工具，不调用业务工具，不调用模型、不读取员工材料。stdio启动会执行交付方声明的连接器启动程序，仍受既有沙盒规则约束。
3. 固定完整实际MCP清单（白名单外新增工具也改变摘要）；获准工具另按名称、schema、effect精确核对。HTTP依据归档OpenAPI声明核对，HTTP/远端实现版本无法核实则内部标implementation=unverified；不声称已核实业务服务语义或远端部署版本。
4. 重新进入协调事务，重查当前身份、配置版本、密文及连接版本，写预检证据与回执。默认900秒到期，探测默认30秒，单个平台串行探测。
5. 人工确认preview_id、expected_version和布尔confirmed=true。应用前再次执行完整预检，证据须相同；最终事务再核本地证据和CAS，然后只追加staged配置及安装事实。数字1或字符串true不能代替确认。

凭据证据使用随机化SecretRecord密文的SHA256，不对秘密明文计算摘要。get_bound一次读取、比对并解密同一记录，避免先核版本再另读新秘密。底层连接secret_ref同样记录密文版本；覆盖、删除、重建均使旧预检失效。PG在最终协调事务内通过FOR SHARE持有秘密行直到提交，避免最后核对与写安装之间被覆盖。A不缓存业务运行凭据；实际运行缓存失效属于B。

预检列明缺失配置、凭据、连接范围、预算或依赖故障；不足条件不能安装。安装确认时过期、工具/schema增长、依赖变化、配置并发变化均409，要求重新预检。输入422、无权403、异租户记录404；清理未完成503，不伪装成安装成功。

## 资源关闭与冷恢复

每次探测使用专属data_dir/capability-probes/probe_*目录。启动中尚未交出句柄的异常也登记清理凭证，全部收尾完成才删除目录。某个关闭失败保留责任；关闭被取消时保留当前及后续句柄供重试，平台关闭会等待在途探测及遗留清理。

Docker可按确定工作目录映射的容器名回收，不扫描其他部署。未知的本机遗留目录无法证明内存进程跟踪之外的进程已退出，因此保留现场并拒绝继续启动或预检；管理员须核实对应进程退出后处理该专属目录，不能直接据目录存在判定安全。全量关闭开关也不跳过遗留资源回收。

## 入口和运行边界

管理员使用“能力配置”登记、预检、查看权限差异、保存与停止安装；发布与分配可在“能力配置 → 运行结果与发布”里查看并经确认停止、撤销（`capability-operations.js`）；安装后的能力卡另有“分配给员工”“发起评测”“发布给员工”（`capability-release.js`）：员工从在职名单选择并按`lifecycle_epoch`固定代次；评测上传交付方的suite.json；发布先取只读预览（每人从哪个修订到哪个修订、将停止的重叠发布），确认时带预览摘要与`supersedes`。每一步先显示确认卡，断线重试沿用同一操作号。员工“功能→我的能力”查询本人此刻可新受理的能力。关闭capability_delivery新受理仍允许管理员查询和停止旧安装。SDK、CLI和原生界面共用HTTP服务、当前权限、CAS及操作回执，不自动补确认或重发写请求。
