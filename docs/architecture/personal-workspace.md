# 原生个人工作台

玄圃是企业核心。文件夹、文件元数据、事项、待办、日程、个人技能、助手偏好和主对话属于玄圃原生领域；飞书等办公平台可作为在线文档或通知适配器，不是这些记录的长期权威，也不要求外部平台提供同名功能。外部文档只保存经过校验的 HTTPS 引用，正文仍由原平台持有；玄圃不根据该地址主动抓取内容。

## 两个入口与一套规则

普通员工以主对话为默认入口，助手可以提出待确认建议；“功能”入口提供直接增改、文件上传、版本查看和回收恢复，两者调用同一个 `WorkspaceService`。模型提供的建议不构成写入授权，确认后的输入仍须通过类型校验、本人关联校验、版本和配额规则。个人技能保存提示说明，不新增脚本执行、连接器访问或业务包授权。

每种记录采用独立的严格输入模型，拒绝未知字段和类型转换。文件内容派生的大小、媒体类型、版本号不能通过普通元数据更新修改。日程采用 UTC 秒保存起止时间，同时保存显示时区；截止时间和时区均接受明确验证。记录统一返回 `id/kind/data/version/created_at/updated_at/trashed_at`，内部对象键和回收批次不对外公开。

## 个人授权边界

所有服务调用必须有当前启用的租户及员工身份。机器 API key 没有个人工作台；管理员身份不会授予读取其他员工私有记录的能力。记录、文件版本、主对话、偏好和请求幂等键均按 `(tenant_id,user_id)` 隔离。附件和事项关联只能指向本人有效记录。既有登录、Cookie 和 CSRF 校验在 HTTP 入口继续生效。

主对话允许服务内部写入 `user` 或 `assistant`，HTTP 的工作台消息接口仅允许读取，客户端不能伪造助手消息。服务内部结果元数据上限为 64 KiB；文本、附件标识和可选事项在独立模型中验证。

## 持久化与原子性

控制面装配相同协议的内存后端及 PostgreSQL 后端。迁移 `0007_workspace` 包含独立的记录、文件版本、偏好、主对话和请求幂等表。PostgreSQL 事务按租户共享锁、员工排他锁顺序执行，保证当前身份、名称、目录关系、版本 CAS、配额、幂等和审计在同一元数据事务内提交。其他员工之间不共用排他锁。内存后端以员工锁和隔离快照提供相同行为。

文件正本使用现有 `ObjectStore`，名称从不参与对象路径；每次内容上传产生唯一对象键。数据库只保存元数据、对象引用和内容摘要，所有历史正本保留。对象写入先于元数据提交，避免成功记录指向尚未保存的内容。对象存储和数据库不是分布式事务：数据库提交失败可能留下无引用对象，此时请求明确失败，工作台记录、空间统计及幂等响应不会部分提交；未来清理必须先核对引用，不能删除已保存版本。

每次领域写入只审计动作、记录标识、类型和版本。文件字节、技能正文、消息正文、个人偏好值和模型结果不进入工作台审计。

## 文件与回收规则

- 单个文件最多 20 MiB；每人文件总空间 1 GiB，包括历史版本和回收站文件。
- 每人最多 10000 条工作台记录、10000 个文件版本；单个文件最多 1000 个版本，空文件版本也计数。
- 同一目录的活动文件和文件夹名称忽略大小写后唯一；拒绝路径、控制字符和特殊目录名，不允许目录环或移入回收站目录。
- 删除目录递归回收所有当前活动后代，保存共同回收批次；之前已单独回收的后代保留原状态。
- 恢复目录一次恢复整个批次；父目录不可用或名称冲突时整体回滚。属于目录批次的子记录须先恢复所属目录。
- 不提供永久删除正本操作。已有元数据关联的事项不能回收，包含回收站内的关联记录；需先恢复并解除关联。历史主对话中的事项标识是历史上下文，不阻止事项回收。
- 下载只读取已有对象，响应强制 `attachment`，并设置 `nosniff`、`private, no-store` 及沙盒策略；HTML、SVG 等内容不会以内联页面形式执行。

## 主对话、重试与建议

主对话使用每名员工独立的单调递增游标，每页至多 100 条；最近窗口逆向读取后按时间升序返回。事项对话先验证本人事项，再按事项索引筛选，最后应用分页窗口。消息请求标识在员工范围内唯一，服务可以按索引直接找回已保存助手结果，不必重新采样模型。

待确认列表通过助手建议的部分索引先筛选，再排除同请求的权威结果回执或兼容历史终态消息，最多返回最近 100 条。后续普通聊天不会占用这份列表的分页窗口。来源消息采用 `<request_id>:assistant`，终态采用 `<request_id>:confirmed` 或 `<request_id>:cancelled`。

原生记录确认通过 `create(..., proposal_id=<request_id>)` 将 `proposal:<request_id>` 的确认决定、`<request_id>:create` 的创建结果、领域数据和审计放在同一员工事务中。名称冲突、关联失效、容量超限或审计故障会连同决定一起回滚，用户仍可修改草稿后重试或取消。领域创建成功后，同内容重试返回原结果，改变创建内容或取消均返回冲突；HTTP确认入口先返回权威回执，忽略已确认操作重发的旧草稿字段，不再次写入。取消也使用同一员工锁，并读取相关决定与创建结果，避免跨进程同时出现已创建和已取消。

提醒确认同样通过 `ReminderService.create(..., proposal_id=<request_id>)` 实现决定与提醒创建同生共死：PostgreSQL 复用原有租户/员工锁，在提醒事务内写入工作台决定；内存后端与工作台取消共用员工锁，批量提交决定和提醒审计后不让出执行权地提交提醒。时间过期、活动提醒额度或审计失败均回滚决定，用户可以调整输入或取消。普通提醒创建不经过建议流程。

建议决定同时保存权威结果回执：原生记录返回完整创建结果，提醒返回持久提醒标识，取消返回取消状态。这些回执与领域写入处于同一事务，`proposal_result` 按本人请求索引读取。`<request_id>:confirmed` / `:cancelled` 聊天消息仅用于展示；即使进程在领域提交后、消息追加前中断，刷新仍显示正确终态，待确认列表也不会再次列出该建议。确认前编辑过的字段以回执结果为准，不依赖重新提交最初的模型草稿。


## 路由恢复与分页

员工路由按租户、员工、请求标识保存原始请求指纹与60秒持有租约，跨实例重复请求不会同时采样。模型选择先持久化，业务会话标识按同一请求稳定派生，后续再保存完整结果和展示消息。会话已创建而结果/展示消息写入失败时，重试恢复相同会话与选择，不重复模型调用；请求内容改变返回冲突。尚无副作用的无效模型选择或创建前业务切版会清除选择，允许原请求重新识别；已经创建的会话按原版本恢复。

这不承诺外部模型请求严格执行一次：若进程在模型返回、选择持久化之前硬崩溃，租约过期后可能重新采样。已保存选择、会话或结果的恢复不再采样。失败或取消的计量使用完整系统提示、文本附件和有界保守图片/PDF估算；供应商实际用量优先。

主对话默认读取最新100条，`before_id`提供排他上界供“加载更早记录”向前分页，`after_id`下界同时生效。没有以总历史条数静默截断最新对话；历史响应受身份、会话和请求轮次约束，不覆盖新回复。若终态聊天缺失，界面根据权威确认回执恢复提示。


输入框正文与工具栏置于同一容器，附件选择使用独立的锚定菜单，不复用模型写入建议容器。菜单在再次点击、外部点击、Esc、焦点离开、发送或上下文切换时关闭，所有按钮保持非提交类型；输入文本、暂存附件与确认卡编辑不因收起菜单而清空。

欢迎页与历史对话共享弹性空间；对话区可缩小，输入框保持自身高度，避免短视口中工具栏溢出对话面板。
