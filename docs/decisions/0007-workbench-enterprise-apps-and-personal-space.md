# ADR 0007：企业版产品形态 —— 员工工作台、企业应用、个人空间（参照 open-dots）

- 状态：Proposed（对照分析与方案建议；采用与否、先做哪块待拍板）
- 日期：2026-09-30
- 关联：ADR 0001（定位与分层）、ADR 0003（成熟组件采用不自研）、ADR 0004（四平面与效应闸门）、ADR 0005 决策 8（沙盒按运行时划分）、ADR 0006（MCP 网关评估）
- 参照：[open-dots](https://github.com/Anil-matcha/open-dots)（MIT，核对版本 `617ac65`，本地 `<open-dots 本地检出>`）

## 背景

xuanpu 第一版面向的是「系统」：业务方发布业务包，集成方拿 API key 调接口，管理员用控制台。它没有面向「员工」的入口。

现在的目标是做出企业级的员工产品，参照 open-dots 的形态（助手对话、插件、审批、审计、电脑操作），并包含 open-dots 没有的两块：

- **企业应用**，分两层：上层是企业发布给员工用的 agent 应用；下层是这些应用背后接入的企业系统（OA、CRM、IM 等）。
- **个人空间**：每个员工自己的网盘式工作空间。员工在这里完成自己的全部工作，用起来像一台电脑；以后内容的编辑、编写都在线完成。

本 ADR 做三件事：核对 open-dots 实际做到了什么；列出 xuanpu 离目标差什么；给出方案建议和拆分顺序。不涉及实现。

## open-dots 实际做到了什么

README 把它描述成「对话、工具调用、审批、连接器、电脑任务」合一的工作台。逐项对代码核对的结果：

| 能力 | 实际实现 | 位置 |
| --- | --- | --- |
| 助手 | 用户自建：名称、角色、系统提示词、模型、头像配色。一个助手对应一条对话线 | `server/app/schemas/contracts.py`、`routers/bots.py` |
| 对话 | 流式输出，历史存 SQLite | `routers/chat.py` |
| 工具调用 | **模型不会自己调用工具。** 只有用户输入以 `/workspace` 或 `/connector` 开头时才解析成动作，执行结果拼进系统提示词后再让模型回答 | `routers/chat.py:84-205` |
| 动作闸门 | 动作必须先登记才能执行，未登记的一律拒绝；每个动作有统一信封（工具、动作、意图、目标、参数、给人看的预览、风险分类、是否要审批） | `services/action_gateway.py` |
| 审批 | 进程内的 `asyncio.Future` 等待，默认 120 秒超时；进程重启后待办丢失 | `services/approval_broker.py` |
| 审计 | 动作全生命周期各记一条：请求、批准 / 拒绝 / 过期、开始、完成 / 失败；结果只记结构摘要不记内容；凭据类字段脱敏 | `action_gateway.py:203-242` |
| 插件市场 | 内置 24 个应用的卡片加 Composio 的 OAuth 跳转。真正能执行的只有 GitHub 列 issue、建 issue 两个动作。拉取 Composio 在线目录的代码用了 httpx 没有的 `res.ok` 属性，异常被吞掉，所以永远显示内置列表 | `routers/connectors.py:78`、`services/connector_actions.py` |
| 电脑 | 每个助手一台：统一的供给方协议（假实现 / Docker / 远端），有创建、启动、暂停、停止、重置、健康检查的生命周期；容器只读根文件系统、去掉能力、限制进程数、seccomp。由界面按钮驱动，不由模型驱动 | `services/computer_provider.py`、`docker_computer_provider.py` |
| 文件 | 只有两样：图片上传（转存到模型服务或退回成 data URL）；工作区内 UTF-8 文本的列目录、读、写，单文件上限 128 KiB | `routers/upload.py`、`services/workspace_service.py` |
| 用户 | 单机单用户：所有表的 `owner_id` 默认写死为 `local-user` | `services/database.py` |

**结论**：open-dots 是一个界面原型加一套闸门设计，不是 agent 系统。它没有 agent 循环、没有多用户、没有文件中心。可借鉴的是产品形态和闸门的数据结构，后端不可复用。

## 借鉴什么，不照搬什么

| 借鉴 | 说明 | xuanpu 现状 |
| --- | --- | --- |
| 界面骨架 | 左栏助手列表，中间对话，审批以卡片形式出现在对话流里，插件、审计、电脑各占一页 | 控制台只有标签页式的管理界面 |
| 动作信封里「给人看」的部分 | 审批卡片展示的是一句人话预览、风险分类、脱敏后的参数 | 待办只有 `scope`、`target`、`args`，没有预览，也没有把副作用分类带给审批人 |
| 动作生命周期审计 | 请求、裁决、开始、结束分开记，能看出卡在哪一步 | 连接器调用只记一条 `connector_call` |
| 执行环境的生命周期 | 暂停、重置、健康状态对用户可见 | 沙盒对调用方不可见，只有后台空闲回收 |

| 不照搬 | 原因 |
| --- | --- |
| 斜杠命令触发动作 | xuanpu 由内核的 agent 循环驱动工具调用，闸门在工具层 |
| 进程内等待审批 | xuanpu 的审批是内核挂起，持久化、可跨实例恢复，已经更强 |
| Composio 作为连接器后端 | 凭据托管在第三方服务上；企业内网系统它连不到；与 ADR 0006 的方向（自部署网关）不一致 |
| 员工自建助手作为主要玩法 | 企业场景里应用由管理员发布并受控；员工自建是否开放见「待拍板」 |
| 每个助手一台电脑 | 企业场景里文件属于人，不属于助手；应按用户划分（见决策 5） |

## xuanpu 离目标差什么

| # | 需要的能力 | 现状 | 差距 |
| --- | --- | --- | --- |
| 1 | 员工身份 | `Principal` 只有角色、租户、API key 标识（`tenancy.py`） | 没有用户、没有组、没有登录 |
| 2 | 面向员工的应用 | 业务包只有管理员视角：发布、切版本、评测 | 没有展示信息，没有「谁能用」，没有应用列表 |
| 3 | 企业系统接入 | 连接器声明在每个业务包里，连同启动命令和密钥引用 | 同一个系统被多个应用用时要各配一遍；没有「以员工本人身份访问」 |
| 4 | 个人文件 | 无文件接口；发消息只传文本（`runtime/sessions.py:349`） | 整块缺失 |
| 5 | 按人隔离的执行环境 | 沙盒按「租户 + 业务包 + 版本」划分，其下所有会话共用一个工作区 | 不同员工的会话能读到彼此的文件 |
| 6 | 员工界面 | 控制台是管理员用的静态页，填 API key 登录 | 没有员工入口；没有 JavaScript 客户端 |
| 7 | 对话类界面必需的接口 | 有事件流、事件回放 | 没有历史消息接口、不能停止生成、断线后拿不回流式增量（后两项是已知限制） |
| 8 | 按人、按应用的用量 | 用量只按租户和日期记 | 无法做成本归属和个人配额 |

## 决策（建议）

### 1. 两个入口，能力都先做成接口

- **控制台**给管理员：租户、密钥、业务包、应用上架、连接、审计、用量。
- **工作台**给员工：对话、应用中心、我的空间、待我处理。
- 所有能力先是 HTTP 接口，工作台只是第一个使用方。集成方仍然可以只用接口、自己做界面。这样平台的定位（ADR 0001）不变：工作台是平台之上的参考前端，不是平台的一部分逻辑。

面向员工的说法可以用「电脑」来比：工作台是桌面，个人空间是磁盘，企业应用是程序，连接是对外的线。这只是产品表述，平台内部仍按 ADR 0004 的四个平面组织。

### 2. 先有用户身份

- 用户来自企业自己的身份源。平台作为 OIDC 接入方，不自建账号密码体系（ADR 0003）。
- `Principal` 增加用户标识。两种凭据并存：浏览器登录会话代表「人」，API key 代表「系统」。系统代员工调用时必须声明是哪位员工，审计同时记下系统和员工。
- 组来自身份源给出的组声明，只用于应用可见范围。平台不维护组织架构。
- 会话、审计、用量都带上用户。普通成员只能看到自己的会话。

其余各项都依赖这一项，所以它排第一。

### 3. 企业应用分两层

**上层：应用**

- 一个应用是业务包的一个入口 skill。
- 展示信息（名称、图标、简介、分类、示例提问）写在业务包清单里，随版本发布。这是 `xuanpu/v1` 内新增的可选字段，已发布的包不受影响。
- 是否上架、对谁可见（全员或指定组）是治理数据，存在控制面，不随版本变。版本回滚不会改变谁能看到应用。
- 建会话时校验可见性；无权访问的应用按「不存在」处理，与跨租户访问的处理一致。

**下层：连接**

- 连接提升为租户级资源：管理员登记一次（名称、启动方式或远端地址、凭据引用、各工具的副作用分类），业务包按名字引用并声明要用哪些工具。现有的包内声明方式保留。
- 附带的好处：连接器的启动命令由管理员登记，不再由业务包作者决定。这缩小了 ADR 0005 后果里「连接器命令等同于在平台节点上运行程序」的风险面。
- 凭据分两种。**企业凭据**（服务账号，管理员配一次）已经支持。**个人授权**（员工自己授权，agent 以员工身份访问其邮箱、日历、文档）需要按用户保管令牌，并依赖远端连接器，放到第二阶段，与 ADR 0006 一起定。
- 每次连接器调用带上发起会话的用户标识，让下游系统能自己鉴权和留痕。连接器进程是多个用户共用的，所以身份必须随每次调用传递，不能放在进程环境变量里。

### 4. 个人空间：每个用户一棵持久的文件树

- 空间属于用户本人。访问者有三类：用户自己（工作台和文件接口）、用户自己会话里的 agent（经沙盒）、以后的在线编辑器。其他用户默认不可见。
- **存储**：文件内容放在目录里，`<数据目录>/spaces/<租户摘要>/<用户摘要>/`；元数据（文件标识、版本号、大小、内容摘要、最后修改者）放控制面存储。用目录是因为沙盒要挂载、脚本要直接读写。多节点部署时与会话存储一样需要共享卷，与 ADR 0005 决策 5 的约束相同。
- **用可撤销代替逐次审批**：agent 在沙盒里对挂载目录的写入是脚本直接写盘，不经过工具层的闸门。所以这里的闸门设在三处：
  1. 挂进沙盒的范围（决策 5）；
  2. 每轮对话结束时比对变更，逐个文件记审计：哪个用户的会话、哪个应用、新增 / 修改 / 删除、前后的内容摘要；
  3. 被覆盖的文件保留旧版本，被删除的进回收站，用户可以撤销。
- **配额**：每个用户的空间容量上限、单文件上限。
- **为在线编辑预留**：文件有不随改名变化的标识、递增的版本号、写入锁。agent 和编辑器同时改一个文件时靠它们判定冲突。

### 5. 空间进会话：执行环境按用户隔离，应用默认只拿到自己的目录

**隔离粒度**。ADR 0005 决策 8 规定沙盒按运行时划分，并写明重新评估的条件是「出现同一业务包内需要按会话隔离文件的场景」。个人空间就是这个场景。建议把引擎池和沙盒的键从（租户，包，版本）细化到（租户，包，版本，用户）；连接器进程仍按（租户，包，版本）共用。细化到用户而不是会话，是因为内核的脚本执行器在建引擎池时一次给定、池内会话共用（`runtime/assembler.py:273-281`），而同一个用户在同一个应用里的多个会话共用文件是合理的。

**沙盒里能看到什么**：

| 目录 | 权限 | 内容 |
| --- | --- | --- |
| 业务包目录 | 只读 | skill 与脚本 |
| 应用专属目录 | 读写 | 该用户空间里划给这个应用的目录。用户在对话里选中的文件被拷进来，产出也写在这里 |
| 整个个人空间 | 读写 | 仅当应用在清单里声明、管理员上架时确认、用户首次使用时同意 |

- 默认只给应用专属目录。用户选中的文件是拷入的副本；应用改完后由平台作为新版本写回原文件，走决策 4 的版本与审计。
- 这样限制的原因：文件内容是不可信输入，可能带着注入的指令；而业务包的 skill 是自然语言。一个应用如果既能读全部私人文件、又能出网或调用对外的连接器，就是一条数据外泄通道。
- 由此再加两条规则：会话里一旦有个人文件进入，`external` 类的连接器调用一律走审批，不受 `relaxed` 档位影响；声明了脚本出网的应用不能申请「整个个人空间」。

**文件给模型看**。图片和 PDF 可以作为消息附件直接给模型，内核已有内联附件机制；其余类型进沙盒由脚本处理。发消息的接口增加文件引用。

### 6. 在线编辑：预留接口，不自研编辑器

办公文档的在线编辑有现成方案，按 ADR 0003 不自研。通行做法是空间充当文件宿主，编辑器经 WOPI 一类的协议取文件、存文件、加锁。候选有 Collabora Online 和 ONLYOFFICE Docs；文本、Markdown、代码用浏览器端的编辑器组件。

本 ADR 不做选型。这两个候选的许可证和能力本次没有核实，届时按 ADR 0006 的做法单独评估。现在只约束一点：空间的数据模型从第一版起就带文件标识、版本号、锁（决策 4）。

### 7. 工作台是一个新包，运行时不引入 Node 服务

- 新包 `xuanpu-workbench`：前端构建成静态文件，随 Python 包分发，平台服务装了它就挂出来，与控制台的挂载方式一样。
- 它是 `xuanpu-sdk-js` 的第一个使用方，这个客户端包随之启动。
- 界面骨架借 open-dots：左栏是应用和会话，中间是对话（流式输出、审批卡片、文件卡片），另有应用中心、我的空间、待我处理三个页面。
- 审批待办补上给人看的预览和副作用分类（借 open-dots 的动作信封）。
- 平台要为它补的接口：会话历史消息、会话标题、停止生成、断线续流。后两项受内核限制，见下节。

## 否决的方案

| 方案 | 否决原因 |
| --- | --- |
| 以 open-dots 为基础改造 | 它没有 agent 循环、没有多用户，存储是 SQLite 里的 JSON 串，审批在进程内存里。能用的只有界面思路，后端与四平面的划分对不上 |
| 在现有控制台上加「应用」「文件」标签页 | 管理员后台和员工入口混在一起；控制台靠粘贴 API key 登录，不能给员工用 |
| 个人空间用对象存储，每次会话把文件取到沙盒 | 脚本需要文件系统视图；大空间每次取一遍太慢，回写同步复杂。等共享卷成为瓶颈再评估 |
| 每个会话默认挂载整个个人空间 | 任何一个应用、任何一次注入都能读走全部私人文件 |
| 沙盒细化到每个会话 | 进程和目录数量随会话数增长；同一用户同一应用的会话共用文件本来就是合理需求 |
| 自研在线编辑器 | 违反 ADR 0003 |

## 对内核的依赖

平台只依赖 taifeng 稳定层（红线 3）。下表依据 taifeng 主干与 `feat/kernel-backlog` 分支（`cc26adb`）核对。

| 需要 | 内核现状 | 处理 |
| --- | --- | --- |
| 消息带图片 | `UserMessage.attachments`、`ImageAttachmentV1`、`ImageInputPolicy` 在稳定层 | 平台接上即可；注入点在子项目设计时核实 |
| 消息带 PDF | `FileAttachmentV1`、`FileInputPolicy` 已实现，但不在稳定层 | 缺口清单新增一项，回 taifeng 立项 |
| agent 不写脚本就能读写文件 | 缺口 4、5：文件类工具工厂不在稳定层，`WorkspaceFS` 协议不存在 | 第一版 agent 经脚本访问文件；这两项的优先级随个人空间上调 |
| 停止生成 | 缺口 10：`CancelTurn` 不在稳定层 | 工作台第一版只能关闭会话 |
| 远端连接器、个人授权 | 缺口 12：`McpHttpClient` 在实验层 | 第二阶段 |
| 按用户隔离执行环境 | 执行器按引擎池给定 | 平台把池的键细化到用户即可，不需要内核改动 |
| 连接器调用带用户标识 | `McpStdioClient` 能否随调用附带元数据，未核实 | 子项目设计时核实 |

## 拆分与顺序

这不是一个项目，是七个。每个单独做设计、计划、实现。

| # | 子项目 | 内容 | 依赖 |
| --- | --- | --- | --- |
| P1 | 用户身份 | OIDC 登录、`Principal` 带用户、会话归属、审计与用量带用户 | 无 |
| P2 | 应用目录 | 清单展示字段、上架与可见范围、建会话校验、应用列表接口 | P1 |
| P3 | 个人空间 | 文件树、上传下载、版本与回收站、配额、文件操作审计 | P1 |
| P4 | 空间进会话 | 执行环境按用户隔离、应用专属目录、拷入与写回、消息附件、变更审计 | P2、P3 |
| P5 | 工作台 | `xuanpu-sdk-js`、对话、应用中心、我的空间、待我处理 | P1 起步，随 P2–P4 扩充 |
| P6 | 连接目录 | 租户级连接、身份透传；个人授权随 ADR 0006 | P1 |
| P7 | 在线编辑 | 编辑器评估与接入 | P3 |

建议顺序：P1 → P2 与 P3 并行 → P4；P5 从 P1 完成后开始并行推进；P6、P7 后置。

## 待拍板

| # | 问题 | 建议 |
| --- | --- | --- |
| 1 | 身份源先支持通用 OIDC，还是直接对接飞书、钉钉、企业微信 | 先通用 OIDC，这几家都能经它接入 |
| 2 | 管理员能否查看员工个人空间里的内容 | 默认不能，只能看审计里的元数据；确有取证需要时走单独的、自身留审计的访问方式 |
| 3 | 员工停用后空间怎么处置 | 冻结并保留一段时间，可由管理员移交给指定用户 |
| 4 | 谁来审批 | 第一版由发起会话的员工本人确认；上级或管理员审批以后再做 |
| 5 | 员工能否自建助手 | 第一轮不开放，只用管理员上架的应用 |
| 6 | 是否纳入浏览器自动化（open-dots 的电脑面板） | 第一轮不纳入；它要求对恶意网页的隔离，是单独的课题 |
| 7 | ADR 0006（采用 ContextForge）是否接受 | P6 的个人授权依赖它的结论 |

## 后果

- 引擎池的数量从「应用数」变成「活跃用户数 × 应用数」，空闲回收的参数要重新估。
- 本 ADR 接受后，ADR 0005 决策 8 被决策 5 取代。
- `xuanpu/v1` 规范新增可选字段（应用展示信息、空间权限声明、连接引用）。
- 平台开始直接面向浏览器里的员工，随之要负责登录会话、跨站请求防护、越权防护这一整面。
- 平台开始保管员工文件，备份、容量、数据驻留成为部署方必须规划的事项。
