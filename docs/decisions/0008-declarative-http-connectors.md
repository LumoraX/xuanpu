# ADR 0008：声明式 HTTP 连接器 —— 用 OpenAPI 文档把外部接口接成工具

- 状态：Accepted
- 日期：2026-09-30
- 关联：ADR 0002（修订其决策 2、3）、ADR 0003、ADR 0004、ADR 0006

## 背景

ADR 0002 规定业务方的自定义能力只有两种形态：MCP server 与沙盒内脚本。

企业接入时面对的是几十到几百个已有的内部接口（ERP、CRM、工单、审批流……），它们几乎都有 OpenAPI 文档，却没有 MCP server。按 ADR 0002 只有两条路：

- 每个系统包一层 MCP server：要写代码、要部署、要运维，接入成本与接口数量成正比；
- 在沙盒脚本里用 `curl` 调：凭据得进沙盒，调用不过连接器闸门，审计里只有一条脚本执行记录。

两条路都让「配置 key 与 api 就能接入」落空。

## 决策

1. **增加第三种扩展形态：声明式 HTTP 连接器。** 业务包里放一份 OpenAPI 3.x 文档，在清单里声明 `transport: http` 的连接器；文档里的每个 operation 是一个工具，工具名 `api__<连接器名>__<operationId>`。
2. **它不违背 ADR 0002 的第 1 条**（平台进程内不加载业务方代码）：OpenAPI 文档是数据，不是代码。平台只按文档拼请求，不执行业务包里的任何东西。ADR 0002 决策 2、3 里的「两种」自本 ADR 起读作「三种」。
3. **与 MCP 连接器共用同一个闸门**（ADR 0004）：白名单 → 副作用分类 → 审批 → 调用 → 审计，一条路径，两种传输。副作用分类逐 operation 声明优先；未声明时 GET / HEAD 算 `read`，其余用连接器的默认值（`external`）。
4. **出口的约束写死在实现里，不交给清单配置**：
   - 目标主机由清单的 `baseUrl`（或文档的 `servers`）定死，模型只能填 operation 声明过的参数，路径参数整体转义；
   - 不跟随重定向，不读进程环境里的代理配置；
   - 凭据只写密钥名，发请求时才从保管库取出，不进返回给模型的文本、不进异常文案、不进审计；
   - 响应体上限 1 MiB。
5. **限流、熔断、重试、双向 TLS 不在平台里做**，交给企业已有的 API 网关（ADR 0003）。

## 否决的方案

- **维持 ADR 0002，要求业务方自己包 MCP server**：接入成本过高，见背景。
- **平台内置一个「OpenAPI → MCP」转换进程**：多一个进程、多一跳，换来的只是形式上符合 ADR 0002；闸门、凭据、审计该做的事一样不少。
- **开放通用的 `http_request` 工具，让模型自己拼 URL**：出口范围无法由清单定死，白名单与副作用分类无从谈起。

## 后果

- 连接器闸门从「MCP 专用」变成「传输无关」；审计的 `connector_call` 记录多一个 `transport` 字段。
- 业务包规范多了 `transport`、`openapi`、`baseUrl`、`auth` 等字段（`xuanpu-spec` 向后兼容：不写 `transport` 仍是 stdio）。
- **目标主机由租户管理员声明，平台不限制可声明的地址范围**（包括内网地址）。平台节点能访问到的地方，租户管理员就能让平台去访问。在增加平台级的出口白名单之前，出网范围靠部署的网络策略约束，这与 ADR 0005「只适合承载受信任租户」是同一档信任假设。
- 凭据方式第一版只有 `bearer`、`header`、`query`、`basic`；需要换取令牌的 OAuth2 流程（client credentials 等）未实现。
- `transport: http` 这个取值已被本 ADR 占用。ADR 0006 设想的「以 HTTP 传输接远端 MCP server」落地时要用别的取值，届时在该 ADR 的后续决策里定。
