# ADR 0001：定位与分层 —— 业务方只管业务，平台是 taifeng 之上的发行版

- 状态：Accepted
- 日期：2026-09-29
- 关联：taifeng ADR 0017（内核定位与立项四规则）

## 背景

taifeng 按其 ADR 0017 定位为 LLM OS 的内核：只提供调度、上下文、取消、恢复、通信等机制，本身不是产品，也不内置任何具体后端。

企业要把 agent 用到生产，内核之外还要一整圈能力：会话放置与执行存活、挂起后的持久化与恢复、沙盒、可多实例共享的存储、模型路由、计量审计、多租户隔离。没有平台时，每个宿主都得各自重造这一圈、各自踩一遍坑（执行存活误判、事件流过早截断之类）。

目标形态类比数据库和操作系统：使用者只设计自己的表结构和应用，执行计划、事务、进程调度由系统负责。

## 决策

1. **业务方只提交业务包**：skills、连接器声明、策略、评测用例。业务包带版本号，可发布、灰度、回滚。
2. **分三层**：
   - **taifeng**：内核，零租户概念；
   - **taifeng-sandbox、taifeng-stores**：实现 taifeng 协议的适配包，不认识租户、不认识业务包，任何 taifeng 宿主都能用；
   - **xuanpu**：平台，负责租户、业务包、运行时、控制面，以及对业务方的全部接口。
3. **判据**：实现 taifeng 协议且不需要平台概念的 → 放适配包；需要租户或业务包概念的 → 放 xuanpu；已有成熟开源方案的 → 采用，不自研（ADR 0003）。
4. **本仓是 monorepo**：每个组件是 `packages/` 下的独立包，各自版本、各自发布。等团队分工或发版节奏分开，再拆成独立仓库。
5. **平台发现内核缺对接口时回 taifeng 立项**，不 monkeypatch、不 fork。

## 后果

- 平台对业务方隐藏几乎全部内核参数，只暴露少数有业务含义的档位（质量 / 延迟、预算、审批强度），在内部换算成内核参数。
- LLM 的成本、延迟、质量无法像 SQL 那样确定，所以平台必须给业务方业务层面的反馈工具：发布前评测、按场景统计成本和效果、轨迹查看。否则业务方终究会被迫去看底层。
