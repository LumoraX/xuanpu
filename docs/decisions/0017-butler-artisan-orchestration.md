# ADR 0017：管家—匠人编排、执行追踪与极简入口

状态：R5 候选实现（2026-11-14，分支 `feat/r5-butler-artisan`；用户提出方向并要求按 R5 计划实施），生产验收尚未完成。修订 0012 决策 1 的「助理只做分流」；不推翻 0002、0004、0014。

## 背景

员工入口现在是 `POST /v1/assistant/route`：模型在目录里选一个业务包入口，自己不执行、不拆分、不验收。页面除对话外还有 8 个侧栏模块、15 张功能卡、5 个浮层。用户于 2026-11-14 明确三点：

1. 界面尽量简单：一个对话输入、一块概览、若干消息与提示；工具与功能全部在后端。
2. 员工只对管家说话；管家能自己办的自己办，办不了的分析后交给匠人，匠人可以编组完成（参照 luwu 的主人—管家—匠人模型）。
3. 需要 deepseek-harness 的核心能力：编排 agent 过程、trace、span。

## 决策

1. **员工只面对管家。** 每位员工一个管家会话，替代一次性分流。管家是平台内置 agent，不属于任何业务包。
2. **匠人就是已发布、且该员工有资格使用的业务包入口。** 不另建匠人注册表、不另建执行内核。派工复用 R2 持久任务与既有会话，每个匠人保留自己的沙盒、连接器凭据、闸门与审计。
3. **管家不直接调用别的业务包的工具。** 跨包协作只经「派工」这一个受控动作，隔离边界（0002、0013）不变。
4. **编排用声明式计划（单人、并行、接力、会诊），不执行模型编写的脚本。** deepseek-harness 的 workflow 脚本范式不采用：模型写的代码进不了平台进程，放沙盒里又多一条难审计的路径。
5. **一次请求一条 trace，每个执行单元一个 span。** span 事实由平台按租户持久化，不含正文、工具参数与凭据；OTel 导出可选。内核只提供执行身份与事实事件，租户概念不下沉（红线 2）。
6. **只依赖 taifeng 稳定层（红线 3）。** 执行身份字段与 `execution_updated` 事件须先进入稳定层；平台不 import `taifeng.experimental`。
7. **写入仍须本人确认。** 管家与匠人提出的写入一律是待确认动作；管家代答匠人的提问只限员工明确说过的事实，并注明出处。
8. **入口收敛为：概览 + 对话 + 输入 + 提示。** 「功能」页保留为「更多」入口（AGENTS.md 企业核心定位第 2 条不变），模型不可用时仍可手动操作。
9. **管家不自行上线匠人或技能。** 可以提出草稿，上线走既有发布与能力交付治理（R4）。

## 不采用

- 把 luwu 代码并入：其自评多数模块完成度 30–65%，且自带一套执行内核、消息总线与容器管理，与 0003 冲突。只取其角色模型。
- 引入 Temporal、LangGraph 等编排引擎：派工是有限状态、短事务加既有持久任务，理由同 0016。
- 让管家在同一引擎里加载多个业务包：破坏包间凭据隔离。

## 后果

- 一次请求可能消耗多个匠人的 token，必须有每条 trace 的预算与匠人数上限。
- 管家引入一层模型判断；直接输入与「更多」页必须在模型停用时可用。
- R4-B 的到人能力决策落地后，派工必须改用它；在此之前按现有租户生效版本解析，不得绕过旧治理。
- 需要先升级内核（平台锁定 2026.10.1.11，内核已 2026.11.14.0）。
