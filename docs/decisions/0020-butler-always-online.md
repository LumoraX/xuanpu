# ADR 0020：管家常在线 —— 回执与一轮解耦、时限与预算随任务伸缩

- 状态：Accepted（R6 实施中）
- 日期：2026-11-18
- 关联：修订 ADR 0017 决策 1 的实现方式（「管家立即答复」由同步一轮改为短等待回执）；不推翻 0017 其余决策
- 实现：[管家](../architecture/butler.md)、[R6 计划](../superpowers/plans/2026-11-18-r6-butler-always-online.md)

## 背景

用户于 2026-11-18 明确：管家像人一样常在线。员工交代一件事，管家自己办或交给别人；员工接着交代下一件，管家同样处理；前一件办完时管家主动回报结果，或告诉员工该做什么。一件事可能几秒办完，也可能持续几天；时限默认 5 分钟，管家可以延长，也可以拆成任务；token 预算随任务需要提高，不是固定 40 万。

R5 的实现与此不符：

- 管家的一轮在 `POST /v1/assistant/messages` 请求里同步跑完，固定 90 秒（代码常量），超时 503；极简入口发送后禁用输入框直到回复，员工在这期间不能交代下一件事。
- 每次请求的 token（40 万）、管家轮数（8）、匠人数（4）是固定配置，管家无法随任务调整。
- 派工、唤醒、交付与转问已经是异步持久的（R5-C2），不需要改。

## 决策

1. **回执与一轮解耦。** 员工说一句话，请求只等一个短窗口（`butler.reply_window_seconds`，默认 20 秒）。窗口内办完照旧返回完整回执；没办完立即返回 `state: "running"` 的回执（含 `trace_id`），这一轮在平台里继续跑，结束后回复写入主对话。员工随时可以说下一句，每句各自一轮、互不阻塞；同一 `request_id` 重试返回进行中或最终回执，不重复跑。
2. **一轮的时限是动态的。** 默认 `butler.turn_seconds`（300 秒）；管家可用工具 `extend_turn` 说明理由后延长，至多到 `butler.max_turn_seconds`（默认 1 天，上限 7 天）。到时限一轮正常收尾：已派出的工作继续，主对话写明「这一轮已到时限停下」，不再报 503。更长的工作应拆成派工、编组或执行安排，由唤醒驱动，而不是让一轮无限延长。
3. **每次请求的预算随任务伸缩。** 现有 `max_tokens_per_trace`、`max_butler_turns_per_trace`、`max_artisans_per_trace` 改为起始预算；管家可用工具 `raise_budget` 说明理由后提高，至多到对应的上限配置（`*_ceiling`）。租户每日 token 配额（`quota.max_daily_tokens`）仍是硬上限，管家不能提高。每次延长与提高都记审计与执行追踪，并在回复里告诉员工。
4. **管家常在线由持久记录保证。** 进行中的一轮登记为持久记录；进程中途退出后，未结束的一轮由唤醒循环按同一 `request_id` 重跑一次（派工按派工请求标识幂等，不会重复派出），重跑仍失败则在主对话写明并保留原话。
5. **前一件事的结果由管家主动回报。** 沿用 R5 唤醒：匠人结束、提问、需要审批、会诊需裁决时，管家把结果或该员工做的事写进主对话并发通知；员工不需要盯着某一次请求。

## 不采用

- **把一轮直接放宽成几天的同步请求**：HTTP 连接、反向代理与浏览器都撑不住，员工也不能同时交代别的事。
- **取消一切上限**：模型可能失控循环；保留可延长的时限与可提高的预算，并以租户每日配额兜底，延长与提高都留痕。
- **一轮中途在另一个进程里精确续跑**：依赖内核线程的中途恢复，复杂度高；本版本按同一请求标识安全重跑，以后需要再立项。

## 影响

- HTTP：`POST /v1/assistant/messages` 增加 `state`（`done` / `running`）；客户端不应再假定回执里一定有最终回复。
- 前端：极简入口发送后不禁用输入；进行中的请求由进展卡跟随，结束后回复出现在对话里。
- 配置：`butler` 增加 `reply_window_seconds`、`turn_seconds`、`max_turn_seconds` 与三项 `*_ceiling`；旧的三项预算含义改为起始值，默认值不变。
