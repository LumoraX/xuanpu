# ADR 0005：第一版的取舍 —— 连接器先内置、密钥先自管、会话靠租约单写

- 状态：Accepted
- 日期：2026-09-30
- 关联：ADR 0002、ADR 0003、ADR 0004；taifeng-stores ADR 0002

## 背景

ADR 0002 把 MCP 网关定为业务扩展的唯一通道，ADR 0003 要求密钥管理、模型网关等采用成熟组件。第一版要先让「发布业务包 → 建会话 → 对话 → 过闸 → 审计」这条主线跑通，其中有几处既有决策暂时做不到位，需要说清楚现在怎么做、为什么、什么时候改。

## 决策

1. **连接器先由平台服务直接承载，不单独做网关。** `xuanpu-server` 启动业务包声明的 MCP server 进程，把它的工具包装后交给内核。白名单、审批、凭据注入、调用审计这四件闸门该做的事都做了，只是和运行时在同一个进程里。独立的 `xuanpu-mcp-gateway` 仍按 ADR 0003 先评估现成方案。
   - 现成方案为什么暂时不用：评估尚未做；而闸门逻辑依赖业务包清单里的副作用分类与租户审批强度，这两样是平台自己的概念，无论最后用哪个网关都要在平台侧实现。
2. **密钥保管库先提供一个自管实现，接缝留给外部保管库。** `SecretVault` 是协议，`EncryptedVault` 是默认实现：AES-256-GCM 加密后存进控制面存储，附加认证数据是「租户 + 密钥名」，主密钥由部署方经配置注入并支持轮换。接 Vault 或云 KMS 时实现同一个协议即可。
   - 现成方案为什么暂时不用：要求每个部署先有一套 Vault 才能试用平台，门槛过高；加密本身用的是成熟的密码学库，没有自造算法。
3. **模型访问只认兼容 OpenAI Chat 接口的网关。** 各家模型的接入、限流、回退交给网关（ADR 0003）；平台只做档位到模型名的换算，并把请求里的模型名钉成平台选定的那个。
4. **会话靠带期限的租约保证单写者。** 实例处理会话前先取得租约并定期续期；优雅退出时放弃租约；崩溃后租约到期，别的实例才能接手，并用线程标识从会话存储续接。
5. **第一版的会话主存是节点本地文件。** 这是 taifeng 目前的限制（`EnginePool.create` 固定用本机 JSONL，日志协议未公开）。跨节点接手要求各节点共用数据目录；线程目录与消息另外镜像进 Postgres 供查询与审计。
6. **一个引擎一条全量事件订阅。** 审计、用量入账、各轮对话的事件流都从这一条订阅分发，避免「先提交、后订阅」之间丢事件。
7. **控制面存储有内存与 Postgres 两个实现，对同一套契约测试负责。** 内存实现只用于测试与单机试用。
8. **沙盒按运行时（租户 + 业务包 + 版本）划分，不按会话。** 同一个运行时下的会话共用工作区。本机隔离用受限读策略：沙盒里的进程只能读业务包目录、只能写工作区，平台数据目录里其他租户的文件不可见。

## 后果

- 连接器进程与平台服务同机运行，连接器本身不在沙盒里（内核的 MCP 客户端不经 `CommandExecutor` 启动进程）。业务包由租户管理员发布，连接器命令等同于租户管理员在平台节点上能运行的程序——**在连接器进沙盒之前，平台只适合承载受信任租户的业务包**。
- 当天用量在一轮对话结束时入账，所以配额拦的是「下一轮」，当天实际用量可能超出上限一轮对话的量。
- 进行中的对话不能单独取消，只能关闭会话（内核的 `CancelTurn` 不在稳定层）。
- 调用方断开后重连，拿不到流式增量，只能经回放接口取已审计的事件与回复全文。
- 同一租户、同一业务包版本下的会话之间没有文件隔离。

| 5 | taifeng 公开会话日志协议，taifeng-stores 提供共享日志后端 |
| 8 | 出现同一业务包内需要按会话隔离文件的场景 |
