# ADR 0014：玄圃是企业核心，提醒持久调度与消息渠道分离

- 状态：Accepted（用户于2026-10-05确认核心定位并授权实施）
- 日期：2026-10-05
- Supersedes #0009 决策1的“只做四件事”、决策3的“所有企业数据一律外部权威”；保留成熟组件、专业工具与可替换进程外业务扩展原则。
- Supersedes #0012 决策5的“所有提醒到点跑模型对话”和“人不在线时必须经飞书提醒”。

## 决策

玄圃拥有企业身份、权限、业务协调、状态与审计。飞书、企业微信、ERP、邮箱、财务等是可替换的外部能力。数据来源可按领域配置并双向演进：阶段性由飞书同步离职，不排除以后玄圃向飞书发布离职事件。核心地位不要求自研在线文档或专业财务软件；其内容可留在专业系统，业务引用、权限和工作流边界必须清楚。

提醒、通知、待办等跨业务基础能力不以外部供应商是否支持同名功能为前提。纯提醒到点只写确定性的通知，无需模型在线或再次计费；未来“到点执行某项工作”独立进入有权限、预算和审批的运行时，不能借提醒接口偷偷执行代码。

后台采用现有Postgres控制面里的持久提醒和投递状态。每秒有限扫描，短事务锁定租户、员工与提醒，重新检查后原子创建站内通知/渠道outbox、推进下次计划；唯一约束消除重复。用户行锁序列化其通知ID分配与提交，保证按游标补读不会漏掉晚提交记录。停用员工的同一事务取消其提醒；进程内监听只能辅助，不能成为正确性依据。

网页使用SSE接收单向变化，写操作走HTTP；SSE是长连接，WSS是加密双向WebSocket，两者都不是定时机制。浏览器关掉仍会产生持久通知，回来可补读。外部飞书通知通过HTTP适配器和有租约的outbox，失败不影响站内记录；界面展示渠道真实状态。未实现浏览器关闭后的系统推送，不能承诺这类推送。

## 选型取舍

| 方案 | 结论 |
| --- | --- |
| 外部平台定时器作为事实来源 | 不采用：业务可用性和迁移被供应商限制 |
| Celery/Redis或Temporal承载首版纯提醒 | 暂不引入：增加第二套持久队列与部署面；通知与业务状态仍需解决同事务提交 |
| APScheduler持久job | 暂不引入：通用job记录不能替代提醒+站内通知+outbox的领域事务 |
| 现有Postgres事务+asyncio唤醒 | 采用：到期动作是可重试的短状态转换；不自研通用工作流引擎 |
| 网页WSS | 暂不需要双向高频流；现有HTTP+SSE足够，未来按交互需求引入 |

## 范围与边界

首版支持一次、每天、每周。UTC时间戳加IANA时区，重复保持当地钟表时间；夏令时缺失时刻跳过，重复时刻只发一次。宕机一次性补发一次，重复任务合并错过的提醒，直接推进下一个未来时间。

外部通知可能重复或最终失败；每次领取换claim_token、稳定供应商幂等键、请求时限短于租约、最多5次并退避，且自首次尝试起限制一小时；超窗且送达未知时明确失败，不能无限期重发。首次领取后确认租户暂停且尚未外发时归还尝试计数和起点，已有发送历史不重置。不能承诺已经发出的请求在员工停用时被撤回。渠道配置表示已有目标和凭据，不代表供应商实际权限已验证，后者由发送结果确认。

新领域后续分期：企业身份与权威来源配置；事项/审批/文档版本签收；业务系统与财务适配。它们未因本ADR自动完成，仍需各自数据模型、规则和验收。

## 依据

- [PostgreSQL SELECT](https://www.postgresql.org/docs/current/sql-select.html)：行锁与队列竞争。
- [WHATWG Server-sent events](https://html.spec.whatwg.org/multipage/server-sent-events.html)：事件、游标与重连。
- [飞书发送消息](https://open.feishu.cn/document/server-docs/im-v1/message/create)、[官方SDK请求体](https://github.com/larksuite/oapi-sdk-python/blob/v2_main/lark_oapi/api/im/v1/model/create_message_request_body.py)：消息HTTP入口与uuid字段。

到期检查和外部投递使用两个独立且可取消的后台循环；外部请求变慢不会阻塞下一轮站内到期检查。关闭平台时同时取消并等待两个循环和所有在途发送，之后再关闭连接池。每轮数据库扫描仍受当前数据库响应时间影响，不承诺硬实时。
