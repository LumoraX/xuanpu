# ADR 0023：执行旁白与小院 —— 匠人动手前说的那句话进 trace

状态：Accepted（2026-11-19，用户认可原型并要求实施；R7）。修订 [ADR 0017](0017-butler-artisan-orchestration.md) 决策 5 的「span 不含正文」一处，其余不变。

## 背景

R5 的进展卡用执行树与瀑布展示一次请求，用户认为「像 DAG 排布，不友好」。R7 把进展卡换成「小院」：管家与匠人是可定制的角色，按执行事实走动、交代、干活；下方「经过」像群聊一样让每个角色用自己的话讲每一步。要讲得出「为什么这么做」，只靠 span 的工具名不够。

## 决策

1. **工具 span 可带一句旁白（`say`）。** 内容是同一执行在调用这个工具之前对员工说出口的话（内核 `assistant_text` 增量），清洗后最长 160 字（放不下时按整句保留结尾）；同一批并行工具只挂第一个。一轮结束时未用掉的话丢弃（那是回复，已在对话里）。
2. **只放说出口的话。** 推理（`assistant_reasoning`）、工具参数与输出、凭据一律不进 trace，与 0017 决策 5 相同。旁白与 span 其余字段一样只给本人、同样保留期、不经 OTel 导出。
3. **派工投递附带说话约定。** 交给匠人的说明末尾追加一行「（每次动手前，先用一句话告诉员工你要做什么。）」；只在投递时追加，派工记录与幂等指纹不变。匠人不说话时，前端按工具名与家具拼模板句，并标明句子是拼的。
4. **派工细节只读接口。** `GET /v1/assistant/dispatches/{id}` 给本人看任务说明、承载方式、最近一次验收、结果摘录（600 字）与问答（含代答出处）；不含匠人内部过程。
5. **小院在前端拼，不改业务包规范。** 工具归到哪件家具由前端按名称归类；匠人默认形象由包名稳定推导；角色设置存本设备。

## 不采用

- 开放工具原始参数与输出：最完整，但长、难读，且会放出连接器规则刻意挡住的数据。
- 只用模板句、不存任何文字：不改存储，但永远说不出「为什么」。
- 让业务包声明工具的家具与角色形象：要改 `xuanpu-spec`（对外契约），等有真实需求再议。

## 后果

- trace 存储多一个可空字段（JSONB 里，无迁移）；旧记录没有旁白，前端退回模板句。
- 匠人说的话质量取决于模型；约定只是提示，不强制。
- 角色设置不跨设备；跨设备与发布方声明形象留待后续。
