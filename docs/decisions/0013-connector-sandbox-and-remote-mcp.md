# ADR 0013：连接器进沙盒、远端 MCP 直连 —— stdio 连接器在单独的连接器沙盒里运行，`transport: remote` 不等网关

- 状态：Accepted
- 日期：2026-10-02
- 关联：ADR 0002（落实其后果第 2 条「MCP server 若由平台代为运行也要进沙盒」；修订其决策 2 里「经 xuanpu MCP 网关接入」）、ADR 0005（补充决策 1；取代后果第 1 条）、ADR 0006（远端 MCP 先直连，网关方案继续暂缓）、ADR 0008（其后果最后一条留待定的传输取值定为 `remote`）、ADR 0011 决策 1；taifeng ADR 0110（`McpHttpClient` 进稳定层）、ADR 0112（MCP stdio server 经 `CommandExecutor` 启动）；taifeng-sandbox ADR 0005（本机后端收紧）
- 详细设计：[P0 底座升级](../superpowers/specs/2026-10-02-p0-foundation-upgrade-design.md) 3.6 节

## 背景

第一版（ADR 0005）里，业务包声明的 MCP server 由平台服务在平台节点上直接起子进程：进程只拿到声明过的环境变量，但文件、网络、进程都不受限。租户管理员发布业务包，等于能在平台节点上运行任意程序，所以平台「只适合承载受信任租户的业务包」。原因在内核：`McpStdioClient.spawn` 不经 `CommandExecutor`（缺口清单第 7 项）。

部署在别处的 MCP server 则完全接不进来：内核的 `McpHttpClient` 在实验层（缺口第 12 项），ADR 0006 设想经 MCP 网关（ContextForge）接入，又因为企业版的拍板而暂缓。

taifeng 2026.10.1.10 把这两处都补上了（内核 ADR 0112、0110）。P0（ADR 0011 决策 1）据此把连接器进程挪进沙盒，并把远端 MCP 作为连接器的一种传输。

实现过程中的安全审查实测出一处新的缺口：Linux 本机后端的启动器（沙盒外的 `bwrap` 进程）拿到连接器的整份环境，环境里放一个 `LD_PRELOAD`，代码就在沙盒建好之前以平台用户的身份在沙盒外执行。macOS 本机后端则查明了一处 seatbelt 管不到的读取（见决策 3）。

## 决策

1. **stdio 连接器在每个运行时单独的连接器沙盒里运行，与脚本的沙盒分开。**
   - 一个运行时（租户 + 业务包 + 版本）一个连接器沙盒，清单里没有 stdio 连接器就不开。连接器进程经内核 `McpStdioClient.spawn(..., executor=)` 起在里面；沙盒不可用时对话以 `503 runtime_unavailable` 失败，**不退回到在平台节点上直接起**。
   - 只读业务包目录（与宿主机同路径，工作目录仍是业务包根目录），只写这个运行时的连接器工作目录 `<data_dir>/connectors/<租户目录>/<名>/<版本>/`，**允许出网**。
   - 环境只有最小的 `PATH`、`LANG`，`HOME`、`TMPDIR`、`WORKSPACE` 指向连接器工作目录，加上清单声明的变量与密钥。
   - 两种后端，由部署配置选：
     - 本机（macOS seatbelt、Linux bubblewrap）：受限读策略，系统运行时目录之外默认读不到；连接器自己的解释器与依赖装在别处时，由部署方在 `sandbox.connector_readable_roots` 里放开（不能是根目录，不能与数据目录、本机对象存储目录相同或互为上下级）。本机没有能整个销毁的边界，平台记下经它起过的进程，关运行时时逐个强杀——内核在启动被取消时不关已经起来的进程（缺口第 24 项）。
     - 容器（docker）：每个运行时另起一个连接器容器，镜像是 `sandbox.connector_image`（缺省同脚本镜像），里面要装好连接器需要的运行时；加固方式与脚本容器相同，只是不断网；带 `xuanpu.role=connectors` 标签。
   - **为什么不与脚本共用沙盒**：出网需求不同。脚本由模型驱动，默认断网，业务包要声明 `policy.sandbox.network` 才放开；连接器本来就是去连外部系统的，必须出网。共用一个沙盒，要么脚本跟着出网，要么连接器连不出去。分开还有一个好处：连接器拿着密钥、会在 `HOME` 里留下凭据缓存之类的东西，脚本沙盒读不到连接器的工作目录。

2. **连接器的 `env` 拒绝动态链接器变量（`LD_*`、`DYLD_*`，不分大小写）。**
   - 规范校验时拒绝（`xuanpu-spec` 2026.10.2.5 起），组装运行时再拦一次（挡住更早发布的包与绕过规范构造的清单），报 `package_invalid`。
   - 理由：本机后端的启动器在沙盒之外，它拿到的环境会被动态链接器解释，`LD_PRELOAD` 之类的变量等于在沙盒外执行代码（bubblewrap 上已复现）。
   - 根治在 taifeng-sandbox ADR 0005 决策 1：bwrap 启动器只用固定的空环境、工作目录固定为 `/`，目标进程的环境经封口的 memfd 以 `--setenv` 交给 bwrap，只在沙盒里生效。seatbelt 的启动器 `sandbox-exec` 是受 SIP 保护的平台二进制，dyld 忽略并删掉其中的 `DYLD_*`（同一 ADR 决策 4）。平台这道拒绝留作纵深防御：黑名单列不全（根治不靠它），但连接器正当的用途里用不到这类变量，拒绝没有代价。

3. **隔离强度按后端区分，生产用 Linux，推荐 docker；macOS 本机后端只用于开发试用。**

   | 后端 | 连接器进程碰得到什么 |
   | --- | --- |
   | Linux bubblewrap | 文件：系统目录（`/usr`、`/bin`、`/sbin`、`/lib*`、`/etc`、`/opt`）、业务包目录、放开的目录只读，连接器工作目录可写；独立的 pid、ipc、用户、挂载命名空间，看不到平台进程。剩余：不过滤 Unix 套接字（挂进沙盒的目录里的套接字连得上，出网时宿主的抽象 Unix 套接字也连得上），没有 seccomp、Landlock；共享宿主网络命名空间，平台节点能到的地方它都能到 |
   | macOS seatbelt | 文件与出网受限，本机 Unix 套接字除 DNS 外一律不通。剩余：**内核对 `KERN_PROCARGS2` 不走沙盒检查，沙盒里能读到同一用户下其他进程的完整参数与初始环境——包括平台进程环境里的主密钥、数据库连接串、网关凭据**；出网时能连本机任意 TCP 端口；依赖 SIP 开着 |
   | docker | 去掉全部 capability、禁止提权、只读根文件系统、限制内存 / CPU / 进程数；出网走 Docker 网络，能到宿主网关、内网与云元数据地址 |

   seatbelt 那一处没有配置能拦住（taifeng-sandbox ADR 0005 决策 2 实测），所以 macOS 本机后端不能承载不受信任的业务包。

4. **同一业务包内的连接器互信。** 一个运行时的全部 stdio 连接器共用一个连接器沙盒、一个工作目录；docker 与 macOS 下它们能看到彼此的进程环境（含密钥），bubblewrap 下每个进程各在自己的 pid 命名空间里、看不到彼此的进程，但工作目录是共用的。不再按连接器拆：同一个包由同一个租户管理员发布，连接器之间本来就在同一个信任域里；按连接器拆，容器后端每个运行时的容器数要随连接器数增长。

5. **远端 MCP 是连接器的第三种传输 `transport: remote`，平台直连，不等网关。**
   - 清单字段：`url`（必填，带主机名的 `https://`；`http://` 只宜试用）、`auth`、`timeoutSeconds`、`effect`、`tools`。工具名前缀与 stdio 一样是 `mcp__`。规范仍是 `xuanpu/v1`（新增可选取值，向后兼容）；`transport: http` 已被 ADR 0008 占用，所以取 `remote`。
   - 运行时用内核稳定层的 `McpHttpClient`（MCP Streamable HTTP）。远端 MCP 不进沙盒：它本来就是一次网络调用，请求从平台节点发出。与另外两种传输共用同一个闸门：白名单、副作用分类、审批、过闸记录都一样。
   - **为什么不等网关**：ADR 0006 设想的「经 ContextForge 接远端 server」，多出来的是多租户的 server 注册与凭据管理；白名单、按副作用分类审批、调用审计无论如何都在平台的闸门里做。远端 server 直连就够用，ADR 0006 继续暂缓，它的两条前置条件（`McpHttpClient` 进稳定层、本机连接器进沙盒）现已满足，将来要接网关时把网关当作一个远端 server 接即可。

6. **远端 MCP 的凭据走传输层，每次请求现取。**
   - 不经 `McpHttpClient` 的 `headers` 注入——那会让明文在客户端对象里一直待到运行时回收。平台给客户端一个自定义的 httpx 传输，每个请求发出之前从保管库取出密钥加到请求头上；客户端与传输对象里不留明文，密钥轮换即时生效。组装时先核对密钥已配置（缺了对话起不来，与另外两种连接器一致），取到的值不保留。
   - **只给发往清单 `url` 同源（协议、主机、端口）的请求加凭据，别的请求一律拒绝发出。** 内核客户端只向这一个端点发请求、不跟随重定向；这道检查挡住以后的改动意外把带凭据的请求引到别处。传输不读环境里的代理与证书配置（与 HTTP 连接器一致），出口走哪里由部署决定。
   - **只开放请求头类凭据**：`bearer` 与 `header`。`query` 会把明文写进 URL（URL 常被日志、异常文本带出去）；`basic` 暂不开放，需要时可以向后兼容地加。`auth.header` 不能是 `Authorization`，也不能是协议、连接管理或 MCP 传输自己用的头（`Host`、`Content-Type`、`Mcp-Session-Id`、`MCP-Protocol-Version` 等），密钥取值不能含换行与空字符——这些会改写报文（HTTP 连接器同样适用）。
   - **不开推送流**（`listen_notifications=False`）。运行时的工具在组装时定下，闸门与权限策略是按那时的工具生成的，之后不随 `tools/list_changed` 增减，推送流收到的通知用不上；不开就省掉每个运行时一条常驻连接与断线重连。
   - **成功的结果也按值脱敏。** 远端每次请求都拿到凭据，它回的任何文本都可能把凭据带回来：交给模型与审计的文本、日志里的排障线索，都拿现取的明文按值替换（先脱敏再截断）。代价是每次调用多读一次保管库；脱敏时密钥已取不到，整段换成一句说明，不冒险原样写出。

7. **连接器的排障线索按值脱敏后才进日志。** stdio 连接器启动或调用失败时，平台日志里记脱敏后的异常文本、退出码与 stderr 末尾约 2 KiB（各段按 repr 写出，外部输出里的换行伪造不出新的日志行）；返回给调用方的只有异常类型。内核 MCP 客户端会把外部输出原样写进日志（缺口第 25、26 项），平台给内核 MCP 的几个 logger 挂过滤器，参数里的字符串与字节串只记长度、附带的异常只记类型。

## 否决的方案

| 方案 | 原因 |
| --- | --- |
| stdio 连接器与脚本共用一个沙盒 | 出网需求不同（见决策 1）；连接器的凭据缓存会落在脚本读得到的地方 |
| 按连接器各开一个沙盒 | 同一个包的连接器本来互信；容器后端的容器数随连接器数增长 |
| 本机后端也给连接器全盘只读 | 平台的数据目录、配置文件、别的租户的业务包都在盘上 |
| 不拒绝 `LD_*`、只靠 taifeng-sandbox 的根治 | 根治之前发布的包、关掉 SIP 的 macOS 都兜不住；拒绝没有代价 |
| 远端 MCP 等 MCP 网关（ADR 0006）落地后再接 | 网关的增量（server 注册、凭据管理）现在用不上，闸门在平台侧无论如何都要做 |
| 远端 MCP 的凭据放进 `McpHttpClient(headers=…)` | 明文在客户端对象里一直待到运行时回收，违背「明文只在出口那一刻取出」 |
| 远端 MCP 开推送流、按 `tools/list_changed` 增减工具 | 闸门与权限策略在组装时生成；运行中冒出的新工具没有副作用分类与审批规则 |
| 远端 MCP 支持 `query` 凭据 | 明文进 URL，URL 常被日志与异常文本带出 |
| 远端 MCP 进连接器沙盒 | 它是一次网络调用，沙盒挡不住它要去的地方；请求方仍是平台 |

## 后果

- ADR 0005 后果第 1 条（连接器不在沙盒里、只适合受信任租户）由决策 1、3 取代：信任边界改为按沙盒后端区分，部署方要遵守的安全须知见[运维手册](../guides/operations.md#安全须知)。ADR 0005 决策 1 的其余部分（闸门在平台服务里、不单独做网关）不变。
- ADR 0002 决策 2 里「MCP server 经 xuanpu MCP 网关接入」读作「由平台在连接器沙盒里代为运行，或部署在别处、经 `transport: remote` 直连」；其后果第 2 条（平台代为运行的 MCP server 要进沙盒）已落实。
- ADR 0006 维持 Proposed（暂缓）；其「前置条件」两条已满足，「后果」里设想的 `transport: http` 改为本 ADR 的 `transport: remote`。
- 缺口清单第 7、12 项删除；新增第 18、24、25、26–29 项（内核 MCP 客户端的读取上限、启动被取消时的进程泄漏、日志写外部内容、HTTP 客户端的异常与会话过期处理）。
- 已知不一致：stdio 连接器**成功**的结果不按值脱敏（失败的、日志里的都脱），远端 MCP 的成功结果脱敏。以后统一。
- docker 后端下每个有 stdio 连接器的运行时最多两个容器，`memory_mb`、`cpus` 与进程数上限各算一份；本机后端不限资源。
- 连接器工作目录在节点本地，不备份、不跨实例共享、不自动清理；docker 下里面的文件可能属 root。
- 「允许出网」意味着平台节点能到的地方连接器都能到；远端 MCP 的 `url` 平台也不限目标（含内网与元数据地址），回包交给模型，等于一次能读到结果的 SSRF。出网范围靠部署的网络策略约束（与 ADR 0008 对 HTTP 连接器的处理相同），以后再考虑平台级的出网控制。
- 需要 `xuanpu-spec` ≥ 2026.10.2.7 才认得 `transport: remote` 及其校验规则（`xuanpu-server` 已按此声明依赖）。
