# ADR 0009：平台保持小核 —— 企业数据一律接入、自有文件走对象存储、垂直业务各自独立（修订 0007）

- 状态：Accepted（2026-09-30 用户确认方向，并拍板首批接入与存储选型，见决策 7）
- 日期：2026-09-30
- 关联：ADR 0001（定位与分层）、ADR 0003（成熟组件采用不自研）、ADR 0004（四平面与效应闸门）、ADR 0005 决策 5（会话主存）、ADR 0007（修订其决策 3、4、5、6 与拆分顺序）、ADR 0008（声明式 HTTP 连接器）

## 背景

ADR 0007 提出了员工工作台、两层企业应用、个人空间。之后讨论了一个更根本的问题：把员工的工作区全部放到服务器上（文档、图片、邮件都在服务器端），是不是当年瘦客户端的重演？

结论是不是。瘦客户端失败的形态，是把**计算和画面**放在服务器上，终端只负责显示。后来赢的形态（Gmail、飞书文档、Figma），是把**数据和状态**放在服务器上，画面在本地浏览器里渲染。AI 场景让后一种更站得住：

| 瘦客户端当年的问题 | 在 AI 场景下 |
| --- | --- |
| 服务器算力贵，PC 越来越便宜 | 大模型只能跑在云端，算力本来就在服务器上，数据迟早要过去 |
| 画面走远程传输，操作卡顿 | 界面在浏览器本地渲染；跟 agent 的交互本身是异步的，一次几秒到几分钟 |
| 用户得不到好处，只是 IT 部门省钱 | agent 在员工离线时继续干活，这是本地环境做不到的 |
| 治理 | 闸门、审计、防注入只能在服务器端做（ADR 0004）；一个在员工电脑上读整块硬盘的 agent 管不住 |

检验标准只有一条：员工打开工作台，能不能看到「我不在的时候，agent 已经替我做完了什么」。如果只是把文件从电脑搬到服务器、用法和原来一样，那就是瘦客户端的重演。

在此基础上，用户确认了三点方向：

1. **所有企业数据都是接入进来的**：Gmail、飞书、企业微信文档等，数据留在原处。
2. **平台自己的文件用对象存储管理**，交给成熟组件。
3. **平台保持小，不做垂直业务。** 报销、财务这类系统以后可以自建，但每个都是独立设计、独立部署的系统。

## 决策

### 1. 平台的边界：只做四件通用的事

平台只做身份、接入、文件、agent 运行与治理。不包含任何垂直业务的数据模型。

**判据**：一个能力如果只对某一类业务有意义（报销单、合同、工单、发票），它属于独立系统，不进平台。

这与 ADR 0001 一致：业务方提交的是业务包（skills、连接器声明、策略、评测），不是数据模型。

### 2. 自建的垂直系统一律独立，按第三方的方式接入

以后自建的财务、报销等系统，都是独立的服务：自己的库、自己的发版节奏、自己的权限模型。

对平台来说，它们和飞书、Gmail 一样，只是一个连接。平台不给自家系统开后门：不共享数据库，不直接读表，只走声明过的接口和闸门。自建系统要像第三方一样，提供 OpenAPI 文档或 MCP server，这样它天然能经 ADR 0008 接入。

这样做的好处：

- 平台能保持小；
- 自建系统可以单独换掉，也可以被别的平台使用；
- 审计口径只有一套：自家系统的调用和第三方系统的调用走同一个闸门。

以报销为例：单据和审批状态在报销系统自己的库里；员工的发票照片先在个人空间里；agent 识别发票、填单，调报销系统的接口提交，并把附件上传到报销系统。报销系统用什么存储，由它自己决定。它可以和平台共用同一套对象存储集群，但要用自己的桶和自己的凭据：共用的是基础设施，数据不共用。

### 3. 企业数据留在来源系统，平台以员工身份接入

- 邮件、日历、IM、云文档（Gmail 与 Google Workspace、飞书、企业微信、钉钉等）都不搬家。
- **不托管邮件**：收发服务器、反垃圾、送达率、合规留存都是独立的专业领域。
- **不自研办公套件**：在「数据在线 + AI」的形态上，Microsoft 365、Google Workspace、飞书、WPS 已经是现成方案，企业的数据也在它们那里。
- **本阶段不建全文索引**：检索用来源系统自己的搜索接口。把外部内容镜像进平台做索引，就得持续同步来源系统的权限（来源里撤了某人的权限，索引也要跟着撤），代价高，等确有需求再单独立项。

**需要的新能力：员工授权（OAuth 用户授权）。**

- 员工在工作台授权一次，平台保管这名员工在该连接上的令牌，到期自动刷新。员工可以随时撤销；管理员可以在租户层面停用某个连接。
- 令牌加密存储，附加认证数据是「租户 + 用户 + 连接」，做法与现有 `EncryptedVault` 的「租户 + 密钥名」相同。令牌不进提示词、不进日志、不进审计正文。
- agent 代表谁在工作，就用谁的令牌。调用时经线程标识找到会话，再找到发起的员工；这与现在过闸审计的归属方式相同（缺口清单第 11 项的现行处理）。
- 企业凭据（服务账号、应用级令牌）照旧由管理员配置。

**以员工身份访问时，优先用 ADR 0008 的 HTTP 连接器。**

- HTTP 连接器的请求由平台逐次拼出，每次注入发起会话那名员工的令牌，天然能按人区分。
- stdio MCP 连接器是按运行时共用的进程，令牌在进程启动时给定。例如飞书官方的 MCP server 提供用户令牌模式，但它面向的是单个用户。
- 所以，stdio MCP 连接器第一版只用于企业凭据。以员工身份走 MCP，要等远端 MCP 传输（ADR 0006）和逐次调用鉴权。

**外部内容一律视为不可信输入。** 邮件正文是最典型的注入载体。沿用 ADR 0007 决策 5 的规则并扩大范围：会话里只要出现以员工身份读到的外部内容（邮件、文档、消息），`external` 类的连接器调用一律走审批，不受 `relaxed` 档位影响。

### 4. 平台自有文件走对象存储，只认 S3 协议（修订 ADR 0007 决策 4）

**范围**：个人空间里的文件、会话里上传的附件、agent 的产出。垂直系统的附件不在此列（见决策 2）。

**存储分工**：

| 放在哪里 | 放什么 |
| --- | --- |
| 控制面存储（Postgres） | 元数据：文件标识、所属用户、路径、版本号、大小、内容摘要、锁、最后修改者 |
| 对象存储 | 文件内容。对象键用不可变的版本标识，不用路径；改名、移动只改元数据 |

**版本与回收站由平台的元数据实现**：每个版本是一个对象，不依赖对象存储自身的版本功能。这样任何兼容 S3 的实现都能用。

**进出沙盒**：按 ADR 0007 决策 5，沙盒默认只拿到应用专属目录。

- 用户选中的文件从对象存储拷进沙盒工作区；
- 每轮对话结束时比对变更，改过的文件作为新版本上传并记审计。

ADR 0007 否决对象存储的理由是「大空间每次取一遍太慢」。在默认只拷选中文件的前提下，这个顾虑不成立，因为不存在「每次取整个空间」。ADR 0007 决策 5 的第三档权限（整个个人空间进沙盒）在对象存储上需要按需拉取，第一版暂不提供。

**上传与下载**：默认由平台鉴权并记审计后，签发限时链接，浏览器直接和对象存储传输，大文件不经平台进程。对象存储对浏览器不可达的部署，改由平台转发。

**对部署形态的影响**：个人空间不再需要多节点共享卷，计算节点离无状态更近一步（ADR 0004 决策 6）。会话主存仍受 ADR 0005 决策 5 的约束，不在本 ADR 范围内。

**选型**：平台代码只用 S3 协议的公共子集，即对象读写、分段上传、限时链接，不用任何一家的扩展。沿用 taifeng-stores 的做法，对至少两种实现跑同一套契约测试。

**MinIO 不作为默认选择。** 以下情况于 2026-09-30 核实：

- 2025 年 10 月，停止发布社区版的二进制和 Docker 镜像；
- 2025 年 12 月，进入维护模式；
- 2026 年 4 月 25 日，仓库归档为只读，README 注明不再维护；
- 许可证是 AGPLv3。

候选实现：

| 候选 | 许可证 | 现状 | 备注 |
| --- | --- | --- | --- |
| [RustFS](https://github.com/rustfs/rustfs) | Apache-2.0 | 2026-09-16 发布 1.0，核心的对象读写、分段上传、版本、复制已进入正式支持 | 定位是 MinIO 的替代；1.0 才发布两周，生产使用记录少 |
| [SeaweedFS](https://github.com/seaweedfs/seaweedfs) | Apache-2.0 | 长期维护，S3 网关是其中一个组件 | 架构与 MinIO 不同，运维方式要单独了解 |
| Ceph RGW | LGPL | 成熟，大规模部署多 | 重，适合已经有 Ceph 的企业 |
| [pgsty/minio](https://github.com/pgsty/minio) | AGPLv3 | 社区分支：只修安全问题、不加功能，恢复了管理界面，提供二进制 | 维护者单一；AGPL 在不少企业的法务上过不去 |
| 云厂商对象存储（阿里云 OSS、腾讯云 COS、AWS S3） | 商业服务 | — | 公有云部署时直接用 |

开发与测试环境默认用哪一个，放到 P3 设计时定：对 RustFS 和 SeaweedFS 跑同一套契约测试后再决定。生产环境由部署方选择。

### 5. 文档在哪里写，就回到哪里改

- 来源系统里的文档（飞书云文档、企业微信文档、Google Docs）在它们自己的编辑器里编辑，工作台只提供跳转，不嵌入另造的编辑器。
- 平台自有文件的在线编辑仍按 ADR 0007 决策 6 处理：采用 WOPI 类的现成编辑器，单独评估。

### 6. 调整拆分顺序（修订 ADR 0007 的「拆分与顺序」）

| # | 子项目 | 相对 ADR 0007 的变化 | 依赖 |
| --- | --- | --- | --- |
| P1 | 用户身份 | 不变 | 无 |
| P2 | 应用目录 | 不变 | P1 |
| P3 | 个人空间 | 存储改为对象存储加元数据；含选型评估 | P1 |
| P4 | 空间进会话 | 拷入与写回改为经对象存储；第三档权限暂缓 | P2、P3 |
| P5 | 工作台 | 增加「连接」页：授权、撤销、查看已授权的连接 | P1 起步 |
| P6 | 连接目录与员工授权 | **提前**：与 P2、P3 并行。不再依赖 ADR 0006，因为以员工身份的访问先走 HTTP 连接器 | P1 |
| P7 | 在线编辑 | 仅限平台自有文件 | P3 |

新顺序：P1 → P2、P3、P6 并行 → P4；P5 在 P1 之后并行推进；P7 最后。

P6 提前的理由：多数企业的邮件和文档已经在线了，「数据都在线」的第一步是把这些已有数据接进来，而不是再造一个存储。

### 7. 首批范围与选型（2026-09-30 拍板）

**首批接入飞书和 Gmail。** 企业微信、钉钉等以后再定。每个来源具体开放哪些接口，在 P6 设计时定；建议飞书从云文档、日历、消息开始。

**飞书走 HTTP 接口调用，不走多人共用的 MCP 进程。**

- 每次调用注入发起会话那名员工的 `user_access_token`（员工授权，见决策 3）。
- 飞书官方的 MCP server（[lark-openapi-mcp](https://github.com/larksuite/lark-openapi-mcp)，MIT）是一个进程服务一个用户：令牌在登录后存在本地，不能多人共用。
- 以后如果某项能力只能走 MCP，就给每名员工单独起进程。这是决策 3 里「等远端 MCP 传输」之外的另一条路。这样做有两个代价：进程数是「活跃员工数 × 应用数」；员工令牌有效期短（约两小时，以飞书文档为准），刷新后还要让进程拿到新令牌。所以按人起进程只作备选。
- 本次没有找到飞书官方的 OpenAPI 描述文件。用到的接口由平台维护一份 OpenAPI 3 描述，只含用到的子集，作为预置的连接模板随平台发布。它是数据不是代码，符合 ADR 0008。

**Gmail 同样走 HTTP 接口加员工授权。**

- Google 只提供自己的 Discovery 描述，不是 OpenAPI 3，因此同样由平台维护一份子集描述。
- **邮件正文以 base64url 编码返回**，而 HTTP 连接器目前把响应原样交给模型，模型读不懂。这个问题 P6 设计时必须解决。候选做法有两种：给连接器加一种通用的响应解码规则（平台代码，不是业务方代码）；或者正文读取改走按人的 MCP 进程。

**对象存储：生产用阿里云 OSS，经它的 S3 兼容接口接入。** 平台代码仍然只用 S3 协议。以下兼容要点已按阿里云文档核实：

| 要点 | 影响 |
| --- | --- |
| 只支持虚拟托管式访问 | 桶名不能带下划线；本地的 S3 实现通常用路径式，所以寻址方式必须做成配置项 |
| 不支持 aws-chunked 分块编码 | 按阿里云文档，Python 的 boto3 要改用 V2 签名（`signature_version='s3'`）。另外，较新版本的 AWS SDK 默认对上传计算校验和，可能引入分块编码，P3 要验证并关掉 |
| S3 兼容接口的外网、内网地址不同：`s3.oss-<地域>.aliyuncs.com`、`s3.oss-<地域>-internal.aliyuncs.com` | 平台服务访问 OSS 走内网地址；发给浏览器的限时链接用外网地址 |
| 跨地域访问不会重定向，直接报 `NoSuchBucket` | 地域写进配置，启动时自检 |

**有一项没核实：** OSS 的 S3 兼容接口能不能生成限时链接（预签名 URL）、要用哪种签名，文档没有写。P3 的第一件事就是验证它。如果不行，只有「生成限时链接」这一项改用 OSS 原生 SDK，隔离在一个实现类里；这是唯一允许出现的 OSS 专用代码。

**本地开发与持续集成**仍用本地的 S3 兼容实现（RustFS 或 SeaweedFS，在 P3 定）。契约测试要同时对本地实现和真实 OSS 跑：真实 OSS 的凭据经环境变量提供，没有时跳过，与 taifeng-stores 对 Postgres 的做法相同。

**访问凭据**：用只授权平台自己那个桶的专用 RAM 身份，不用主账号的 AccessKey。

## 否决的方案

| 方案 | 否决原因 |
| --- | --- |
| 平台内置垂直业务模块（报销、合同、工单） | 平台变重；每个业务发版都要拖着平台一起发；与 ADR 0001「业务方只提交业务包」冲突 |
| 平台给业务包托管业务数据库（做成 aPaaS） | 同上。垂直系统需要自己的数据时，独立建系统 |
| 自家系统直连平台数据库，或平台直读自家系统的库 | 边界会被慢慢蚀空；审计会出现不经闸门的路径 |
| 把邮件、文档同步镜像到平台 | 权限同步难、数据重复、合规面扩大 |
| 自建邮件服务器或办公套件 | 见决策 3 |
| 个人空间用本地目录加共享卷（ADR 0007 原方案） | 多节点要共享卷，扩容、备份都绑在文件系统上；对象存储是企业已有的基础设施 |
| 直接依赖 MinIO 社区版 | 已停止维护并归档，见决策 4 |
| 用托管授权服务（例如 Composio）保管员工令牌 | 令牌存在第三方；企业内网系统连不到；ADR 0007 已否决 |

## 对内核的依赖

没有新增的内核缺口。

- 文件的拷入与写回由平台在内核之外完成。
- 按员工注入令牌，由平台的连接器桥根据线程标识完成。
- ADR 0007 列出的依赖（PDF 附件类型不在稳定层、文件类工具与 `WorkspaceFS`、`CancelTurn`）仍然有效。

## 后果

- 平台多出一项必需的外部依赖：兼容 S3 的对象存储。
- **每个来源都要在对方平台注册授权应用**（飞书开放平台的自建应用、Google Cloud 的授权应用等），每个租户各自注册、各自拿客户端凭据。部署成本落在租户侧，接入手册要写清楚。
- Gmail 的读信权限属于 Google 的受限范围：只给本组织 Workspace 用户用的内部应用，与面向组织外用户的应用，审核要求不同。各来源的授权方式与审核要求本 ADR 未逐项核实，接入每个来源时确认。
- **平台握有员工的授权令牌**：一旦被攻破，攻击者可以以员工身份读邮件。缓解措施有四项：只申请用得到的权限范围、令牌加密存储、员工可随时撤销、每次使用记审计。
- 自建的垂直系统要像第三方一样提供接口描述，这是它们接入平台的前提。
- 平台要长期维护飞书、Gmail 两份接口描述的子集；来源接口变了，描述要跟着改。这类维护集中在预置连接模板里，不进平台代码。
- 本 ADR 接受后，以下内容被取代：ADR 0007 决策 4 的存储方式、决策 5 第三档权限的时间点、「拆分与顺序」，以及否决方案表里「个人空间用对象存储」一行。
