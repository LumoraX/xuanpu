# ADR 0010：用户身份 —— 飞书登录、服务端登录会话、离职事件走回调

- 状态：Accepted
- 日期：2026-09-30
- 关联：ADR 0003（成熟组件采用不自研）、ADR 0007（决策 2 与拍板结果第 1、3 项）、ADR 0009
- 详细设计：[P1 用户身份](../superpowers/specs/2026-09-30-p1-user-identity-design.md)

## 背景

ADR 0007 定了先做用户身份（P1），拍板结果定了直接接飞书登录。落到实现，还有几处取舍会长期影响平台，单独记下：

- 用飞书的哪个标识认人；
- 登录状态放在哪里；
- 员工离职后平台怎么知道；
- 要不要引入飞书 SDK 或 OAuth 库。

依据的飞书事实见详细设计第 3 节，均于 2026-09-30 对照飞书开放平台文档与官方 SDK `lark-oapi` 1.7.3 的源码核实。

## 决策

1. **登录走飞书 OAuth 2.0 授权码流程，加 PKCE，由平台自己实现。** 飞书的网页登录不是标准 OIDC，不返回 id_token。整个流程只有「拼授权地址、换令牌、取用户信息」三步。平台内部按「身份源」抽象，以后可以加通用 OIDC。

2. **用 `union_id` 认人。**

   | 标识 | 为什么不用或用 |
   | --- | --- |
   | `open_id` | 不用：每个应用一套，应用重建后会变 |
   | `user_id` | 不用：管理员可以修改 |
   | 邮箱、手机号 | 不用：飞书明确提示是管理员导入的、未经本人验证，不建议当登录凭证 |
   | `union_id` | 用：在同一开发商的各个应用之间不变，自建应用的开发商就是企业自己 |

   平台内部一律用自己分配的用户标识，飞书标识只作外部映射。另外，首次登录时绑定飞书企业的 `tenant_key`，之后的登录与事件都必须一致。

3. **谁能登录由飞书应用的「可用范围」决定。** 首次登录自动建账号，默认普通成员。平台不再维护一份开通名单，避免两边各配一遍。

4. **登录会话存在服务端。** cookie 里只放随机令牌，库里只存它的摘要；每个请求都查库，不做缓存。不用自包含令牌（JWT），因为员工停用必须立即生效，而自包含令牌在到期前没法收回。有效期默认 7 天，从登录时刻算起，不滑动。

5. **离职感知：飞书事件走 HTTP 回调，另加每日对账。**
   - 不用长连接。飞书的长连接协议没有公开规范，只能用官方 SDK；而 SDK 的长连接客户端在模块导入时绑定全局事件循环、`start()` 一直阻塞，放不进平台的异步服务，同一进程里也开不了多个。要用它，只能每个租户单独起一个进程，进程数是「平台实例数 × 租户数」，还要另外看护。
   - 回调要求 Encrypt Key 必填，以便验签。
   - **对账时在飞书查不到的人不自动停用。** 飞书文档说明，不在应用通讯录权限范围内的人不会返回；离职员工是否返回，文档没写。自动停用可能误伤，所以只做标记，由管理员判断。

6. **系统代员工调用要显式授予，生效角色取两者中较低的。** API key 签发时单独授予这项能力，调用时声明员工。生效角色取 key 的角色与员工角色中较低的那个，防止普通成员的 key 借管理员身份越权。审计同时记下 key 和员工。

7. **登录拿到的飞书令牌用完即丢。** 登录只申请识别身份需要的最小权限；读数据的授权由 P6 单独申请、单独保管，权限范围和撤销都与登录分开。

8. **不引入飞书 SDK，也不引入 OAuth 库**（按 ADR 0003 说明理由）：
   - 长连接用不上，见决策 5；
   - 剩下的是 4 个接口调用和回调的验签解密，用现有的 `httpx` 与 `cryptography` 就能写完；引入 SDK 反而会带进 `requests`、`pycryptodome`、`websockets`；
   - 飞书的令牌接口要 JSON 请求体，不是标准 OAuth 的写法，OAuth 库帮不上多少忙；
   - 密码学部分没有自造算法，都是现成库的标准原语。

## 否决的方案

| 方案 | 原因 |
| --- | --- |
| 经身份中介（Keycloak、Casdoor 等）把飞书转成 OIDC | ADR 0007 拍板结果第 1 项已否决：P6 本来就要实现同一套飞书授权流程，为它再部署、运维一个组件不划算 |
| 平台里预先开通员工 | 与飞书的可用范围重复维护 |
| JWT 登录令牌 | 停用无法立即生效 |
| 长连接收事件（每租户一个进程） | 见决策 5 |
| 只做定时对账 | 离职到停用最多延迟一个周期，这段时间里 agent 仍能用他的授权 |
| 用邮箱认人 | 见决策 2 |

## 后果

- **飞书的服务器必须能从公网访问到平台的事件回调地址。** 纯内网部署要么放通这一个地址，要么将来补上长连接进程。
- 飞书应用要开 `contact:contact.base:readonly`（获取通讯录基本信息）权限，并且「通讯录权限范围」要覆盖「可用范围」，否则对账会出现大量查不到的人。
- 平台开始直接面向浏览器，要负责 cookie、跨站请求伪造、开放跳转这一整面的防护（详细设计第 12 节）。
- 有 4 项飞书行为只能用真实应用核实（详细设计第 14 节）。核实结果与本 ADR 不符时，改用新 ADR 修订。
