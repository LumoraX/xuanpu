# ADR 0019：玄圃自有账号 —— 用户名口令登录，外部平台降为可选登录方式

- 状态：Accepted
- 日期：2026-11-17
- 关联：Supersedes ADR 0007「用户来自企业自己的身份源，平台不自建账号密码体系」一条；ADR 0003（成熟组件采用不自研）、ADR 0010（服务端登录会话）、ADR 0014（玄圃企业核心）
- 实现：[账号体系](../architecture/accounts.md)

## 背景

ADR 0007 定下「平台不自建账号密码体系」，员工只能经飞书（后来加了企业微信）登录。ADR 0014 之后玄圃是企业核心系统，外部平台必须可以替换；而现在没有飞书或企业微信就没有任何人能登录，第一名管理员也只能从飞书进来。这与核心定位矛盾，也挡住了以后把 Google、GitHub 等作为登录方式或能力连接接进来：它们都需要先有一个玄圃账号去挂。

平台用户（`UserRecord`，`usr_…`）本来就是玄圃自己的，会话、审计、用量都记它；缺的只是一个不依赖外部平台的凭据。

## 决策

1. **玄圃账号是唯一的权威账号。** 飞书、企业微信，以及以后的 Google、GitHub、通用 OIDC，都只是挂在账号上的登录方式或能力连接，可以增减，不能替代账号本身。
2. **第一种自有凭据是用户名加口令。** 用户名在租户内唯一、不区分大小写，由管理员分配。邮箱、手机号以后作为可验证的联系方式另加，不作为第一版的登录名。
3. **口令只存 argon2id 摘要，由 `argon2-cffi` 计算。** 参数用库的默认值（RFC 9106 低内存档）；登录时库判断参数过时就顺手重算。慢哈希放进线程池、全进程限并发，防止被刷成 CPU 拒绝服务。不自造任何密码学。
4. **账号由管理员开通，员工自己设口令。** 管理员建账号得到一次性设置链接（只存摘要，7 天有效）；重置口令同样签发一次性链接（24 小时）。平台不发邮件，链接由管理员经企业自己的渠道转交。令牌放在链接的片段（`#`）里，不进服务端日志与 Referer。
5. **登录沿用 ADR 0010 的服务端登录会话。** 口令登录成功后签发同一种 cookie；停用、退出、过期规则完全相同，不引入 JWT。
6. **失败不透露原因。** 用户名不存在、口令错误、账号锁定、账号停用对外是同一个 401；用户名不存在时照样算一次摘要。同一账号连续失败 5 次锁 15 分钟。
7. **登录与设口令接口按 cookie 写请求防护。** 要求 `X-Requested-By: xuanpu` 与同源 `Origin`，防止跨站把员工登录进别人的账号；没有配置 `public_url` 的部署不开放口令登录。
8. **第一名管理员经平台管理员签发的租户管理员 API key 开通**，走与日常相同的建账号接口，不另设后门。

## 否决的方案

| 方案 | 原因 |
| --- | --- |
| 部署 Keycloak / Zitadel 作账号中心 | 账号是租户核心数据，要与停用流水线、审计、组织在同一事务边界内；为第一种凭据再运维一个身份系统不划算。以后要对其他企业系统提供 SSO 时，再评估玄圃自己作 OIDC 提供方还是接入现成产品 |
| 用邮箱作登录名 | 国内企业未必配邮件服务；飞书来的邮箱未经本人验证（ADR 0010 决策 2） |
| 自写口令哈希或用 PBKDF2 | ADR 0003；argon2id 是当前推荐算法 |
| 员工自助注册 | 企业系统的账号由企业开通 |
| 平台直接发设置邮件 | 需要邮件服务，留给后续「联系方式」一期 |

## 后果

- 部署可以完全不接飞书、企业微信运行；已经接了的照旧工作，飞书仍可自动建账号。
- 飞书来的员工也可以由管理员补发设置链接，获得口令作为备用登录方式。
- 新增两张表（`local_credential`、`account_token`），迁移 `0026`。
- 每台实例同时最多算 4 个口令摘要（每个约 64 MiB 内存），高并发登录会排队。
- 后续分期：二次验证（TOTP）、外部登录方式的统一抽象与账号绑定、玄圃给桌面端与命令行签发令牌、按员工授权的能力连接。
