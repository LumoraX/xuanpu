# R3 企业数据与协同设计提案

- 日期：2026-10-22；状态：详细实施提案，等待实施授权，不代表功能已实现。
- 已确认：企业日常办公与业务协同优先；用户选择**企业微信只读**作为首个真实集成。
- 基线：本地主线`823cd571ef7482138fea1fdae5a111196ae87af3`；R2生产server 2026.10.22.2、console/SDK/CLI 2026.10.22.1、迁移0014。R2强制验收已完成，真实企业OAuth仍未验。
- 来源：[总规划](2026-10-20-platform-capabilities-design.md)、[R2验收](../../guides/releases/2026-10-21-r2-acceptance.md)、[ADR0014](../../decisions/0014-enterprise-core-and-durable-reminders.md)。

## 1 交付目标与路线

员工以自己的玄圃身份连接企业微信、读取有权看到的信息，把明确材料交给一个部门；接收方能认领、退回、要求补充、提交成果，经有权审批人与发起人分别决定后签收。全部状态在玄圃，通知出口和外部数据源可替换。

| 路线 | 取舍 |
| --- | --- |
| 分层交付连接、组织、共享、交接审批，推荐 | 每层可独立验收；先真实只读再跨员工流转，复用R2，权限缺口不会藏进大版本 |
| 同时接文档、日历、邮件及企业微信完整生态 | 外部权限和接口组合太多，真实验收前提无法冻结；不采用 |
| 直接建设无人部门agent和通用流程引擎 | 当前主体只有人、机器与系统调用者，现有事务按个人隔离；过早提升服务身份风险和改造成本高；不采用 |

采用第一条。R3-A连接与企微只读 → R3-B组织岗位 → R3-C共享事项 → R3-D交接及组织审批 → R3-E统一体验、真实试点和发布。A可先只读本人资料，B以后才开放经规则允许的其他成员查询。

不含：任意DAG/BPMN、多人会签与任意代理、无人部门服务账号自动执行、外部写操作、企微消息代发/聊天归档、全量文档检索、个人邮箱、跨租户协作、多实例、R4统一能力市场和行业财务流程。首个部门流程为**内部材料核对与结果交付**，避免把报销付款规则做进通用平台。

## 2 已有机制与真正缺口

| 当前实现 | R3增量 |
| --- | --- |
| `identity/`的Feishu登录、稳定usr标识、停用流水线和员工API | 增加WeCom身份适配与显式稳定映射；保留Feishu接口，不按名字/邮箱自动合并账户 |
| `secrets.py` AES-GCM及SecretVault、HTTP/remote MCP逐请求取租户密钥 | 复用加密与逐次读取；新增installation与员工consent解析，不重建Vault、不把应用token当员工权限 |
| `runtime/assembler.py`已含ExecutionScope，员工/任务隔离已实现 | 复用scope；连接授权依然每次调用验证，不能只相信缓存key |
| `workspace/`按员工事务，私有matter/file/todo/event | 新增共享事项领域及跨域事务；不把两个个人事务拼作一次交接，不修改旧私有内容归属 |
| `work_tasks/`、`task_triggers/`的grant、budget、effect、恢复 | 复用原执行、配额和unknown屏障；R3交接不是新的模型worker或R2状态 |
| `runtime/content_access.py`本人正文、管理员元数据 | 继续生效；组织管理员不因此获得个人或共享事项正文 |
| 统一站内通知和outbox | 新增共享事项/交接/审批来源，动态权限过滤及稳定语义键 |

只使用泰逢公开接缝。R3没有既定内核改动；若稳定协议不支持某个入口，先记契约阻塞，不能导入私有类或伪造已验恢复。

## 3 企业微信第一试点与授权边界

### 3.1 身份、应用凭据、员工同意是三件事

1. `Installation`由企业管理员登记provider、外部企业标识、应用标识、固定端点、secret引用和允许operation；自建应用先行，不同时实现第三方应用服务商授权。
2. `ExternalAccountBinding`把企微稳定成员标识映射到玄圃usr；必须绑定同一企业。已有人先显式映射，新人首次登录只在管理员明确允许的入职策略下建普通成员，绝不按同名自动合并或自动授予管理员。
3. `EmployeeConsent`是玄圃对具体installation、用途、可读对象和有效期的委托。默认仅`self_profile.read`；可撤销，带version/epoch。授予/扩大必须由员工本人浏览器确认，API key/act-as不能代替本人同意。
4. `CredentialBroker`每次真实调用从已认证会话查usr，验证租户、员工、binding、consent、installation和当前范围，再注入应用token。工具参数不能指定另一usr、企业、连接密钥或access_token。

企业微信团队的[历史API示例](https://github.com/sbzhu/weworkapi_python/blob/master/api/src/CorpApi.py)展示应用凭据取token及成员读取调用形态；[团队README](https://github.com/sbzhu/weworkapi_python/blob/master/README.md)说明缓存与失效更新。这是历史一手实现，**不能保证2026年的权限、字段和产品范围**。2026-10-22对官方文档门户的抓取未成功；A0必须在当前官方文档及真实自建应用后台重新冻结契约，才能验收真实集成，不套用飞书PKCE或OAuth refresh_token假设。

### 3.2 首批明确行为

- 员工：真实网页登录/绑定本人企微身份，明确同意后只读本人基础资料，显示provider、读取时刻、实际字段及不可用字段；不默认取手机号、邮箱等敏感字段。
- 管理员：只读预览应用实际可见的部门及成员范围，分批列出不完整/失败；A阶段不导入、不删除玄圃组织，不把可见范围当全企业。
- 企业应用token按installation缓存、单次更新合并；失效后至多一次重新取token并重试已确认只读调用，不伪造个人refresh_token。任何无员工调用不能使用员工consent。
- 用户撤销只撤销玄圃委托，不宣称已撤销供应商整个应用token。供应商token失效、应用权限变化、用户不再可见均应明确阻塞。
- 首次真实验收需要CorpID、AgentID、secret私有引用、可信域名/IP、实际员工和可见范围，由A0清单列明；本规划不索要密钥。

## 4 组织岗位及权威来源

玄圃分配稳定部门、岗位、成员关系ID；外部标识仅映射。部门树、岗位职责、审批权限和账号角色分别建模；担任部门负责人不自动成为tenant_admin。

| 数据 | 默认权威与同步 |
| --- | --- |
| usr/部门/岗位稳定ID、流程与权限 | 玄圃；外部不能覆盖内部ID和授权决定 |
| 外部成员/部门标识及可见范围 | 对应installation；保存采集时刻、完整性、外部版本/摘要 |
| 名称、任职、成员状态 | 每字段选择local或指定source；外部变化先形成预览差异，按审批的来源规则应用 |
| 操作岗位、审批职责、部门承办权限 | 玄圃管理员/被授权组织管理人，供应商普通字段不能提升权限 |

第一版只做**只读外部采集→差异预览→明确应用到玄圃**，不向企微写回。来源缩小、分页失败、单次缺失不能推导离职或批量删除；显式经权威来源验证的停用才进入既有停用流水线。旧Feishu登录刷新名称等行为也必须服从新字段权威，不能下次登录又覆盖本地决定。重组、离职、权限变化产生持久治理事件，后台监听只能辅助，鉴权必须即时查当前状态。

## 5 共享事项、材料与模型上下文

新增`SharedMatter`，保留旧个人matter接口与表。每个共享事项有负责人、参与者、责任部门、版本、状态、权限epoch和历史；内容权限显式授予，管理员只有统计不继承正文。

成员角色：owner管理成员/提交；editor改工作内容并交付；viewer只读。执行身份、审批职责、组织管理权不由此互相推导。每次读写、列表、搜索、SSE补读、附件下载和统计都按当前ACL过滤。

材料通过本人原生确认发布**固定版本共享副本**，也支持直接上传及经确认的共享文本草稿，网络/对象I/O在事务外、pending intent+提交CAS在事务内。个人原件归属不变；删除个人原件不自动撤回已经发布的共享副本，界面须说明。更新材料形成新revision，旧版本和签收证据保留；平台受控生成的共享结果保留source_refs并限制后续读取/发布。撤回阻止后续服务端获取，不能追回已经读到或下载的字节。

R3的共享读取不把文件静默复制到接收人的私有空间，不允许通用R2任务凭shared_id绕过本人输入检查。共享上下文读取仅走受控工具并记录source dependency；每次后续模型请求、恢复、正文补读前验证ACL epoch，撤权关闭/阻塞受影响会话并清除可复用上下文。已发送给模型的历史字节不声称可撤回。共享文件直接挂进通用后台沙盒、共享输入派生物全链路治理另立后续工作，R3不冒称支持。

## 6 部门助理与交接

部门助理首版是**有真人责任人的部门受理入口**：部门可配置接收岗位、值守人和一个固定助理视图；读取共享事实、提出核对摘要和下一步草稿。实际认领、退回、补充、组织决定和交付由有权真人执行。没有员工身份的部门API key不能借此运行个人连接，部门不会被伪装成一个普通usr。

`Handoff`状态：submitted→accepted→in_progress→delivered→signed_off；分支needs_information、returned、cancelled、disputed。needs_information经发起人补充→submitted；returned为本次终态，重新提交创建新handoff并引用原单；delivered后发起人可签收或disputed，disputed由承办人明确重办→in_progress。任何分支都不能自动改成signed_off。

一次交接固定：shared matter版本、明确材料版本、目标部门、截止、请求类型、发起人；接收方得到的只是明确授予的事项和材料：未认领队列只见packet摘要，认领后只给当前承办人所选材料的内容权限；不能借同一shared_id打开其余正文或附件。首版跨部门submit由事项owner原生确认，普通editor只能准备建议。队列支持两人竞争认领但只有一个承办人，转交需有权真人确认，不自动读取发起人的个人会话或其其他文件。

业务交接不使用内核同伴消息做权威队列。助手在当前真人身份下读取有权共享事实，不能自主认领、组织批准、自动签收或对外执行。R2只接受本人既有可用材料；交接的完成不由task succeeded或一条聊天声明推导。

## 7 组织审批与成果签收

`ApprovalRequest`独立于工具批准、交接和成果签收；首版只支持**一到三步顺序单人审批**，审批人来自显式员工或当前岗位规则，无会签/或签/自动代理。提交时冻结规则版本、目标对象版本、材料revision/摘要与审批步骤；决定时再验证审批人当前资格、目标版本和输入是否变化。

- 不允许发起人自批；未决步骤无有效审批人/离职/岗位失效进入blocked，不能默认通过或静默换人。
- 审批同意只推进内部工作资格；仍不授权外部写入或发起人的个人连接。
- 审批通过后若材料变化，旧批准记录保留但对新内容失效，须新请求；拒绝/退回/撤销有独立回执。
- `handoff delivered`可在规则要求的内部审批全部通过后提交；原发起人或明确指定签收人核对固定成果revision后签收，不能用审批同意代替签收。
- 首试点用“内部材料核对→部门受理→负责人批准→承办人提交结果→发起人签收”，不写入外部业务系统。

## 8 事务、故障与事件

R3-B建立`CoordinationStore`，memory与PG同契约。PG复用现有连接池：短事务按租户协调锁→有序参与员工行→组织/事项→交接→审批→outbox加锁，全部限定同租户；锁序在编码前固定并测试。身份停用先提交原身份事务，再执行可重入跨域收尾，不能嵌套原WorkspaceStore事务。

领域变更、版本CAS、request_id幂等回执、业务事件与通知投递意图同事务提交。外部HTTP、模型、对象传输均不在事务内。事件逐条ack，不以最大序号当提交水位；稳定语义键抑制重复。撤权先让查询与决定拒绝，异步取消/清理不得成为权限生效的前提。

通知只保存必要来源引用，收件人补读时再查当前可见性；外部通知默认关闭，正文不随通知泄露。模型只提出建议，原生接口可在模型不可用时处理认领、补充、批准和签收。

## 9 数据、部署及签收

建议迁移：0015连接身份与委托；0016组织岗位/来源/协调事务；0017共享事项/材料/来源依赖及通知来源；0018交接及通知来源；0019顺序审批及通知来源。实施前核对最新编号，有占用时顺延，绝不改已发布SQL。旧默认空字段及旧API保持兼容，所有R3开关默认false并有tenant_ids。

独立签收层：源码/双后端测试→真实PG/HTTP故障→真实模型→CUA桌面/窄屏→真实企微身份/权限→镜像源码与版本→兼容部署→合成灰度→真实部门试点→前向回退及清理。R2门禁不能拿来当R3通过数。

没有真实企业身份或供应商范围证据，A/E保持partial；没有跨人员完整接受、退回、补充、交付、审批、签收，D/E不能完成。外部写入接口实际调用计数必须为0。只读许可不因试点获得发消息或财务授权。

详细工作包见[R3总计划](../plans/2026-10-22-r3-delivery.md)。
