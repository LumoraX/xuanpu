# 财务F4：F0–F3缺口收敛设计

用户已明确要求拆出F4并开始开发，继续使用独立存储、Skill/API和HITL；本设计在该授权内细化，不改变财务权威边界，也不启用尚未选定的外部供应商。本轮基线a9543f0，复用独立检出xuanpu-finance-f0，分支feat/finance-f4；不推送、合并或部署生产。

## 缺口与取舍

| 缺口 | 当前事实 | F4实施及验收 |
| --- | --- | --- |
| 通知与待办 | F1/F2 finance_outbox持久pending，F3缺少统一提醒 | 原生财务站内通知，持久消费旧Outbox；补齐当前审批/超时、F0补件、F2/F3未知及红字期限/档案健康提醒；不声称微信、飞书或邮件送达 |
| 分页 | F3及统一计划/待办先读全量再逐行授权 | 在SQL内完成相同最小权限过滤、独立count和LIMIT limit+1；游标绑定主体/过滤条件；不改变授权与目标类型 |
| 接入状态 | listIntegrations固定unconfigured，内部审批/隔离通道也被误报 | 从实际持久政策、配置/代数、模式给出internal/configured_simulation/unconfigured/disabled等状态，明确正式未验收；不暴露凭据 |
| 运行可见性 | health只有进程探活，故障任务与在途需逐项查 | 公司reviewer只读运营概览：F0/F2/F3队列、最早排队/未知、待审/过期与站内通知计数；展示后台任务故障，不返回原回执/账户/对象键 |
| 独立备份恢复 | 只有指南建议，没有配套恢复演练 | 使用成熟pg_dump/pg_restore工具，维护时获得与服务相同的独占锁，备份独立DB+加密对象+清册hash；只恢复新空目标库和新对象根，校验后输出恢复证据，不启动写任务 |
| 正式能力与外部依赖 | 尚无真实供应商、标准样本/签名、WORM/异机DR、真实模型评测及企微/飞书报销 | 显式记录为外部阻断；保持正式动作关闭；不以本轮隔离验收冲销 |

推荐按“原生内部收敛+性能+可恢复性”推进。仅性能优化无法补通知与恢复缺口；直接接真实供应商缺少授权和接口资料。采用已有PostgreSQL事务/唯一约束、AES-GCM、pg_dump/pg_restore，不自研消息中间件或备份数据库格式。

## 原生通知与HITL

财务通知和通知读状态仍在独立财务PG。通知是待办索引及状态变化提示，不能代表业务批准、渠道成功或外部消息送达。旧finance_outbox由有界消费者映射为原生站内通知后标记inbox_recorded；无对应可见资源或收件人时保留可诊断状态，不能无声丢弃。

F4补充当前可操作来源：F0开放异常的owner；F1/F2/F3实际当前审批人（含到期提醒）；F2/F3 outcome_unknown的原经办；红字待核对期限和归档审计/补包缺口的当前有权经办。按来源ID、版本/状态、收件人和提醒种类稳定去重，不按扫描次数发新消息；恢复和并发不得重复。扫描和消费均有batch上限并避免旧记录永久饿死新记录；无真实接收人不扩大为全公司广播。通知只带固定中文摘要和资源引用，避免原件、完整账户、凭据等正文复制。

读取和已读命令必须核对租户/公司当前授权以及当前资源可见性；撤权/撤销审批资格后不能通过旧通知继续取他人资料。未读计数独立于页面，保留游标和limit 1–100。已读是人工偏好状态，不是审批，真实员工接口具有expected_version和幂等键，模型不能代读/代批准。页面点击通知后恢复原目标/原计划；使用既有预检→专用批准→原经办执行，不能从通知正文创建成功状态。

后台通知任务不依赖模型；模式disabled停止生成，实例锁丢失同时取消通知任务。外部查单依然只GET，通知不触发付款、税务、开票或归档写入。外部通知适配器未配置时明确none，native_inbox可单独使用。

## 查询与运营

F3所有列表和统一计划/审批队列以相同SQL授权谓词做count与分页。保持当前reviewer、owner、actor及有效generation审批指派语义，具体可见性不得宽于单记录读取；不要通过JOIN产生重复行。count和页面在repeatable_read内一致，跨租户/公司/条件游标拒绝。跨F2/F3合并列表采用有界UNION索引投影再读取当前页，不先加载全量业务JSON。

listIntegrations报告实际内部审批和模拟通道是否配置、策略是否启用及正式未验收；它是配置状态，不声称外部网络健康。新增getFinanceOverview只允许当前company reviewer；指标均限定同一tenant/company，原始事件和敏感回执不返回。API响应使用严格schema；Skill只能读取概览和通知，不获得新的执行权限。

## 配套备份与恢复

新增运维CLI，使用显式DSN文件、local对象根、32字节密钥文件及备份路径。F4首先支持local加密对象；S3服务端版本备份单列未实现并明确拒绝，不能静默遗漏。运行服务与维护命令共用WORKER_LOCK=617472002；服务未停止时备份失败，不强制停止或绕锁。

维护锁贯穿dump、复制、restore和发布；监听连接终止并在每个检查点核对持锁连接。丢锁立即取消子进程、停止后续步骤，禁止发布完整备份或新对象根，并明确报告目标DB是否可能已提交。

获得锁后pg_dump --format=custom保留独立DB；复制整个不可变密文对象目录（拒绝符号链接、路径穿越和非正常文件）；清册记录格式版本、文件hash/大小、DB标识、密钥指纹及时间，不包含DSN/令牌/密钥内容。临时目录权限0700；只有全部校验成功才原子发布到不存在的备份目录，失败不留下貌似完整的备份。密钥另行保全，备份不携带密钥。

恢复先核对清册、所有实际文件hash/大小和密钥指纹，再检查目标DSN只指向明确新建的finance_restore/finance_test库、public无用户表且没有其他非系统schema，对象目录不存在。获得目标同一独占锁；pg_restore使用单事务、退出即报错，不覆盖既有数据。对象先暂存，从finance_receipt/finance_item责任索引及F3归档请求/描述符建立原object_key映射，以AAD进行真实AES-GCM认证并核对已知明文hash/大小；必需引用缺失、错误对象根或合法头但认证失败均拒绝。prepared但尚未写对象的索引单列待恢复；额外无法映射的密文列为未认证，不能算完整可用。完整性验证通过后才发布；目标失败须报告状态而不自动drop或覆写库。恢复不会修改平台岗位、替换部署配置/凭据或启动worker；财务库内岗位及渠道历史随快照保留，重新启用前须复核现行授权和配置，旧dispatching/unknown保持原号只查。恢复报告必须区分数据库恢复、密文校验及实际原件解密读取，不能仅count/hash就声称已恢复可用。

测试额外覆盖dump/复制/restore中维护锁丢失、错误对象根、缺一个必需文件、XF01头合法但认证失败。

真实演练使用原件、F1审批历史、F2/F3未知请求/回执及归档材料，备份→新空库/新对象根→旧原件真实解密及原计划/请求保持→只读核对，禁止重发外部写入。该证据仅为同机隔离演练，不能外推异机故障域、生产RTO/RPO或真实WORM灾备。

## API、界面与验收

新增listFinanceNotifications、readFinanceNotification、getFinanceOverview；listIntegrations改为实际配置投影。JSON金额和既有human签名规则不变。通知只读工具加入已有Skill，不另加空壳Skill；已读工具不加入模型白名单。辅助页增加“财务提醒”“运行概览”，清楚区分未读/已读、待审批/已过期、未知/成功及当前模拟范围。
