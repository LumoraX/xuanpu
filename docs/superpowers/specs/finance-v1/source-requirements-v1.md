# 内部发票管理工具开发规范（V1.0）

## 0. 文档目的与适用对象

本文档用于研发、测试、财务合规方对齐需求，定义内部发票管理工具的数据模型、状态机、业务流程、接口约束、校验规则和归档要求。

适用对象：后端开发、前端开发、测试、财务产品负责人、合规对接人。

核心定位：本系统不是“上传发票填报销单”的表单工具，而是：
以 XML 原件为起点、以状态机为骨架、以证据链为输出的发票数据基础设施。

---

## 1. 合规底线

| 编号 | 底线要求 | 工程含义 |
|---|---|---|
| L1 | XML 数据电文是法定原件 | PDF/OFD 仅用于展示，不得替代 XML 归档；系统必须原生接收、解析、存储、校验 XML |
| L2 | 入账需形成结构化数据文件 | 不能只把票面字段存成宽表，入账信息需按标准组织结构化数据，并与会计凭证关联 |
| L3 | 归档不是存文件，而是存证据链 | 每张发票可追溯：来源渠道 → 查验结果 → 业务匹配 → 审批 → 支付 → 会计凭证 → 归档位置 |

研发注意：任何“先存文件再说”“票面字段差不多就行”的设计，都会导致后续合规改造。数据模型必须从 L1-L3 倒推。

## 2. 术语与对象边界

| 术语 | 定义 | 系统标识 |
|---|---|---|
| 发票记录 | 一张数电发票的主记录，业务唯一键为：20位发票号码 + 开票日期 + 销方税号 | Invoice |
| 结构化票面数据 | 从 XML 解析出的标准化字段集合 | InvoiceField |
| 业务关联 | 发票与报销单、采购订单、合同、付款单等的匹配关系 | BusinessLink |
| 入账记录 | 发票在会计层面的入账结果 | PostingRecord |
| 归档包 | 不可变证据集合：XML原件 + 结构化数据 + 业务关联快照 + 四性检测 + 审计元数据 | ArchivePackage |
| 状态事件 | 发票状态每次变更的审计记录 | StateEvent |

边界说明：本系统不替代 ERP 记账和 OA 审批。系统职责是发票数据归集、校验、状态管理、证据链组织和归档，并通过接口与 ERP/OA 交换凭证号、审批单号等关键标识。

## 3. 数据模型

### 3.1 发票主记录 Invoice

标识与状态类：

| 字段 | 类型 | 说明 |
|---|---|---|
| invoice_id | 内部主键 | 系统生成 |
| invoice_number | 20位字符串 | 数电发票号码，业务唯一键组成 |
| issue_date | date | 开票日期，业务唯一键组成 |
| seller_tax_id | 字符串 | 销方税号，业务唯一键组成 |
| invoice_type | 枚举 | 数电专票/数电普票/其他 |
| lifecycle_status | 枚举 | 见状态机 |
| is_red | 布尔 | 是否红字发票 |
| original_invoice_number | 字符串 | 红票关联的蓝票号码 |

金额与税务类：

| 字段 | 类型 | 说明 |
|---|---|---|
| amount_without_tax | decimal(18,2) | 不含税金额 |
| tax_amount | decimal(18,2) | 税额 |
| amount_with_tax | decimal(18,2) | 价税合计 |
| tax_rate | decimal(5,2) | 税率/征收率 |
| deductible_flag | 布尔 | 是否可抵扣 |
| effective_tax_amount | decimal(18,2) | 可抵扣税额 |

来源与文件类：

| 字段 | 类型 | 说明 |
|---|---|---|
| source_channel | 枚举 | 税局API/邮箱/上传/扫描/第三方同步 |
| xml_object_key | 字符串 | XML原件对象存储路径，不可为空 |
| pdf_object_key | 字符串 | 版式文件路径，可选 |
| xml_checksum | 字符串 | XML哈希值，防篡改 |
| xml_received_at | datetime | XML接收时间 |

入账与归档类：

| 字段 | 类型 | 说明 |
|---|---|---|
| posting_status | 枚举 | 未入账/已入账/已冲回 |
| voucher_number | 字符串 | 会计凭证号，ERP回写 |
| accounting_period | yyyy-MM | 会计期间 |
| archive_status | 枚举 | 未归档/已归档/归档异常 |
| archive_package_id | 字符串 | 关联归档包 |

### 3.2 结构化票面字段 InvoiceField

设计原则：票面字段不以宽表散落存储，而以“键值对 + 数据元标识符”存储，便于对齐国家标准和扩展票种。

| 字段 | 说明 |
|---|---|
| field_code | 数据元标识符，对齐电子凭证会计数据标准 |
| field_name | 标准标签 |
| field_value | 标准化后的值 |
| raw_value | XML原始值，用于追溯 |
| data_type | 日期/金额/字符串/枚举等 |

研发注意：field_code 必须来自标准元素清单，不能自行发明。标准外的业务扩展字段使用 EXT_ 前缀隔离。

### 3.3 业务关联 BusinessLink

| 字段 | 说明 |
|---|---|
| invoice_id | 关联发票 |
| business_type | 报销单/采购订单/合同/付款单/验收单 |
| business_id | 外部系统单据号 |
| link_method | 自动匹配/人工绑定 |
| match_score | 自动匹配置信度，可选 |
| linked_at | 关联时间 |
| linked_by | 操作人，自动则为 system |

支持一对多和多对一：一张发票可关联多个业务单据，多张发票可关联同一业务单据。不要在 Invoice 上设计单值 business_id。

### 3.4 状态事件 StateEvent

| 字段 | 说明 |
|---|---|
| invoice_id | 关联发票 |
| from_status | 变更前状态 |
| to_status | 变更后状态 |
| event_type | 查验通过/用途确认/入账/红冲锁定/归档等 |
| event_source | 系统触发/人工操作/税局回调 |
| operator | 操作人或系统标识 |
| occurred_at | 发生时间 |
| payload | 事件上下文 JSON |

StateEvent 只追加、不修改。它是审计日志，也是红冲判断时“是否曾入账/确认用途”的直接依据。

## 4. 状态机

发票生命周期不能用一个“有效/无效”标签替代，必须显式建模多个正交状态维度，并记录每次变更。

### 4.1 三个正交状态维度

| 维度 | 状态集合 | 说明 |
|---|---|---|
| 票据状态 ticket_status | NORMAL / RED_LOCKED / RED_ISSUED / VOID_ABNORMAL | 正常、红冲锁定、已红冲、异常凭证 |
| 入账状态 posting_status | NOT_POSTED / POSTED / REVERSED | 未入账、已入账、已冲回 |
| 用途确认状态 usage_status | NOT_CONFIRMED / CONFIRMED | 是否已进行用途确认 |

### 4.2 关键约束

1. usage_status = NOT_CONFIRMED 且 posting_status = NOT_POSTED 时，开票方发起红冲后票据被锁定，不允许再进行用途确认。
2. posting_status = POSTED 时，开票方或受票方可发起红冲，但需经对方确认《红字发票信息确认单》；确认时限为发起后72小时，超时流程自动作废。
3. 已部分红冲且已入账，未冲红部分仍可抵扣勾选；全额红冲则不允许继续抵扣。

### 4.3 状态流转触发点

| 触发事件 | 状态变化 | 系统动作 |
|---|---|---|
| 获取到发票 | ticket_status = NORMAL | 创建 Invoice，写 XML，解析字段 |
| 查验通过 | 记录 verified_at、verify_result | 写 StateEvent |
| 业务系统调用入账接口 | posting_status = POSTED | 写 PostingRecord，回写凭证号 |
| 用途确认成功 | usage_status = CONFIRMED | 写 StateEvent，记录确认所属期 |
| 红字发票或红冲锁定通知 | RED_LOCKED 或 RED_ISSUED | 写 StateEvent，阻断后续入账/确认，触发异常流程 |
| 归档完成 | archive_status = ARCHIVED | 生成不可变 ArchivePackage |

研发注意：状态变更必须通过统一状态服务完成，禁止各模块直接更新 Invoice 状态字段。每次变更必须同时写 StateEvent。

## 5. 业务流程与功能模块

### 5.1 端到端主流程

采集归集 → 结构化解析 → 查验/验真 → 查重与合规校验 → 业务匹配（四流一致性） → 入账/用途确认 → 归档封装

每个环节输出可被下一环节消费；异常必须进入异常池，不能静默丢弃或卡住主流程。

### 5.2 模块 A：采集与解析

- 支持税局 API 拉取、邮箱/上传/扫描、第三方同步。
- XML 必须原生处理：接收 XML 后解析结构化字段，同时写 XML 原件到对象存储；不得先转 PDF 再解析。
- 解析失败的 XML 进入异常池，保留原始文件，不得删除。

### 5.3 模块 B：查验与查重

- 对接税局查验能力或合规第三方通道，校验真伪、状态、红冲关系。
- 查重：以 invoice_number + issue_date + seller_tax_id 为业务唯一键硬性判重；辅以票面关键字段相似度作为软性预警。
- 查验结果结构化记录，不能只存“已验证”标记。

### 5.4 模块 C：业务匹配与四流一致性校验

四流合一应实现为多源数据一致性校验，而非人工判断。

| 校验维度 | 规则 | 容差/窗口 |
|---|---|---|
| 主体一致 | 合同卖方=发票销方=资金收款方；合同买方=发票购方=资金付款方 | 精确匹配 |
| 金额一致 | 发票价税合计与业务单据金额差异在容差内 | 默认0.01元，可配置 |
| 时间有序 | 业务发生时间 ≤ 开票时间 ≤ 入账时间，且开票与业务时间差在窗口内 | 默认30天窗口 |
| 内容一致 | 发票明细与业务单据标的映射校验 | 按品名映射表或人工兜底 |

输出 MatchResult：通过则推进，不通过进入异常池并标注断点维度。

### 5.5 模块 D：入账与用途确认

- 入账接口支持同步/异步双模式。同步即时返回；异步返回请求ID，通过查询或回调获取结果。
- 入账前必须校验：ticket_status=NORMAL、未被红冲锁定、查重通过、业务匹配通过。
- 入账成功后回写 voucher_number、accounting_period，并写 PostingRecord。
- 用途确认需记录确认结果和所属期，与 usage_status 联动。

### 5.6 模块 E：红冲处理

- 监听或接收红冲锁定和红字发票通知，触发状态变更和后续阻断。
- 已入账发票红冲，记录《红字发票信息确认单》编号和确认结果。
- 72小时确认时限需系统提醒，但不得由系统自动替用户确认。

### 5.7 模块 F：归档封装

归档必须生成不可变 ArchivePackage，包含：

1. XML 原件，必选；
2. 结构化数据文件，按标准组织；
3. 业务关联快照，归档时刻只读快照；
4. 四性检测结果：真实性、完整性、可用性、安全性；
5. 审计元数据：归档时间、操作人、哈希值、版本号。

归档后 ArchivePackage 不可修改。后续状态变化作为增量事件追加，不覆盖已归档内容。

## 6. 接口设计约束

### 6.1 与税局/第三方平台对接

| 约束 | 要求 |
|---|---|
| 异步优先 | 批量下载、入账、用途确认等耗时操作设计为异步任务，返回任务ID，轮询或回调获取结果 |
| 幂等键 | 所有写操作必须接受幂等键，建议用 invoice_number + operation_type 或外部请求ID |
| 限流与重试 | 重试仅针对瞬时失败，必须结合幂等键；业务失败不得重试 |
| 回调验签 | 回调必须验证签名/来源，回调处理本身也必须幂等 |

### 6.2 与 ERP/OA 对接

- 入账接口由本系统主动调用 ERP，或 ERP 调用本系统。无论方向，invoice_number + voucher_number 必须双向可回查。
- 业务匹配所需外部单据字段以接口获取或定期同步为准，不允许在发票系统中手工虚构业务单据信息。

### 6.3 文件存储

- XML 和版式文件使用对象存储，数据库只存 object key 和哈希值，不存文件二进制。
- 临时文件必须加密、限期、隔离，任务完成后及时清理。
- 归档包使用写一次读多次存储策略，归档后禁止覆盖。

## 7. 校验规则清单

以下规则应实现为可配置规则引擎，而非硬编码。

### 7.1 硬性拦截，阻断流程

| 编号 | 规则 |
|---|---|
| R01 | XML 原件缺失或哈希校验失败 |
| R02 | 发票号码格式非法或销方税号缺失 |
| R03 | 业务唯一键已存在且状态非作废 |
| R04 | 发票状态为 RED_LOCKED 或 RED_ISSUED 时，禁止入账/确认 |
| R05 | 入账请求对应发票尚未完成查验 |

### 7.2 告警/人工确认，不阻断但进入异常池

| 编号 | 规则 |
|---|---|
| W01 | 查重相似度超阈值但业务唯一键不完全一致 |
| W02 | 四流校验中金额在容差内但主体或时间维度不一致 |
| W03 | 发票连号：同一销方连续号码多张进入同一报销单 |
| W04 | 销方名称/税号命中黑名单或敏感词库 |
| W05 | 跨期报销：开票日期与提交日期间隔超过配置阈值 |

## 8. 归档与非功能要求

### 8.1 归档规则

- 归档触发条件可配置，如入账后自动归档或审批完成后归档。
- 归档前执行四性检测，检测结果纳入 ArchivePackage；不通过则 archive_status=异常，不得标记已归档。
- 归档后提供穿透查询：从发票号码反查业务单据、审批记录、付款回单、会计凭证和 XML 原件。

### 8.2 安全与审计

| 要求 | 落地方式 |
|---|---|
| 操作日志 | 登录、查询、新增、修改、审批、归档、配置变更记录操作人、时间、IP、内容，保存不少于6个月 |
| 权限最小化 | 采集人员不可修改入账状态；审批人员不可删除归档包；财务人员不可绕过校验直接标记已入账 |
| 敏感数据 | XML 中银行账号、个人身份信息等加密存储或脱敏展示 |
| 防篡改 | 归档包使用哈希链或数字签名；关键状态变更由 StateEvent 追加记录，不允许物理删除 |

### 8.3 性能与可观测性

- 采集解析任务支持水平扩展，单张发票解析不阻塞批量任务。
- 异步任务必须有状态查询接口和失败告警，不能出现提交后无下文。
- 核心链路每一步埋点，支持按发票号码追踪全链路耗时和异常节点。

## 9. 研发对齐与分阶段交付

| 阶段 | 范围 | 验收标志 |
|---|---|---|
| P0 数据基座 | 数据模型 + XML 原生采集/解析 + 状态机 + StateEvent 审计 | 任一发票状态变更可完整追溯；XML 原件与结构化字段一一对应 |
| P1 合规闭环 | 查验查重 + 入账/用途确认接口 + 红冲状态联动 + 归档包生成 | 已入账发票被红冲时系统能正确阻断并记录；归档包含齐备5类内容 |
| P2 证据链 | 四流一致性校验引擎 + 业务匹配 + 异常池 + 穿透查询 | 可从发票反查任意关联业务单据和凭证；四流断点可归因 |
| P3 规模化 | 批量异步任务、限流重试、性能优化、规则引擎可配置化 | 批量采集和入账在可接受时延内完成，异常不累积 |

## 10. 一句话对齐

这个系统本质上是“以 XML 原件为起点、以状态机为骨架、以证据链为输出”的发票数据基础设施，而不是一个“上传发票填报销单”的表单工具。

数据模型和状态机先行，后续所有功能都在这个骨架上生长。研发如果只能先做一件事，先把以下四样做对、做扎实：

1. Invoice
2. InvoiceField
3. StateEvent
4. XML 原件存储与哈希校验
