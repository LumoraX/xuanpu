# 玄圃主动业务助理设计

> 2026-10-20 修订：按用户确认，主动业务由 LLM 理解上下文、识别待跟进事项；规则与调度提供可靠执行底座。本文为实现目标；2026-10-20 已进入代码实现与验收，实际发布状态以部署回执为准。

## 目标与首期边界

玄圃是企业核心。主动助理持续关注用户已经表达的目标、承诺、等待结果和业务进展，主动发现需要处理、需要核实或缺少安排的事情，提供下一步并跟进结果。LLM 参与业务理解与判断，规则负责时间计算、权限、状态核验、调度和去重；系统不能只在用户建好待办或提醒后才工作。

首期读取用户有权访问的玄圃主对话、关联业务会话和本人工作区。确定性检查首先覆盖 `workspace_item.kind=todo`，语义识别同时覆盖尚未转成待办的对话承诺：

- 有截止时间的开放待办：截止后识别为逾期，分阶段提醒。
- 没有截止时间的开放待办：按最后一次有效变更时间识别为长期未处理。
- LLM 识别对话中的明确承诺、时间意图、等待结果，以及结合内容可能已经拖延的工作；发现后向用户核实或提出安排，不要求用户预先配置业务或填写密钥。
- 日程与事项可作为判断上下文；没有权威结果时不认定会议缺席、业务未完成或外部人员没有回复。
- 系统可以提出下一步建议，但不会未经确认提交报销、发送外部消息或修改企业业务数据。

“短期应完成但长期未完成”包括用户明确约定的短期目标、对话中表达的相对时间，以及模型根据工作内容提出的合理跟进建议。明确承诺与推测必须分开保存和展示；例如“下午发报价”有明确时间意图，“发一份报价通常很快”只能作为询问依据，不能据此宣告逾期。

## 主动业务闭环与 LLM 职责

业务闭环为：观察变化 → 理解目标与进展 → 识别需要关注的事项 → 核实最新状态 → 提醒或准备下一步 → 接收用户决定 → 跟进结果。没有发现需要处理的事情时保持安静。

### 触发与上下文

- 对话产生新承诺、任务或业务状态变化时，创建持久化语义评估任务；低频后台复查负责用户不在线时的跟进。
- 确定性时间扫描仍每 60 秒执行；LLM 默认每用户每 30 分钟至多一次批量评估，事件触发与到期复查共用预算并合并重复请求。该频率是实现默认值，管理员配置，普通员工无需配置。
- 只读取本租户、当前用户有权访问的记录、关联消息和业务状态；按更新时间分页并保存消息游标。每次上下文最多 100 条记录、32 KiB 文本，记录截断情况。缺少相关上下文时给出待核实结论，不能把未读取的资料描述成已检查。
- 周期复查只装入已到 `next_review_at` 的跟进记录和增量变化，不反复把全部历史发送给模型。进程重启后从持久游标、租约与下次复查时间继续。

### 结构化判断与证据

LLM 输出经服务端严格校验的候选：`intent_type`（承诺跟进、等待结果、可能停滞、缺少时间安排）、`evidence_refs`（消息/工作区/业务记录及版本）、`reason`、`certainty`（明确记录或推测）、`proposed_time`、`next_review_at`、`suggested_action`。引用必须指向传入模型且用户有权读取的真实记录；禁止凭空生成业务对象、完成状态或授权。

服务端在发送前重新核实员工状态、访问权限、任务最新版本和用户已作出的处理。事实与推测使用不同表达：系统确知待办仍为开放状态时可以说明“待办尚未标记完成”；仅缺少完成记录时询问“这件事完成了吗”，不能断言用户没有做。模型输出本身不能创建企业业务事实或触发外部业务变更。

### 跟进记录与决策

新增 `proactive_followup`，保存租户/用户、稳定事项 ID、来源消息与记录版本、意图、证据、判断理由、明确/推测标记、建议时间及其来源、下次复查时间、最近通知、用户决定与审计。状态为 `candidate`、`awaiting_user`、`waiting`、`resolved`、`dismissed`；worker 的执行状态和租约独立保存，不与业务状态混用。

- 有待办的跟进以待办 ID 关联；没有待办的承诺以来源消息 ID 和承诺片段序号建立稳定键。模型不能自行决定去重键。新对话可以补充证据或在用户确认后关联同一跟进。
- 同一跟进、同一证据版本和同一阶段只通知一次；有待办的语义候选与确定性检查合并成一个关注事项。语义建议同一事项至少间隔 24 小时，只有明确新进展或用户指定跟进时间才可提前。
- 模型的置信判断不能单独开启自动业务执行。证据不足只提出简短问题；无可操作建议则不发送提醒。
- 发现缺少时间或提醒安排时，给出一个可修改的建议；用户确认后通过既有工作区/提醒服务设置，转为 `waiting` 并保存下次复查时间。
- 用户说“完成了”“改到周五”“不用再跟进”时，解析为带证据和版本的动作建议，沿用平台确认与审计规则更新状态。完成或忽略后停止相应跟进；延后后等待新时间，不能继续按旧判断打扰。
- 系统可主动执行已授权的只读查询、准备草稿和材料；提交报销、发业务消息、写企业数据等动作遵循现有业务权限和审批，不能因后台触发而跳过。

### 运行与成本边界

语义任务使用持久租约、`attempts`、`next_attempt_at`、`claim_token` 和输入版本指纹；模型调用在数据库事务外执行。结果提交时重新校验输入版本，过期判断丢弃并安排新一轮，不发送旧状态提醒。模型调用沿用平台现有适配、租户预算、配额、用量审计和可取消超时，不新增另一套模型密钥或执行引擎。

模型错误、超时、无预算或输出不合规则记录明确状态并退避重试，不伪造语义检查成功。规则提醒仍可独立运行；通知必须标明来自明确时间规则还是上下文判断。对话、附件和外部文档属于待分析数据，其中的指令不能变成后台执行授权。

## 判定规则

### 有截止时间的逾期待办

只检查 `status=open` 且 `due_at` 已存在的待办。以待办的 `due_at` UTC 时间戳和用户设置中的 IANA 时区计算经过时间；阈值是绝对 elapsed duration，不按服务器本地日历计算，因此不受夏令时跳变影响。

- 到达截止时间：阶段 `overdue_due`，生成一次提醒。
- 逾期 1 小时：阶段 `overdue_1h`。
- 逾期 1 天：阶段 `overdue_1d`。
- 逾期 3 天：阶段 `overdue_3d`。

每一阶段最多生成一条主动检查通知。标记完成、删除或归档后立即停止；延后会推进工作区版本、关闭旧检查代际并按新 `due_at` 重新计算。

### 没有截止时间的长期未处理待办

只检查 `status=open` 且 `due_at` 为空的待办。新增 `last_progress_at` 表示有证据的业务进展，首次值为创建时间；用户确认进展、调整完成目标、重新打开已完成待办时更新，单纯读取、改标题/标签/格式不重置。保留 `updated_at` 负责版本并发与上下文增量读取，不能把修改元数据视为完成进展。旧数据首次迁移以创建时间为依据并标记进展未知，首轮只提出核实，不声称确知业务停滞。

- 连续 3 天无变化：阶段 `stale_3d`。
- 连续 7 天无变化：阶段 `stale_7d`。
- 连续 14 天无变化：阶段 `stale_14d`。

阶段使用绝对 elapsed duration。用户选择忽略后，本阶段不再提示；业务进展或目标发生变化、进入新阶段后按规则评估。`generation` 改为跟进目标代际：截止时间、完成状态、有效进展或重新开启发生变化时推进；普通元数据更新只推进 `item_version`，不能重建相同阶段再次催办。阶段以稳定的 `stage_index` 表示，阈值快照写入检查记录。回收的待办不扫描；恢复时重新核实当前进展，不把恢复操作当成已开展业务。

## 持久化模型

新增迁移表 `proactive_check`，至少包含：

- `tenant_id`, `user_id`, `item_id`；
- `generation`：跟进目标代际，独立于 `item_version`，只在目标、完成状态或有效业务进展变化时推进；
- `check_type`：`overdue` 或 `stale`；
- `stage_index`：从 0 开始的稳定阶段序号；
- `threshold_seconds`：本代采用的固定阈值快照；
- `basis_at`：本阶段的依据时间；
- `item_version`：候选快照对应的工作区版本；
- `status`：`open`, `notified`, `ignored`, `resolved`, `failed`；
- `first_seen_at`, `notified_at`, `handled_at`；
- `attempts`, `next_attempt_at`, `lease_until`, `claim_token`, `last_error`；
- `created_at`, `updated_at`。

唯一键为 `(tenant_id,user_id,item_id,generation,check_type,stage_index)`。工作区每次变更推进版本；目标/进展改变时在同一协调事务中推进代际并关闭旧代检查。完成、回收会关闭当前检查，恢复后核实再续接。通知仍保留为历史记录，不因检查关闭而删除。扫描时重新读取并锁定待办，确认版本、状态和时间仍匹配后才写入检查记录。

新增 `proactive_scan_state`，主键为 `(tenant_id,user_id)`，保存 `round_id`、`last_item_id`、`updated_at`。到达末页时开启新的 `round_id` 并清空游标；候选锁定失败不推进游标。

扩展现有 `notification` 表而不新建第二个通知流：`reminder_id`、`due_at` 改为可空，增加 `source`（`reminder`、`proactive_check` 或 `proactive_followup`）、`proactive_check_id` 可空、`proactive_followup_id` 可空、`body` 可空，保留现有数据库序列 `notification_id` 作为用户范围内的全局单调游标。所有通知写入者在分配序号到提交期间持有用户行锁，防止晚提交造成游标漏读。来源与关联 ID 通过 CHECK 与租户/用户复合外键约束互斥一致。规则通知以检查 ID 唯一；语义通知以跟进 ID、证据版本和阶段唯一；正文上限 4000 字符。现有提醒通知保持 `source=reminder`。`/v1/notifications` 和 SSE 继续使用同一个 `notification_id` 游标，返回来源、正文、关联 ID 和投递状态，前端不需要合并两个接口。

现有 `notification_delivery.notification_id` 外键继续复用。主动检查发送使用相同的 `notification_id`、租约、重试字段和 Feishu 幂等 key；发送正文从 `body` 读取，`due_at` 为空时不生成原定时间行。这样外部渠道仍只有一套投递状态和租户/用户隔离。
## 后台协议与并发

新增 `ProactiveCheckStore`，禁止通过 HTTP 入口或伪造员工 Principal 读取工作区。后台查询必须显式带 `tenant_id,user_id`，只枚举 active tenant 和 active user；停用时关闭未处理检查并取消未发送外部投递。

新增 `ProactiveCheckWorker`，与现有 `ReminderWorker` 一样由应用生命周期启动和关闭：

1. 每轮按租户、用户分页读取候选，批次上限 100，并使用 `proactive_scan_state(tenant_id,user_id,round_id,last_item_id)` 的稳定 `(tenant_id,user_id,item_id)` 游标继续扫描；到达末页后开启新 round 并清空游标，避免大租户饥饿。
2. 用 `FOR UPDATE SKIP LOCKED` 或等价租约 claim 候选；锁顺序固定为租户 → 用户 → 工作区项目 → 检查记录，和工作区写事务一致。扫描 claim 失败不推进游标，下一轮从原位置重试。
3. 在短事务内重新校验版本、状态、`due_at`、`last_progress_at`，插入或更新 `proactive_check`，必要时创建 `notification` 和 `notification_delivery`，并推进扫描游标，然后提交。
4. `proactive_check` 保存 `attempts`、`next_attempt_at`、`lease_until`、`claim_token`、`last_error`；数据库错误不推进游标，候选按 1/5/30 分钟退避，超过 5 次进入 `failed` 并保留人工可重试入口。
5. 不在事务内调用模型或外部网络。外部发送沿用 `notification_delivery` 的 lease、最多五次可重试和幂等 key；站内通知写成功不受飞书失败影响。
6. 规则检查可使用确定性模板直接落库；语义检查必须有通过验证的模型结果，模型失败不能以模板代替业务理解并宣称检查成功。

主动检查每 60 秒扫描一次；这不是硬实时承诺。服务重启、扫描中断或多实例并发后依靠持久记录、锁和唯一约束恢复。

## 用户动作与接口

通知和对话建议卡展示：事项标题、检查类型、阶段、依据时间和操作入口。动作均带 `request_id` 与 `expected_item_version`。新增 `WorkspaceCheckCoordinator`，与 WorkspaceService 共用同一数据库事务和锁顺序，在一次事务内完成工作区更新、旧 generation 关闭、新 generation 创建和动作审计；内存实现使用同一把用户锁。通过现有工作区/提醒服务执行并记录审计：

- `open`: 打开待办详情，不改状态；
- `complete`: 将待办改为 `done`，检查标记 `resolved`；
- `postpone`: 写入新的 `due_at`，关闭旧代并创建新代；
- `set_reminder`: 复用 `ReminderService`，仍需用户确认提醒时间和渠道；
- `ignore_stage`: 将当前检查标记 `ignored`；
- `ignore_type`: 用户设置中关闭同类主动检查，可设置过期时间。

版本冲突返回 409，前端重新读取待办和检查状态；同一 `request_id` 重放返回第一次结果，不重复写入。

## 用户设置

扩展 `SettingsData`，向后兼容缺省值；首期阈值固定，不开放用户自定义阶段，避免阶段语义漂移：

```json
{
  "proactive_checks": {
    "enabled": true,
    "quiet_hours": {"enabled": false, "start": "22:00", "end": "08:00"},
    "ignored_types": [{"type": "stale", "until": 1793462400.0}]
  }
}
```

`ignored_types` 使用对象数组，`until` 为 UTC 秒时间戳，可为空表示持续忽略；由用户重新开启或到期恢复，修改某条待办不能撤销用户关闭同类提醒的选择。类型包括规则检查和语义跟进类型。IANA 时区来自用户设置，免打扰按该时区解释并支持跨午夜；免打扰只延迟网页浮层和外部投递，通知仍立即写入玄圃并保持未读。关闭主动检查后不创建新检查；重新开启时只评估当前阶段，每个待办最多补发一条当前阶段通知，不补发历史阶段，避免通知洪泛。

## 通知、模型与渠道

玄圃通知中心是权威结果。网页通过同一个游标接口补读定时提醒、规则检查和语义业务跟进，来源字段说明判断依据；对话是处理问题与反馈结果的主入口，模块页保留查询和操作兜底。网页打开时按免打扰设置显示右侧浮层，关闭网页后通知仍持久保存。

LLM 负责上下文理解、遗漏识别、判断是否需要核实以及提出下一步。系统负责对这些判断进行证据校验、权限检查、频率控制和可靠投递。飞书是可选出口，沿用已有投递状态和重试；飞书失败不撤销玄圃通知。

## 验收

1. 有截止待办在截止、1 小时、1 天、3 天四个固定阶段各最多一条通知；重复扫描、服务重启、多实例并发均只产生一条。
2. 无截止待办在 3 天、7 天、14 天无业务进展阶段各最多一条通知；标题、标签或格式更新不重置业务进展时间，不引发重复催办。
3. 标记完成、删除、归档后不再检查；延后后旧代停止，新 `due_at` 重新计算。
4. 忽略当前阶段后不重复提示；进入新阶段或跟进目标代际变化后按规则恢复检查，单纯 `item_version` 变化不能解除忽略。
5. 版本冲突返回 409；同一 `request_id` 重放不产生第二次动作。
6. 关闭主动检查不生成新检查，已有未读通知仍可查看；免打扰期间延迟投递但不丢失。
7. 停用租户/员工后不产生新检查，外部 delivery 被取消或标为 skipped；重新启用不跨租户读取数据。
8. 数据库重启、扫描中断、批次超过 100 条、游标继续扫描后最终覆盖全部候选。
9. 用户时区跨 DST 时，绝对 elapsed duration 不重复也不跳过阶段。
10. 站内通知写入成功但飞书发送失败时，站内仍可见，delivery 状态可重试。
11. 全量 `pytest`、Ruff、mypy 通过，并在部署环境完成一轮真实短期逾期检查。
12. 仅在对话中说“下午把报价发给客户”、未创建待办或提醒，系统仍能识别承诺、保存真实消息证据并主动核实结果。
13. 缺少完成记录时询问是否完成；关联业务已经完成、用户撤销目标或已明确结束跟进时，不再发送过期判断。
14. 无截止的短期工作能得到附依据的跟进建议；模型推测不能变成真实截止时间、已完成或未完成事实。
15. 用户为缺少安排的承诺确认提醒后，保存下次跟进时间并等待；重启后继续，确认重放不重复创建任务。
16. 同一待办同时被规则与模型命中只产生一条关注事项；多个 worker、重复模型结果和 metadata 更新不重复通知。
17. 模型超时、预算耗尽、截断上下文、非法引用、提示注入和跨租户证据均不会产生伪造业务结论；有独立规则的提醒仍运行。

## 后续扩展

日程出席和外部业务完成结果需要明确的数据来源与同步契约；语义跟进可提出核实问题，但不能凭模型推测写成这些业务事实。更多业务包可通过既有只读连接器提供进展证据，在玄圃权限与审计下接入同一主动业务闭环。
