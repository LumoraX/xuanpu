# 玄圃能力规划建议稿

- 日期：2026-10-20。
- 状态：用户于 2026-10-20 确认按本规划推进，首期服务企业日常办公与业务协同。2026-10-25已推进至R4详细规划；各阶段实现、部署与真实业务验收分别记录。
- 定位：玄圃承载企业身份、规则、流程、权限、工作状态和审计；每个员工通过自己的助理完成工作，部门通过岗位助理协作。
- 成功标准：员工交办的事情有负责人、执行状态和可检查的结果；员工离线后，已授权工作持续推进，关键决定回到有权的人手中。

## 一 路线选择

| 路线 | 收益 | 代价与局限 |
| --- | --- | --- |
| 企业日常办公与业务协同优先，推荐 | 复用已有身份、工作区、事项、提醒与审批基础，直接形成员工可用的任务闭环 | 需要先接通执行、数据授权和持久任务，界面功能增加不会替代这些工作 |
| 研发与通用编程优先 | 文件、终端、代码导航等能力容易与通用 Harness 对照 | 编程工具投入较多，不能直接验证企业协同价值；作为后续能力包推进 |
| 单部门垂直业务优先 | 容易确定业务规则和结果验收 | 依赖具体部门流程及数据，过早实施会让通用平台被单一业务绑定；在基础闭环之后选择一个试点 |

首期采用第一条路线。DeepSeek Harness 用于参照执行环境、能力组合和开发者体验。玄圃的交付顺序按员工任务和企业协同价值确定。

## 二 员工应该获得的体验

员工默认进入对话，直接表达目标、补充材料、查看结果并作决定。独立“功能”入口保留文件、事项、待办、日程、提醒和审批的直接操作，与对话共用数据和权限。模型不可用时，必要的业务操作仍可完成。

一次交办可以跨多次对话、多个工具和多个执行者。员工能看到它正在处理、等待谁、缺少什么、产出了哪些文件；切换页面或关闭浏览器不导致已受理任务消失。

员工回来时看到与自己有关的变化：完成的成果、等待本人确认的操作、交出去的事项进展和需要处理的问题。没有实质变化时保持安静。普通员工不需要选择业务包、填写模型密钥或了解沙盒与内部工具。

首期围绕四个场景验收：

1. 把本人上传的会议材料整理为纪要和行动项，确认后创建待办与日程，成果文件保存到个人空间。
2. 把一组办公表格整理为汇总表和周报，保留输入版本、计算依据及输出文件；失败可定位并续办。
3. 跟进“今天下午把报价发给客户”这样的明确承诺，到期核实进展；缺少完成证据时询问，不擅自认定未完成或代发报价。
4. 把事项交给另一个员工或部门，接收方能接受、退回和补充材料；发起人能看到真实进展与结果。该场景在协同阶段完成。

## 四 平台中的核心对象和事实来源

企业身份、组织、能力授权、连接、事项、任务、审批、交接、文件引用、通知和审计应使用稳定标识。会话是工作入口与交流记录，任务保存执行状态，事项汇集目标、参与者、任务与成果；三者不混用。

平台持久任务至少保存：租户、负责人、实际执行身份、触发来源、目标、输入引用与版本、能力版本、授权依据、预算、执行尝试、当前状态、产出及结果回执。一个任务可经历多轮内核执行，不能直接把单次 `turn_completed` 当作整件事完成。

任务状态建议统一为待处理、执行中、等待本人、等待他人、成功、失败、已取消，以及结果待核实。工具执行成功、通知已生成、外部请求已发送分别记账。外部系统可能已执行但响应丢失时，进入结果待核实，先查询或人工核对，不能自动重发非幂等写操作。

玄圃拥有企业工作规则、授权决定、编排状态及审计。每个外部集成仍须声明字段或对象的权威来源、同步方向、稳定映射、冲突处理及迁移方式。外部财务账本、邮件或文档正文可留在原系统；玄圃保存经授权的引用、版本和操作回执。不能把“统一入口”误作所有外部数据已经同步成功。

| 对象 | 归属与同步原则 |
| --- | --- |
| 企业身份与组织 | 玄圃稳定身份为引用中心；按来源规则接收或发出变更，同一字段不能无条件双向覆盖 |
| 事项、任务、授权、交接与流程实例 | 玄圃保存权威状态；外部消息与门户是展现或通知出口 |
| 文档、邮件、业务单据及账本 | 由集成契约明确权威系统；跨系统通过引用和经确认的变更协作 |
| 通知投递 | 站内通知、外部渠道送达与用户已读分开；发送失败不能改写业务结果 |

财务、报销、合同等领域模块独立设计规则和记录，通过平台权限、流程及进程外扩展接入。业务数据模型不进入泰逢内核；平台也不直接加载业务方代码。

## 五 贯穿能力的执行约束

授权分为读取、草拟、提交和持续执行的范围。首期沿用现有确认规则；读取外部内容后的对外操作继续要求本人确认。持续授权的范围、时效和撤销另行设计，不能通过个人 skill、后台触发或模型判断绕过既有权限。

每次执行及后台唤醒时重新检查员工状态、权限、连接令牌、输入版本和预算。停用员工后取消或移交持久任务，撤销令牌并保留审计。等待审批期间输入发生变化时，按变更是否影响操作重新确认；旧确认不能授权变更后的写操作。

企业审批和个人确认分别记录。个人确认只能代表本人同意，不能替代财务审核或部门审批。确认、执行和回执使用稳定操作标识，重复点击、网络重试及进程恢复不得重复提交已经核实成功的操作。

生产执行空间按租户、员工和事项划定访问范围；共享依赖显式授权。文件、进程和网络执行遵循同一身份和隔离策略。文件产出写回经过版本与路径检查，记录来源和变更。终端、浏览器和后台任务均受取消、超时、资源和清理策略约束。

主动助理由模型理解上下文、提出候选判断；服务端核实证据、状态、权限和版本。明确承诺与推测分别保存，未知结果用“待核实”表示。确认完成、忽略或调整时间后更新跟进状态；相同证据和阶段不反复通知，缺少可操作变化时保持安静。

管理员默认查看运维和用量元数据。个人正文访问应按既有隐私目标收紧，例外调查需要独立授权和审计。知识索引、摘要、模型上下文和缓存继承源数据权限；分享、调岗、离职、撤权和删除均需验证传播效果。

## 六 交付阶段及验收

以下阶段号是本规划的交付顺序，引用既有 P0 至 P11 工作项，但不代表这些旧工作项已完成或被正式改写。各阶段按验收结果推进，工期在独立设计和资源确认后估算。

| 阶段 | 交付结果 | 依赖与验收门槛 |
| --- | --- | --- |
| R0 核清现状与加固基础 | 确认平台实际内核版本和稳定接口；收敛内容可见性、重复审批、取消与结果未知处理，确定受支持部署范围 | 单实例作为首期验收基线；多实例必须补写入持有权保护、跨实例配额及故障接管后单独验收。源码、安装依赖、镜像和实际部署分别记录 |
| R1 员工可以交办并取得成果 | 贯通个人空间、隔离执行、文件工具、结果写回和统一任务状态；助理按员工有权使用的能力办事 | 复用 P2、P3、P4、P5、P10 的基础。先支持平台内材料，不依赖员工外部授权。会议纪要和表格汇总场景可真实完成；浏览器断开后，服务进程仍存活时任务继续，重新进入能查到进展和成果。进程重启及执行中断恢复由 R2 验收 |
| R2 员工离线后工作继续推进 | 通用持久任务、时间与事件触发、重启续跑、工作动态；衔接已有主动业务与通知 | 复用 P9、主动业务实现及 R1 任务契约，保留已有承诺识别、安排与通知能力。新增已授权任务的后台执行与重启恢复，预算受控，外部写入不因重试而重复 |
| R3 企业数据与协同接通 | 员工连接授权、组织岗位、共享事项、部门助理、交接与组织审批；真实办公系统只读接入先行 | 复用 P1、P6、P11。R0 内容隐私约束是员工外部数据接入前提；R1 后可提前做连接契约和一个只读试点。跨部门交接完整通过接受、退回、补充、完成与签收 |
| R4 业务能力可复制交付 | 统一能力目录、到人及可选岗位分配、版本评测与回滚、知识治理、业务模块及运营面板 | 先选一项办公业务流程，直接到人且不要求部门，再扩大连接器和模块。每个能力有安装条件、权限声明、失败处置和业务验收；按能力、员工和场景统计，部门为已有组织下的可选维度 |

2026-10-25：用户暂缓真实员工验收，继续拆[R4详细实施计划](../plans/2026-10-25-r4-delivery.md)，设计见[R4交付治理](2026-10-25-r4-repeatable-capabilities-design.md)。R3已部署技术证据仍见[分层记录](../../guides/releases/2026-10-24-r3-acceptance.md)；真实员工待项暂缓，不补写为通过。R4规划不代表已实现或已经生产发布。

R0 在主线开始前建立范围和门槛；不必等全部运维增强完成才做 R1。主动助理的只读识别与通知可沿用现有设计先行推进，其后台业务执行依赖 R1、R2 的统一执行契约。多实例、跨租户和复杂业务不得以“后续补验收”方式混入首期完成范围。

第一批交付聚焦“会议材料变行动项”和“办公表格变成果文件”。两条路径共同验证附件、执行、审批、成果保存、浏览器断开后继续执行及重新进入后的可见结果；R2 再增加进程重启和执行中断恢复验收。同时验证基础直接操作在模型不可用时仍可完成。首期完成后再进入真实部门交接试点。

## 七 验收方式与效果衡量

每个场景用确定输入、预期业务结果和可核实回执验收。分别记录源代码与测试、真实模型、后台进程、浏览器、部署和真实外部系统证据，不能以接口 200、任务成功事件或截图替代整条业务链路。

重点故障场景包括：跨用户越权、身份撤销、过期审批、重复确认、外部写入超时、模型失败、浏览器关闭、进程重启、文件版本冲突、预算耗尽和取消过程中结果未知。多实例增加写入持有权丢失及并发接管验证。

| 指标 | 定义 |
| --- | --- |
| 任务完成率 | 满足预先定义业务验收且有结果证据的任务数 / 本轮预先冻结、满足运行前提的任务数；另报取消、阻塞、失败及结果未知 |
| 结果正确率 | 人工或确定性校验正确的结果数 / 实际抽检结果数，保留题目、输入版本与抽检范围 |
| 人工介入 | 每任务必要审批、缺失信息澄清与故障返工分别统计，避免用减少必要审批制造改进 |
| 成本与时延 | 每场景报告端到端耗时及分布、模型用量、执行成本和重试开销；审批等待单独列出 |
| 主动助理有效性 | 正确识别、错误提醒、重复通知、漏检分别统计；记录证据与评审依据，不只计算点击率 |
| 恢复与一致性 | 已承诺恢复的故障场景中恢复成功的数量，以及重复外部写入、状态丢失和跨用户泄露事件 |

首轮先建立固定场景和基线，再据真实样本确定成功率与成本目标。不凭能力清单给出“已达到 DSH 百分之几”的结论。

## 八 分层与后续设计单元

泰逢继续负责循环、上下文、技能调度、工具、取消、挂起恢复和代理通信的通用机制。沙盒与存储适配包实现不含租户业务概念的协议。玄圃负责身份、组织、权限、能力交付、事项、持久任务、流程、协同、连接授权、治理与产品入口。

扩展统一为能力包、连接器和受控工具的声明与生命周期，安装、版本、配置、权限和评测可组合。保留业务扩展进程外的边界；不因参照 DSH 而引入租户任意代码在平台进程内运行。

后续按以下单元分别出契约和实施计划，每个单元能独立验收：

1. 运行版本、任务与操作回执契约，以及首期部署与权限加固清单。
2. 员工执行空间、文件输入输出和成果保存。
3. 岗位能力组装与个人能力的安全边界。
4. 持久任务、触发与恢复；主动助理复用既有设计，核对与该任务契约的衔接。
5. 员工连接授权、撤销和一个真实只读集成。
6. 组织、共享事项、部门身份、交接与审批。
7. 业务能力交付、知识治理及首个部门流程试点。

R0、R1 的设计先行。详细技术选型以现有机制和成熟组件评估为前提，不在本规划中承诺另建调度、检索或工作流框架。
