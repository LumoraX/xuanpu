# R5-D：匠人编组设计

日期：2026-11-14。状态：待实施。上级：[R5 设计](2026-11-14-r5-butler-artisan-design.md)。依赖 R5-C。

## 1 目标

一件事需要多个匠人时，管家声明一个计划：谁并行、谁接力、谁会诊；平台按计划执行、收齐、裁决分歧，员工在概览里看到整组进展。

## 2 计划

管家用 `dispatch_group` 提交一份声明式计划，平台校验后执行；不是脚本。

```
plan:
  title
  steps: [ step ]
step:
  mode: parallel | relay | consult
  members: [ { artisan, brief, inputs } ]      # 1..N
  when: 可选，只允许引用前一步的终态（completed / failed）
```

| 模式 | 语义 | 收口 |
| --- | --- | --- |
| parallel | 成员各做各的一部分，互不可见 | 全部到终态后管家汇总 |
| relay | 前一个成员的成果引用作为后一个的输入 | 逐个进行，任一失败即停并上报 |
| consult（会诊） | 成员做同一件事或同一问题的不同角度，结果互相可见，可定向追问 | 全部表示完成后比对分歧再裁决 |

校验：成员数、总步数、每成员匠人须在本人当前可用清单内、材料归属、预算。计划固定后不可改；调整须提交新修订，旧修订保留在 trace 里。

## 3 执行

- 每个成员是一次独立派工（R5-C 的执行），各有自己的沙盒、凭据、闸门、审计与 span；编组是它们的父 span。
- 同一业务包内的并行可以由匠人自己用内核的 spawn 与等待完成；跨包并行由平台在任务层面做，不把多个包装进一个引擎。
- 接力传递的是成果引用与摘要，服务端复核下一个成员对该成果的读取资格；不传上一个匠人的内部过程。
- 成员需要本人确认的写入，照常变成对话里的确认卡，注明来自哪个成员。
- 取消编组会请求取消所有未终态成员；各成员按真实终态收敛。

## 4 会诊消息

- 编组有一块成员可见的消息区：只追加，成员可发结论、可 @ 另一成员提问；管家始终在场。
- 成员只能看到发到消息区的内容，看不到彼此的内部推理与工具结果。
- 追问有轮数上限；超限由管家收口。消息区内容是数据，不是指令。
- 第一步只做「各自给结论 → 管家比对」；成员互问放在第二步，实现上用平台持久消息加唤醒，不依赖两个引擎常驻。

## 5 分歧裁决

全部成员完成后：

| 分歧 | 处理 |
| --- | --- |
| 低（措辞差异） | 管家综合，注明依据的成员 |
| 中（评估不同） | 管家综合并明确列出不一致之处 |
| 高（结论矛盾，或涉及金额、对外、审批） | 交员工裁决，并排给出各成员结论 |

分歧度由模型比对得出，只用于决定走哪条路；最终交付里保留每个成员的原结论可查，不抹掉少数意见。

## 6 失败处理

成员失败不自动换人重跑。有外部效应且结果未知的成员先核实。部分成功按实际说明：哪些完成、哪些没有、整体是否仍可用。

## 7 上限

每编组成员数（默认 4）、每计划步数（默认 3）、每 trace 匠人总数与 token 沿用 R5-C；深度 1。

## 8 数据（拟）

`dispatch`、`dispatch_group`、`group_member`、`group_message`，均带租户与员工复合外键、`request_id` 幂等、版本号；与任务、会话用引用关联，不改既有严格 JSON 记录的读者。

## 9 验收

并行两匠人各自完成并汇总；接力中间失败即停；会诊三成员低、中、高分歧各走对路径；高分歧时员工能看到并排结论并裁决；成员撤权后该成员被拒而其余继续；取消后无成员继续产生副作用；重启续跑不重复派工；瀑布显示真实交叠。
