## 1. 目标、边界、检验标准

**目标**：企业接入自己的身份、数据和模型之后，员工在一个工作台里用管理员发布的 agent 应用完成工作；每一步都有闸门和审计；计算节点可以随便加。

**边界**（ADR 0009）：平台只做四件通用的事——身份、接入、文件、agent 运行与治理。只对某一类业务有意义的东西（报销单、合同、工单）不进平台，做成独立系统，像第三方一样经连接接入。

**检验标准**（ADR 0009）：员工打开工作台，能看到「我不在的时候，agent 已经替我做完了什么」。做不到这一条，就只是把文件从电脑搬到了服务器。

这条标准现有的八个子项目（P1–P8）覆盖不到，见第 12 节第 1 项。

## 3. 概念模型

```
租户 ──┬── 用户 ──┬── 登录会话
      │         ├── 外部身份（飞书 union_id）
      │         ├── 授权（对某个连接的员工令牌）
      │         ├── 个人空间 ── 文件 ── 版本
      │         │        └── 个人 skill（员工自己写的 SKILL.md）
      │         └── 会话 ── 一轮对话 ── 待办（审批）
      │                │
      ├── API key       └── 属于一个应用、钉住一个业务包版本
      ├── 密钥
      ├── 连接（飞书、Gmail、自建系统…）── 工具白名单与副作用分类
      ├── 业务包 ── 版本 ── 入口 skill ＝ 应用（展示信息随版本）
      │                      └── 上架与可见范围（不随版本）
      ├── 审计（只追加）
      └── 用量（按天；按用户；按应用）
```

| 概念 | 一句话 | 出处 |
| --- | --- | --- |
| 用户 | 企业员工。来自飞书，平台不自建账号密码 | ADR 0010 |
| 调用者 | 一次请求是谁发的：人（登录 cookie）、系统（API key）、系统代人 | P1 设计 |
| 应用 | 业务包的一个入口 skill，加上给员工看的展示信息 | ADR 0007 决策 3 |
| 连接 | 租户登记一次的外部系统。业务包按名字引用 | ADR 0007 决策 3、ADR 0009 |
| 授权 | 某位员工对某个连接的授权令牌。agent 代表谁工作就用谁的 | ADR 0009 决策 3 |
| 个人空间 | 员工自己的文件树。元数据在库里，内容在对象存储 | ADR 0009 决策 4 |
| 会话 | 某位员工在某个应用里的一条对话。创建时钉住版本 | 现状 + P1 |
| 待办 | 一轮对话停下来等人确认的操作。由发起会话的员工本人确认 | ADR 0007 拍板结果第 4 项 |
| 个人 skill | 员工自己写的 skill，放在个人空间里，只对自己的会话生效 | 本文 7.8（修订 ADR 0007 拍板结果第 5 项） |

「企业应用」的两层就是表里的**应用**（上层，给员工用）和**连接**（下层，接企业系统）。

平台仍按 ADR 0004 的四个平面组织。下表是「现有」与「本轮新增」的对照：

| 平面 | 现有（第一版） | 本轮新增 | 子项目 |
| --- | --- | --- | --- |
| 治理面 | 租户、API key、密钥保管库、业务包版本、配额、审计、用量、评测 | **身份**：用户、登录会话、停用流水线。**应用目录**：上架、可见范围。**连接与授权**：租户级连接、员工令牌保管与刷新 | P1、P2、P6 |
| 计算面 | 运行时组装、会话租约、事件枢纽、空闲回收 | 会话归属到用户；执行环境按用户隔离；停止生成；待办收件箱；个人 skill 进入会话；（建议）定时与事件触发 | P1、P4、P5、P10、P9 |
| 效应面 | 连接器闸门（MCP 进程、HTTP 接口）、沙盒脚本、模型调用 | 按员工注入令牌；**文件进出沙盒**（拷入、写回、变更审计）；**只读浏览**；外部内容进入会话后收紧审批 | P6、P4、P8 |

| 接入层 | HTTP 接口、Python 客户端、控制台、命令行 | 工作台、JavaScript 客户端；两种认证并存 | P5、P1 |

## 5. 贯穿全局的规则

每个子项目的设计都要对照这七条。前五条来自已有 ADR，后两条是本文补的（理由见第 12 节）。

| # | 规则 | 出处 |
| --- | --- | --- |
| 1 | **副作用都过闸门，都留审计。** 闸门依次是白名单、审批、调用、审计 | ADR 0004 |
| 2 | **凭据只以名字出现。** 明文只在出口的那一刻取出，不进提示词、日志、审计 | ADR 0004、0009 |
| 3 | **每条数据都有主人（租户，用户）。** 访问别人的数据一律按「不存在」处理 | 红线 5、P1 |
| 4 | **平台不加载业务方代码，不含垂直业务的数据模型** | ADR 0002、0009 |
| 5 | **只依赖内核稳定层** | 红线 3 |
| 6 | **外部内容一旦进入会话，对外的操作一律要本人确认。** 「外部内容」包括个人文件、以员工身份读到的邮件与文档、网页。这个标记随会话保存，只增不减 | ADR 0007 决策 5、ADR 0009 决策 3；实现方式见 12.4 |
| 7 | **员工的内容，管理员默认看不到。** 包括个人空间、会话正文、以员工身份读到的内容。管理员看得到的是元数据；看内容走取证通道 | 由 ADR 0007 拍板结果第 2 项推出，见 12.2 |

## 6. 主线流程

### 6.1 登录（P1）

```
员工 → 工作台 → 平台 /v1/auth/feishu/login → 飞书授权页 → 回调
平台：换令牌、取用户信息 → 按 union_id 找到或新建用户 → 发登录 cookie
```

细节见 P1 详细设计。登录拿到的飞书令牌用完即丢；读数据的授权是另一回事（6.2 第 2 步）。

### 6.2 员工让应用替自己办一件事（P2、P6、P3、P4 合在一起）

以「把上周的会议纪要整理成周报发给主管」为例：

```
1. 员工在应用中心打开「周报助手」
     └ 平台核对：应用已上架、对他可见                         （P2）
2. 应用要读飞书文档。员工还没授权 → 工作台提示去「连接」页授权    （P6）
     └ 飞书授权页 → 平台保管他的令牌（加密，绑定 租户+用户+连接）
3. 员工发消息，附上个人空间里的一份模板
     └ 平台把模板拷进他在这个应用下的沙盒目录                    （P4）
     └ 会话标记为「有外部内容」                                （规则 6）
4. 模型调用「搜索飞书文档」「读取文档」
     └ 连接器闸门：由会话找到员工 → 取他的令牌 → 注入请求         （P6）
     └ 读操作直接放行；审计记一条，只记摘要不记正文               （12.3）
5. 模型在沙盒里跑脚本生成周报文件
6. 模型调用「发送飞书消息」——对外操作，且会话里有外部内容
     └ 挂起，待办进入员工的「待我处理」                          （规则 6）
7. 员工确认 → 续跑 → 消息发出，审计记下「谁批准、用谁的令牌、发给了谁」
8. 这一轮结束：平台比对沙盒目录，把周报作为新文件写回个人空间，
   逐个文件记审计                                           （P4）
```

### 6.3 员工离职（P1 牵头，P3、P6、P9 各挂一个动作）

```
飞书离职事件（或每日对账）→ 停用流水线：
  1. 用户标为停用，删除全部登录会话                 （P1）
  2. 关闭他名下的会话                             （P1）
  3. 撤销他在所有连接上的授权，删除令牌              （P6）
  4. 个人空间冻结，保留 90 天，可移交               （P3）
  5. 停掉他的定时与触发任务                        （P9）
```

第 2–5 步都是挂在 P1「员工停用」通知点上的监听者，各自可重复执行。兜底规则在运行时：主人已停用的会话，谁也不能再推进。

### 6.4 员工不在的时候（建议新增，P9）

```
触发（定时，或连接上的事件）→ 以这名员工的身份开一轮对话
  ├ 只读的事直接做完
  ├ 要对外的事停在待办里
  └ 结果进入「动态」：做了什么、产出了哪些文件、有几件事等他确认
员工回来 → 工作台首页先看动态和待办
```

### 6.5 员工把自己的做法沉淀成 skill（P10）

```
员工在工作台「我的 skill」里新建：名字、一句话说明、给模型的指令、可以调用的其他个人 skill
     └ 平台生成 SKILL.md，存进个人空间 /skills/<名字>/，校验、记审计
之后在允许个人 skill 的应用里对话：
     └ 组装这名员工的执行环境时把他的个人 skill 一并装进去
     └ 模型按需调用；审批、预算、审计与应用自己的 skill 完全相同
```

## 7. 各个域

每个域是一个子项目，单独出详细设计。这里只定：它负责什么、和别的域怎么接、哪些已经定了。

### 7.1 身份（P1）

已有详细设计和 ADR 0010，本文不改动，只补两处与其他域的接口：

- 「员工停用」通知点是全系统的收口（6.3）。P3、P6、P9 的设计都要写明自己挂的监听者做什么。
- 会话可见性要在 P6 落地前收紧，见 12.2。

### 7.2 应用目录（P2）

| 项 | 设计 |
| --- | --- |
| 应用是什么 | 业务包的一个入口 skill |
| 展示信息 | 名称、图标、简介、分类、示例提问。写在清单里，随版本发布 |
| 上架与可见范围 | 存在控制面，不随版本变。可见范围是全员或指定的飞书部门、用户组 |
| 组从哪来 | 飞书。平台不维护组织架构，只缓存「这名员工属于哪些组」，登录和对账时刷新 |
| 校验 | 建会话时核对可见性；看不到的应用按不存在处理 |
| 用量 | 在按租户、按用户之外，加上按应用的维度 |

清单新增的字段是可选的，已发布的包不受影响（规范仍是 `xuanpu/v1`）。

### 7.3 连接与员工授权（P6）

这是「数据都在线」的第一步，也是风险最集中的一块。

**连接**是租户级资源，由管理员登记一次：

| 字段 | 说明 |
| --- | --- |
| 名字 | 业务包按它引用 |
| 传输 | HTTP 接口（按 OpenAPI 描述）、MCP 进程、远端 MCP（内核新开放，见第 8 节） |
| 凭据方式 | **企业凭据**：管理员配一次的服务账号。**员工授权**：每位员工自己授权 |
| 授权应用 | 员工授权时用的客户端标识、密钥引用、授权地址、权限范围 |
| 工具 | 白名单；每个工具的副作用分类；读到的内容是否算外部内容 |

**预置的连接模板**：飞书和 Gmail 各一份接口描述的子集，随平台发布。它们是数据，不是代码。租户登记连接时选模板、填自己的授权应用即可。

**授权**按（租户，用户，连接）保管令牌：

- 加密方式与现有的密钥保管库相同，附加认证数据换成「租户 + 用户 + 连接」；
- 到期自动刷新；刷新失败就把授权标为失效，下一次调用返回「需要重新授权」；
- 员工随时撤销，立即生效，进行中的对话也拿不到令牌；
- 员工在「连接」页能看到「agent 用我的授权做过什么」。

**调用路径**：连接器闸门由会话找到员工，再取他的令牌。没有员工的会话（系统用 API key 直接建的）调用员工授权的工具，直接失败并说明原因。

**业务包怎么用**：清单里按名字引用连接，并声明要用哪些工具。现有的「在包里直接声明连接器」的写法保留。发布或上架时，平台核对引用的连接存在、工具在连接的白名单内。

P6 详细设计必须回答的问题：

1. Gmail 正文是 base64url 编码，模型读不懂。建议给连接模板加声明式的响应变换规则（平台的通用代码，规则本身是数据）。
2. 评测没有员工，怎么测要员工授权的应用（12.5）。
3. 飞书员工令牌约两小时过期，刷新的并发控制（多实例同时刷新只能成功一个）。

### 7.4 个人空间（P3）

| 项 | 设计 |
| --- | --- |
| 元数据 | 在 Postgres：文件标识（改名不变）、所属用户、路径、当前版本、锁 |
| 内容 | 在对象存储：每个版本一个对象，对象键用版本标识，不用路径 |
| 版本与回收站 | 由元数据实现，不依赖对象存储自己的版本功能 |
| 上传下载 | 平台鉴权、记审计后签发限时链接，浏览器直接和对象存储传输 |
| 配额 | 每人容量上限、单文件上限 |
| 取证 | 一名管理员申请、另一名批准，限时只读，每一步记审计 |
| 停用 | 冻结 90 天，可移交，到期删除 |

**对象存储的抽象放在 xuanpu，不放进 taifeng-stores。** taifeng-stores 只装内核协议的适配器，而文件中心不是内核协议。抽象只有一个小协议：读、写、删、分段上传、签发限时链接。实现两个：兼容 S3 的（生产用阿里云 OSS），和落在本地目录的（只用于单机试用，让快速上手仍然不依赖外部服务）。

会话里上传的附件、agent 的产出也是个人空间里的文件，不另建一套存储。

### 7.5 空间进会话与执行环境（P4）

**隔离粒度**：执行环境按（租户，业务包，版本，用户）划分（ADR 0007 决策 5）。连接器进程仍按（租户，业务包，版本）共用。系统会话没有用户，仍按运行时共用。

内核刚补的执行归属标识（脚本调用带会话标识）让另一条路成为可能：引擎池不拆，只把脚本按会话分发到各自的沙盒。本文**不采用**，原因是只有脚本调用带了标识；命令执行器和工作区文件协议的调用里没有（它们在建引擎池时一次绑定）——那样会变成脚本隔离了、命令和文件工具没隔离。维持 ADR 0007 的做法，同时向内核提一项新需求：命令执行与工作区文件访问也带上归属标识。拿到之后可以把引擎池并回去，那是纯优化，不影响对外行为。

**沙盒里能看到什么**（ADR 0007 决策 5、ADR 0009 决策 4）：

| 目录 | 权限 | 内容 |
| --- | --- | --- |
| 业务包目录 | 只读 | skill 与脚本 |
| 应用专属目录 | 读写 | 这名员工在这个应用下的目录。选中的文件拷进来，产出写在这里 |

第三档「整个个人空间」暂不提供。

**沙盒目录是缓存，不是数据的家。** 会话换到别的节点时，目录从对象存储重建。每轮对话结束时比对变更，改过的文件作为新版本上传，逐个记审计。

**文件给模型看**：图片和 PDF 作为消息附件直接给模型；其余类型进沙盒由脚本处理。P0 之后（第 8 节），PDF 附件在内核稳定层里，内核的文件类工具也可以经沙盒的文件接口读写，P4 可以给模型开放「不写脚本也能读写文件」的工具。

### 7.6 工作台（P5）

静态前端，随 Python 包分发，运行时不引入 Node 服务（ADR 0007 决策 7）。它是 JavaScript 客户端的第一个使用方。

| 页面 | 内容 | 依赖 |
| --- | --- | --- |
| 首页 | 动态（agent 做了什么）、待我处理 | P1；动态依赖 P9 才有内容 |
| 对话 | 流式输出、审批卡片、文件卡片、停止生成 | P1 |
| 应用中心 | 对我可见的应用 | P2 |
| 我的空间 | 文件树、上传下载、版本、回收站 | P3 |
| 连接 | 授权、撤销、查看「用我的授权做过什么」 | P6 |
| 我的 skill | 新建、修改、停用自己的 skill | P10 |

平台要为它补的接口：

| 接口 | 现状 | 做法 |
| --- | --- | --- |
| 会话历史消息 | 只有事件回放 | 会话主存进 Postgres 后直接查（第 8 节） |
| 会话标题 | 无 | 会话记录加字段，首轮后生成 |
| 停止生成 | 只能关闭会话 | 内核已开放取消当前一轮（第 8 节） |
| 待我处理 | 只能逐个会话查 | 新增待办索引：事件枢纽在挂起、核销时维护，按用户查 |
| 审批卡片 | 只有工具名和参数 | 补上一句人话预览和副作用分类（借 open-dots 的动作信封） |
| 提醒 | 无 | 有待办时经飞书消息提醒本人 |

### 7.7 定时与事件触发（建议新增 P9）

见 6.4 与 12.1。范围只有三样：定时触发、连接上的事件触发（首批只做飞书事件）、动态。触发出来的就是一个普通会话，走同样的闸门、预算、审计；规则 6 保证无人值守时不会对外乱发。

### 7.8 个人 skill（建议新增 P10）

员工要能把自己的做法沉淀下来：怎么写周报、客户怎么分级、报销怎么填。这些是「我的业务」，不该等管理员发版。ADR 0007 拍板结果第 5 项定的是「员工不自建助手」，这里把它收窄成：**员工可以写自己的 skill，但入口仍然是管理员上架的应用**。

| 项 | 设计 |
| --- | --- |
| 是什么 | 一个目录一份 SKILL.md，和业务包里的 skill 同一种东西。标识统一带 `me.` 前缀，不会和应用自己的 skill 撞名 |
| 存在哪 | 个人空间 `/skills/<名字>/`。版本、回收站、配额、停用后的处置都随个人空间（P3），不另建一套 |
| 怎么写 | 工作台「我的 skill」页用表单填：名字、一句话说明、指令、可调用的其他个人 skill。平台生成 SKILL.md。直接改文件要等在线编辑（P7） |
| 第一版不含什么 | 不带脚本，不能当入口，不能引用应用没有开放的工具。脚本是员工写的代码，等 P4 的按用户沙盒稳定之后再开 |
| 校验 | 保存时解析元数据，再在暂存目录里让内核实际加载一遍，与业务包发布时的做法相同 |
| 对谁生效 | 只对本人的会话。别的员工看不到，也用不到。分享给团队以后再说 |
| 在哪些应用里能用 | 应用在清单里声明 `personalSkills: true` 的会话里。租户可以整体关掉 |
| 怎么进会话 | 执行环境本来就按（租户，应用，版本，用户）划分（7.5）。组装时把应用的 skill 目录与这名员工的个人 skill 合成一个目录交给内核，并把入口 skill 可调用的子 skill 列表追加上他的个人 skill。这一步只改本地缓存目录里的副本，发布的业务包不动 |
| 治理 | 创建、修改、删除记审计；会话里调用了哪个个人 skill，内核事件里有。内容属于员工本人（规则 7），管理员看不到正文；要查看走取证通道 |
| 风险 | 个人 skill 的指令只能支配应用已经开放的工具，审批强度与预算也由应用决定，所以它拿不到比应用更多的权力。它能做的坏事是让 agent 以员工本人的身份做员工本人有权做的事，责任边界清楚 |

内核已经有「白名单之外的 skill 按策略授权」和「来源信任分层」两项能力，是这件事的正解：个人 skill 作为单独一层来源加载，由策略决定能否被发现和调用。但它们都还在实验层，所以第一版用上表的「合并目录」办法，只依赖稳定层；两项晋升后换过去（第 8 节的新需求）。

依赖 P3（存放）和 P4（按用户的执行环境）。有一个现成的用法：管理员发布一个「通用助手」应用（平台的样例里给一份），员工的个人 skill 在它里面就是自己的助手。

### 7.9 在线编辑（P7）、只读浏览（P8）

按 ADR 0007 的约束，排在最后，本文不展开。P8 需要一个平台级的出口代理来屏蔽内网地址段，这个代理也顺带解决 HTTP 连接器目前「不限制目标地址」的问题。

## 8. 底座先要动的地方（P0）

内核在 `feat/kernel-seams` 上把平台提的 14 项缺口全部补上了。它们合入发版之后，第一版留下的几个最大的限制可以直接去掉。这一步不产生员工可见的功能，但后面每个子项目都站在它上面，所以排在最前。

| 内核补了什么 | 平台与适配包跟着做什么 | 去掉的限制 |
| --- | --- | --- |
| 引擎池接受外部会话存储 | 状态面用 Postgres 时，会话主存直接进库，不再只是镜像 | 多实例不再需要为会话共享数据目录 |
| 取消当前一轮进稳定层 | 新增停止生成的接口 | 「只能关闭会话」 |
| MCP 进程经执行器启动 | 连接器进程放进沙盒；taifeng-sandbox 的执行器要返回可持续读写的进程 | 「只适合承载受信任租户」 |
| 重跑工具时带提交标识 | 过闸审计直接归到那一轮，不再只能按线程归属 | 审批后执行的调用在审计里缺提交标识 |
| 远端 MCP 客户端进稳定层 | 连接支持远端 MCP 这种传输 | 「MCP 只支持 stdio」。接一个远端 MCP server 不再需要先部署网关（ADR 0006 继续暂缓） |
| 工作区文件协议 | taifeng-sandbox 的文件视图对齐它 | 为 P4 的文件类工具铺路 |
| PDF 附件进稳定层 | P4 直接使用 | 缺口清单第 14 项 |
| 线程信息类型、模拟模型客户端进稳定层 | taifeng-stores 去掉单点引入；平台的测试可以换用内核自带的模拟器 | 两处绕道 |

**业务包归档也进对象存储。** 现在业务包发布到哪个实例，文件就解在那个实例的数据目录里，所以多实例要共享数据目录。既然对象存储已经是必需的依赖（ADR 0009），归档存进去，各实例用到时解到本地缓存。

这两件事做完，**计算节点的本地盘上只剩缓存**（业务包解包目录、沙盒工作目录），丢了可以重建。ADR 0005 决策 5「会话主存是节点本地文件」随之被取代。

同一步里顺手收掉写使用手册时查出的几处（都已记在架构总览的已知限制里）：

| 问题 | 做法 |
| --- | --- |
| 停机时等事件流结束没有时限 | 给 HTTP 服务器设收尾时限，取停机排空时间 |
| `/openapi.json` 不需要凭据 | 关掉 |
| 人工拒绝的调用没有过闸记录 | 送回拒绝时补记一条 |
| 租户配额不能修改 | 补接口 |
| 没有指标端点 | 补 Prometheus 格式的指标 |

**要向内核提的新需求**（接在缺口清单后面，不阻塞 P0）：

| # | 需求 | 谁要 |
| --- | --- | --- |
| 15 | 命令执行器与工作区文件协议的调用带归属标识（会话、提交） | 7.5：把按用户拆开的引擎池并回去 |
| 16 | `EnginePool.create` 接受多个 skill 目录与来源分层（注册表本身已支持） | 7.8：个人 skill 作为单独一层加载 |
| 17 | 白名单之外的 skill 授权策略、来源信任分层晋升稳定层 | 7.8：用策略而不是合并目录 |

**内核的审计模式本阶段不用。** 内核把会话日志后端的对接口放在了实验层，问平台要不要为它开例外。建议不开：审计模式整体还在实验层，平台的审计目前走自己的审计表，够用；等它转为稳定再评估。

## 9. 数据放在哪里

| 数据 | 放在哪里 | 谁能看 | 保留 |
| --- | --- | --- | --- |
| 租户、用户、API key 摘要、应用上架、连接登记 | Postgres | 管理员 | 长期 |
| 租户密钥、员工令牌 | Postgres，加密；主密钥在部署配置里 | 谁也读不出明文 | 到撤销或停用为止 |
| 业务包归档 | 对象存储 | 管理员 | 长期（版本不可变） |
| 会话正文 | Postgres | 员工本人；管理员走取证 | 可配置的保留期；员工可删除自己的会话 |
| 个人空间的文件（含个人 skill） | 元数据在 Postgres，内容在对象存储 | 员工本人；管理员走取证 | 到员工删除；停用后 90 天 |
| 审计 | Postgres，只追加 | 管理员看元数据；员工看自己的 | 按企业的留存要求，平台不自动清理 |
| 用量 | Postgres | 管理员 | 长期 |
| 邮件、云文档、日历 | **来源系统**，平台不存副本 | 由来源系统自己的权限决定 | — |
| 垂直系统的业务数据 | **各系统自己的库** | — | — |

外部内容会以两种形式留在平台里，设计上要承认并约束它：被模型读到的部分在会话正文里（属于员工本人，见规则 7）；审计里只留摘要（12.3）。

## 10. 部署形态

```
           ┌─ 平台实例 × N ──（同机或同集群）── 沙盒后端（Docker）
反向代理 ──┤
           └─ 飞书事件回调也从这里进来（需要公网可达，ADR 0010）

Postgres × 1 组        对象存储（阿里云 OSS）       模型网关
```

| 项 | 要求 |
| --- | --- |
| 平台实例 | P0 之后无本地状态，可以水平加。会话同一时刻只由一个实例处理，靠租约保证 |
| 反向代理 | 做 TLS；按路径里的会话标识做粘性路由；放通飞书回调地址 |
| 对象存储 | 浏览器要能直接访问它的外网地址；桶上配跨域规则 |
| 出口 | 平台节点出网的范围由部署方的网络策略约束；P8 之后另有平台自己的出口代理 |
| 试用 | 保留单机形态：控制面在内存、对象存储落本地目录、不接飞书（只用 API key）。快速上手不增加外部依赖 |

## 11. 代码与仓库布局

`xuanpu-server` 里每个域一个目录，各有自己的存储协议和迁移脚本，共用一个连接池：

```
xuanpu_server/
├── identity/       P1  用户、登录会话、飞书客户端、事件回调
├── catalog/        P2  应用上架、可见范围、组缓存
├── connections/    P6  连接登记、授权与令牌、授权流程
├── files/          P3  元数据、对象存储协议与实现、配额、取证
├── triggers/       P9  定时、事件触发、动态
├── runtime/            组装、会话、事件枢纽、连接器闸门、沙盒
│   └── workspace.py  P4  拷入、写回、变更比对
├── controlplane/       租户、API key、业务包登记、审计、用量
└── api/                每个域一个路由文件
```

新增的包：

| 包 | 内容 |
| --- | --- |
| `xuanpu-sdk-js` | JavaScript 客户端 |
| `xuanpu-workbench` | 工作台的静态文件 |
| `xuanpu-connections` | 预置的连接模板（飞书、Gmail 的接口描述子集）。只有数据，可以独立于平台发版 |

依赖方向：各个域只依赖 `controlplane` 的基础类型与保管库，互相不依赖；`runtime` 在组装时把它们接起来；域之间的联动（如停用）走 P1 的通知点，由 `bootstrap` 注册。

## 12. 把几份决定放在一起之后发现的出入

单看每份 ADR 都成立，合起来有六处对不上或没人管。每处给出建议。

### 12.1 检验标准没有对应的子项目

ADR 0009 的检验标准是「员工不在时 agent 已经做完了什么」。但 P1–P8 做出来的全是员工在场、主动发起的对话。没有任何东西会在员工不在时启动 agent。

**建议**：新增 P9「定时与事件触发、动态」，排在 P4 之后。它不含垂直业务，符合小核的判据。不做的话，平台就是一个带文件和连接的聊天工具。

### 12.2 管理员能看全部会话，和「默认不能看员工空间」矛盾

P1 设计 8.1 规定管理员可以看本租户全部会话。P6、P4 之后，会话正文里会有员工的邮件和私人文件的内容——管理员翻会话就等于翻员工邮箱，绕过了 ADR 0007 定的取证通道。不带代调用的 API key 同理，它现在也能读全部会话。

**建议**（规则 7）：管理员和系统 key 默认只看得到会话的元数据（谁、哪个应用、何时、用量、调了哪些工具）。正文只有本人可见；系统 key 只能读它自己建的、或它代调用的那名员工的会话。管理员要看正文，走取证通道。P1 可以先按现有设计做，但这条要在 P6 上线之前落地。

### 12.3 审计会把外部内容存下来

现在审计里记着工具的完整参数和返回内容（截断到 8000 字符）。接上飞书和 Gmail 之后，审计表里就会有邮件正文。这和「外部数据不搬家」相抵，也让审计表变成最敏感的一张表。

**建议**：连接上标了「读到的是外部内容」的工具，审计里只记参数摘要、返回内容的大小与摘要，不记正文。正文只在会话里。这条在 P6 里实现，作为连接的一个属性。

### 12.4 「外部内容进入会话后收紧审批」由谁来记

两份 ADR 都提了这条规则，但没说这个标记放在哪。内核有一套输入来源标记能算出同样的结论，但它还在实验层。

**建议**：平台在会话记录上放一个标记，由闸门在三个时机置位——文件拷入、以员工身份的读取成功返回、打开网页。只增不减，随会话保存，换实例也不丢。同时在工具上声明输出是否可信（这个字段在稳定层的类型上，不引入实验层依赖），等内核的来源标记转稳定后可以改为以它为准。

### 12.5 评测没有员工

评测由管理员触发，没有员工身份，也就没有员工令牌。用了员工授权连接的应用没法评测。

**建议**：放到 P6 详细设计里定。方向是给连接配一个「测试身份」（一个专用测试账号的授权），评测时用它；不配就跳过依赖该连接的用例并在报告里注明。

### 12.6 用量只到租户和用户，没有到应用

ADR 0007 的差距表第 8 项要求按人、按应用归属成本。P1 加了按用户的，按应用的没有子项目认领。

**建议**：放进 P2，用量多一个（业务包，入口）的维度。

另外，ADR 0007「对内核的依赖」一节已经过时（依据的是补缺口之前的内核）。ADR 只增不改，以本文第 8 节和更新后的缺口清单为准。

## 13. 路线

```
P0 底座升级 ─┬─▶ P1 身份 ─┬─▶ P2 应用目录 ──────┐
            │            ├─▶ P3 个人空间 ──────┼─▶ P4 空间进会话 ─┬▶ P10 个人 skill
            │            ├─▶ P6 连接与授权 ────┘                  ├▶ P9 触发与动态
            │            └─▶ P5 工作台（随各项扩充）                ├▶ P7 在线编辑
            └─ 三仓合入、发版                                     └▶ P8 只读浏览
```

| 里程碑 | 做完能看到什么 | 包含 |
| --- | --- | --- |
| M0 底座 | 多实例不再要共享卷；能停止生成；连接器进沙盒 | P0 |
| M1 能登录 | 员工用飞书登录控制台，只看到自己的会话；离职自动停用 | P1 |
| M2 能用应用 | 员工在工作台里打开应用对话、在「待我处理」里确认操作 | P2，P5 的对话与应用中心 |
| M3 数据接进来 | 应用以员工身份读飞书文档和日历、读 Gmail；对外操作由本人确认 | P6，P5 的连接页 |
| M4 有自己的文件 | 个人空间；对话里带文件，产出写回空间 | P3、P4，P5 的我的空间 |
| M5 有自己的做法 | 员工写自己的 skill，在应用里用 | P10，P5 的我的 skill 页 |
| M6 不在也在干活 | 定时与事件触发；首页的动态 | P9 |
| M7 | 在线编辑、只读浏览 | P7、P8 |

M2 和 M3 可以并行，谁先完成不影响另一个。M3 是第一个对员工有实际价值的节点：数据本来就在线上，接进来就能用，不用等个人空间。

每个子项目仍按「详细设计 → 实现计划 → 实现」走，详细设计要写明它如何满足第 5 节的七条规则。
