# R2 持久执行、触发与工作动态设计

状态：详细实施计划的设计依据，待实施。日期：2026-10-21。承接[能力总规划](2026-10-20-platform-capabilities-design.md)的R2；此次只写设计和计划，不迁移、部署或改变后台执行。

## 目标与当前基线

员工明确交办或确认一次执行安排后，关闭网页、退出登录以及平台进程重建不丢失已授权工作。时间和可信业务事件可产生持久任务；重启从可证明安全的阶段继续；不能证明外部结果的操作停止等待核实。

检出基线为xuanpu `354d51b`，server `2026.10.21.3`，taifeng `2026.10.1.11`，sandbox `2026.10.21.1`，数据库迁移至0010。[R1生产记录](../../guides/releases/2026-10-21-r1-production.md)已区分关页、服务重建补读和自动续跑；此次未重新探测生产。

| 现有机制 | R2复用及变化 |
| --- | --- |
| WorkTaskStore、员工事务、状态CAS与事件 | 保留业务状态与本人内容权限；增加持久调度、attempt及阶段提交，不再靠进程内字典决定能否执行 |
| TaskRegistry.reconcile | R1清理旧容器并结算interrupted；R2仅对明确标记可恢复的新任务执行恢复决策 |
| TaskRunner | 现有_prepare每次可能发新UserMessage；拆成阶段执行，不将原请求重新发送等同恢复 |
| ArtifactService | 既有上传幂等键继续使用；补充私有成果暂存和恢复缺失上传，不能只补已有索引 |
| R0 operation_receipt | 继续保护人工决定；它不是逐个外部调用的执行回执，新增效应意图账本，不依赖异步审计推断未执行 |
| 提醒与主动业务 | 识别、跟进、通知、停催继续沿用；“提醒我做”与“替我执行”有不同确认和授权 |
| 单实例/会话租约/执行隔离 | 全部保留；新调度字段不代表支持多实例生产或分布式高可用 |

## 方案选择与分期

推荐扩展现有PostgreSQL事务、后台生命周期和公开泰逢接口。任务状态、触发占位、回执和业务记录能共享事务；无需新增Redis或另一个任务主库。平台仅实现任务领域状态及调度协调，不自建通用工作流语言、通用cron解释器或RPC执行协议。

另两种方案：引入独立消息队列可解耦派发，但本期仍需实现事务投递、授权、检查点和副作用核实；引入成熟工作流引擎适合后续多worker及长业务流程，但本期会同时增加服务、部署和确定性重放适配。两者保留为后续架构决策，不作为本期依赖。

R2分三段：A持久执行与安全恢复；B时间/事件触发；C工作动态、客户端和故障发布验收。A完成后可独立验收立即交办的恢复，B不得绕过A直接调模型，C全部完成才宣告R2整体交付。

## 任务、执行次数和检查点

继续使用WorkTask作为员工看到的工作单位。保留原有八个status，增加dispatch_state解释排队、重试等待和授权阻塞，不把每次执行次数变成一项新工作。

- `execution_kind`：office或capability，旧记录默认office。
- office保留R1严格受理接口及材料要求；capability通过新增专用受理接口选择服务端真实目录里的入口，可以无附件。后台一期支持发布能力的只读执行；涉及写入的调用仍逐项等待明确批准。
- `completion_policy`由服务端登记的适配器确定：office必须有已核验文件；capability必须有持久轮次结论及明确工具回执。模型文字不是业务成功证明。无下游业务确认的结果仅表示处理完成，不声称付款、报销或归档完成。
- `attempt_no`从1递增；重算使用新session/thread和新可写scope，session请求键含task_id/attempt_no。原挂起续接是明确例外：保留原session/thread/call_id和批准ID，以新attempt/epoch接管并新建scope，仅服务端登记且公开契约验证的无文件依赖、无进程内状态HTTP调用可用；文件/脚本/stdio/MCP或依赖先前scratch的pending本期block_resume，不在空目录继续。旧工作区只用于明确清理或已冻结成果恢复，不直接重挂继续写。
- `lease_epoch`单调增加。所有任务阶段、成果指针、预算和效应记录写入必须比较当前attempt/owner/epoch。失效worker的迟到结果不能提交。
- 涉及共享额度的事务先取得租户/用量日额度锁，之后统一员工锁→任务→派发记录→attempt/效应/预算记录；其他事务从员工锁开始，不在持有员工锁时反向申请额度锁。候选扫描不先锁住派发行再等待员工锁；每次只载入选定任务，避免放大现有每人1000任务加载。

阶段为`accepted → inputs_pinned → executing → outputs_frozen → artifacts_committing → awaiting_decision → settled`。capability使用`executing → result_committing → settled`；等待工具批准或外部核实以业务status及专用block_reason表达。每个阶段检查点和对应任务事件同事务提交。

| 崩溃位置 | 恢复决定 |
| --- | --- |
| accepted已提交，尚未派发 | 同一task_id继续排队，先查取消、身份、授权、预算 |
| 新容器启动结果未知或旧容器尚未确认退出 | 保留资源责任，按已登记名称清理；清理未核实则阻塞，不启动第二个容器 |
| executing，确认从未跨外部效应屏障 | 清理旧资源后，以新attempt、新session和固定输入重算；展示“重新执行第N次”，不声称指令级续跑 |
| executing，已有任何write/external派发意图 | 禁止把原UserMessage整轮重放；先恢复公开内核挂起/结果记录并对照效应账本；契约不支持则进入outcome_unknown |
| 已冻结成果及私有暂存校验完整 | 不调模型；补齐缺失的幂等上传，核对全部对象后保存候选/成功状态 |
| waiting_user（行动项） | 保留候选和原决定指纹，等待本人决定，不创建第二份待办/日程/提醒 |
| waiting_user（工具批准） | 保留原session/thread/审批ID；仅无文件和进程状态依赖且公开契约通过的登记HTTP调用可接管原提交；其他情况block_resume，不丢失原pending |
| 已落库原生行动项、尚未展示回执 | 从同员工事务回放原回执；不再创建 |
| outcome_unknown | 不自动改回accepted；不因租约过期、重启、再次批准或“重试”按钮重发 |
| 旧R1终态/旧R1遗留运行记录 | 保留原结论；升级不追溯开启自动重跑；旧运行记录按R1清理并结算 |

## 外部副作用和人工核实

新效应账本包含tenant/user/task、attempt、持久logical_action_id、参数摘要、effect类别、approval_operation_id、派发状态、下游幂等键及权威回执引用。正文、凭据和原始参数不进入管理视图。

在网络发送前，必须提交`dispatch_intent`；提交失败绝不调用下游。提交后即视为“可能已发送”，直至有明确回执。状态至少区分not_dispatched、dispatch_intent、confirmed_success、confirmed_not_applied、outcome_unknown。传输超时、5xx、取消、审计失败、连接断开均不能自动推断not_applied。

稳定action_id在第一次执行计划/调用持久化时产生，并与原提交call_id绑定；跨attempt保持。若无法证明新的模型调用属于同一逻辑动作，不能靠参数相同猜测去重，更不能给新ID后再次发出。普通只读工具不借此获得写入权限。

本期不宣称任意外部系统exactly-once。仅服务器登记、经过验收的连接器适配器可以声明下游幂等键和权威查询语义；业务包自由字段、模型输出或一个HTTP 200不能开启自动重发。没有此契约时，R2遇未知写入就阻塞，并显示“请到业务系统核实”。

新增本人核实决定只允许提交已有权威业务回执或证明明确未执行的查询结果；服务端适配器独立验证后结算。自由文本“没执行，重试”不能成为证明。原任务保留证据链；后续另建任务需明确确认，且仍受原效应未知屏障约束。

## 持久授权和预算

ExecutionGrant以tenant/user/grant_id独立持久化，不要求先有task；直接交办的task或定义版本引用它。定义产生的所有occurrence共同消费该grant的总执行次数与总预算，同时每项WorkTask有更小的独立累计预算，不能每次复制全额授权。

交办授权独立于浏览器cookie寿命，持久记录委托员工、初始角色上限、能力版本/digest、输入范围、效应上限、有效期、最大次数及预算。创建和修改安排须本人明确确认。源于代员工key的授权还要检查原key是否仍有效、是否仍允许act_as；吊销后不得继续代执行。

每次认领、恢复、模型请求及外部调用前复核租户启用、员工启用、权限交集、能力/连接授权可用、授权有效期和固定输入；角色上调不扩张原授权。员工离职、租户暂停或授权撤销时停止未开始occurrence，运行中任务走取消清理；已发出的未知写入仍如实保留未知。

建议初始策略：最多3次attempt（含首次）、重试退避30秒和120秒、自动恢复窗口30分钟、单attempt活动执行600秒。等待本人批准不占运行槽，不自动批准；授权过期后等待重新确认。额度由配置与租户/员工上限取更小值，不能由模型调高。

跨attempt累计tokens、执行时长和已知费用；任务ModelClient包装器覆盖子skill及内部重试的每个实际请求，先持久预留额度并设置max_output_tokens，再调用和扣实；输入上界或网关限额无法证明时不开放该模型的后台执行。逐请求结算与根轮次subtree_usage不得双重计费。崩溃且用量未知时保持完整保守上界预留，不能退款后再跑；只有账本可读、旧预留仍计入占用且剩余预算足够覆盖下一请求完整上界时才可继续，否则block_budget。沿用现有UTC用量日和租户配额，新增本任务累计上限；预算耗尽进入blocked，原生查询/取消仍可用，恢复不重置余额。

## 时间和事件触发

`TaskDefinition`保存任务模板、持久授权、版本及触发器；`TaskOccurrence`代表一次应执行的实例，并关联唯一WorkTask。definition版本、occurrence和触发来源不能由材料内容控制。

- 一期时间规则为once/daily/weekly，复用现有日历算法和IANA时区；不自研cron。一次性时间需无歧义偏移；周期规则在夏令时缺失时刻跳过该天，重复时刻取较早的一次，确认卡明确说明。
- occurrence稳定键为definition_id/version + UTC计划时刻，或definition_id/version + 可信event_id，数据库唯一约束保障去重。
- 对通过资格检查的实例，occurrence占位、WorkTask受理和推进next_run须同一个员工事务提交，失败不得只推进时间游标。输入正本下载不放进数据库锁；提交时复核捕获的版本/digest。
- 默认错过超过15分钟不补跑并记录missed；15分钟内最多补1次。授权可明确选择coalesce_latest（合并为最近1次），不提供无限追赶；每次仍复核授权和截止时间。
- 每员工最多100个启用定义，沿用现有每员工1000项WorkTask上限；达到任务/对象配额时保留blocked occurrence和原计划时刻，设置下一次资格检查时间（默认60秒），不忙循环、不静默删除旧任务来腾额度。窗口过期按已确认misfire策略结算。已结算outbox可以压缩正文外的诊断字段，但必须保留事件/定义版本/任务关联和去重墓碑，不能TTL后重新执行旧事件。
- 运行重叠默认skip并保留skipped_overlap；不排出无限队列。暂停不丢既有结果，修改definition版本取消旧版未开始occurrence，不追溯启动历史任务。
- 可信事件一期只接平台内`workspace.file_revision_committed`、`workspace.todo_completed`和`work_task.succeeded`；事件在原业务事务提交outbox，含本人主体和精确版本引用，正文按本人授权补读。
- 源事务在员工锁内冻结已启用的definition_id/version订阅清单，后建定义不接收旧事件；outbox逐条记录投递结算，不用BIGSERIAL高水位证明较小ID都已提交；崩溃后重新认领未结算行。领域事件、occurrence、task各有去重约束。
- 默认忽略触发链自身生成的文件与状态；可信origin_chain用于环路检测，最大深度3、单定义每小时最多20次，超限暂停并通知本人。客户端metadata不得伪造来源。
- 任意外部webhook、组织级事件总线、部门流程和跨人代办不属本期；以后经独立集成适配器转换成已鉴权的领域事件。

## 工作动态和体验

主对话可提出后台交办/执行安排草稿，确认卡显示做什么、何时、用哪些材料、预算/次数和需要人决定的步骤；模型只产草稿，服务端校验。直接入口可创建、暂停、修改和取消同一记录。

工作卡展示排队、正在恢复、第N次执行、等待批准、预算不足、结果待核实和已完成；保留八个原status，新增展示字段。工作动态复用work_task_event、原生通知和主动业务引用，不再建一套聊天历史或通知系统。事件补读有本人分页游标，管理统计不含目标、文件名和成果正文。

只对等待人、最终成果、终止失败、预算阻塞及结果未知等有意义变化通知，键为task_id + semantic_transition_id；同一恢复和同一事件重复处理不重复提醒。飞书等外部投递沿用已配置渠道和原有回执边界，不用“任务成功”证明外部通知送达。

## 数据、发布与验收门槛

建议增量迁移0011持久派发/attempt/grant/budget、0012效应意图与检查点、0013定义/occurrence/outbox投递；实施开工先核对编号，已占号则整体顺延，已发布迁移不改。memory和PostgreSQL保持一致的事务语义，生产队列仅使用PostgreSQL。

R2策略任务在正常服务关闭时停止并清理执行，将dispatch设为paused_shutdown并保留非终态status/安全检查点；启动后按恢复策略认领，不先写interrupted再突破终态重跑。R1策略及已取消/失败/未知终态保持旧结论；用户取消与服务关闭是不同原因。

三个开关`durable_tasks_enabled`、`task_triggers_enabled`、`task_activity_enabled`默认false。先部署能读新字段的R2代码和增量表，再对独立合成租户开启、故障验收，最后启用正式租户。回退先停触发和新认领、结清资源，使用兼容新格式的R2代码关闭功能；旧R1严格JSON解析器不能直接读取新增记录，不能假称切回旧镜像就可无损回退。

验收必须覆盖：接受提交后SIGKILL、启动容器窗口、模型执行中、冻结后、部分上传后、原生记录提交后、外部写入成功但回执丢失、等待批准、取消/停用竞态、预算未知、时区切换、停机错过触发、乱序提交事件和循环触发。分别保留自动测试、真实PG/对象存储、Linux容器、真实模型、浏览器、构建/迁移及部署证据。没有下游计数器/权威回执时，不通过“无重复外部写入”验收。

详细实施顺序见[R2总计划](../plans/2026-10-21-r2-delivery.md)。
