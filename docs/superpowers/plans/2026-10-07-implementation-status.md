## 4. 已落地的能力

### 4.1 底座（P0）

细节与差异见 [P0 设计](../specs/2026-10-02-p0-foundation-upgrade-design.md)的状态行与 [P0 计划](2026-10-02-p0-foundation-upgrade.md)。

### 4.2 身份（P1）

九个任务全部完成，提交与验收见 [P1 交接](2026-10-02-p1-progress.md)。计划之外有两处后续改动：

- `6339500`：迁移 0005 让飞书事件的两项密钥可以为空。登录只需要 App ID 与 App Secret。两项都配齐才接收事件，否则事件回调返回 404，不降级接收明文。不配事件时，离职停用最长滞后一个对账周期。
- `898853c`：控制台区分「飞书个人登录」与「后台凭据已连接·非个人登录」，避免后台凭据看起来像员工本人。

### 4.3 员工直接对话与自动分流

- 员工登录后直接输入，不选业务包。普通入口 `/console/`；管理员入口 `/console/?admin=1`。
- `POST /v1/assistant/route`（`assistant.py` 的 `AssistantRouter`）：由配置的模型从候选目录里选一项，输出 JSON。候选目录包括本租户生效业务包的入口（最多 100 个），以及内置的 `@workspace`、`@reminders`。服务端逐项核对目录，不在目录里就报错，不默认选第一个。
- 业务、版本、入口都相同的活动会话就复用；否则新建一个钉住版本的会话，之后走原来的流式 `/messages`。切换业务时，原会话及其待审批保留。
- 主对话存在 `workspace_message`，每人一条递增序号，刷新后恢复。路由认领有 60 秒租约，模型的选择先落库，重试时不重新调用模型。业务会话历史从审计读：`GET /v1/sessions/{id}/history`。
- 与 ADR 0012 的差别：现在是「每轮选一个包」，不是「多个能力包合成一个助理」。

### 4.5 提醒与通知（ADR 0014）

- ADR 0014 推翻 ADR 0009 的决策 1、3（平台只做四件事、企业数据一律以外部为权威），以及 ADR 0012 决策 5 中的两点：提醒到点跑一轮模型，人不在时必须经飞书提醒。纯提醒到点只写一条确定性的通知，不调用模型。
- 数据（迁移 0006）：`reminder`（once / daily / weekly，带 version）、`notification`（BIGSERIAL 作游标，`(reminder_id, due_at)` 唯一）、`notification_delivery`（目前只有飞书渠道，带租约与重试）。
- 调度：没有独立服务。每个平台实例的 `ReminderWorker` 跑两个循环，一个扫到期，一个做外部投递，每秒一次，每次最多 100 条。行锁、版本核对、`ON CONFLICT DO NOTHING` 三者合起来，保证多实例不重复。停机后，一次性提醒补发一次，重复提醒把错过的合并成一次。员工停用时，同一事务里取消其提醒。
- 界面：顶栏通知浮层；右上角悬浮提示卡最多 3 张；网页用 fetch 读 SSE，token 不放 URL。「功能 → 提醒」可以不经模型手动增改删。
- 渠道：站内通知始终有；可选同时发一条飞书文本消息。最多重试 5 次，限 1 小时内；超出窗口标为 `delivery_unknown`。

### 4.6 新增 HTTP 接口

`/v1/assistant/route`、`/v1/assistant/proposals*`、`/v1/sessions/{id}/history`、`/v1/reminders*`、`/v1/notifications*`（含 SSE `events`）、`/v1/workspace/{items,files,settings,summary,messages}*`；`POST /v1/sessions/{id}/messages` 增加 `attachments`。字段以 [HTTP 接口](../../architecture/http-api.md)为准。

## 5. 与原设计的偏离

1. **无状态底座在部署中没有用上。** P0 做了 Postgres 会话主存与 S3 对象存储，为的是多实例无共享卷。但 Postgres 会话主存只支持 Chat 协议（`config.py` 第 320 行），而本机与服务器用的模型走 Responses 协议。所以这两处的会话主存都是 `state.backend: local`，文件也在本地卷，平台只能跑单实例。要上多实例，得先解决 Responses 协议的外部会话主存，或者换 Chat 协议的模型。
2. **助理的组装方式。** ADR 0012 设想多个能力包合成一个助理，现在是每轮自动选一个包（第 4.3 节）。
3. **产品定位上收。** ADR 0014 把玄圃定为企业核心，修订了 ADR 0009 的小核定位。AGENTS.md 新增了「企业核心定位」一节。
4. **路线顺序。** 见第 3 节开头。

## 6. 未验收与已知限制

未验收：

- 真实飞书应用：[飞书接入手册](../../guides/feishu-login.md#6-本地验证边界与真实应用核对清单)的五项核对全部未勾。部署记录提到迁移了「已有飞书员工映射」与会话，但没有按清单记录的真实登录证据。
- 飞书提醒消息没有在真实员工身上投递过。
- 公网：没有域名。因此没有 Nginx 虚拟主机与证书，`public_url` 仍是回环，Cookie 没有切到 Secure。新域名的飞书回调与公网 SSE 未验收。桌面包要等域名定了重建。

已知限制（摘要，全文见[架构总览](../../architecture/README.md)的「已知限制」）：

- 单实例（第 5 节第 1 条）；会话租约没有 fencing；并发数只在本实例内计。
- 容器里的沙盒放宽了 seccomp 与 /proc 掩蔽，隔离强度不等于虚拟机；Linux bwrap 没有 seccomp；macOS 后端只用于开发。
- 管理员仍可读全部会话正文。ADR 0011 规则 7 要在 P6 之前收紧。
- 对象存储与数据库不在同一事务里，可能留下孤儿对象，目前没有清理工具，也不提供永久删除。
- 浏览器关闭后没有系统推送；Mac 休眠时提醒停，恢复后补发。
- 试用工单是内存数据，重建就重置；目前只装了工单这一个样例业务。
- 没有删除租户的接口；主密钥轮换后没有批量重加密；审计没有清理与归档。
